# U3021: Call that grants a boundary module more than its ceiling

A call into a boundary module grants it more than its ceiling.

## Why Una rejects it

From edition `0.3`, each entry of `[boundaries]` in `una.toml`, or from edition `0.4` of the `boundaries` section of `ita.una`, gives a boundary module its ceiling: the most authority it may ever receive, as `C[ops]` strings (ADR 0093). At every call into the boundary, what the call grants must lie within the ceiling:

- each `with` binding that the callee's `uses` name counts at every operation the binding permits, not only those the callee declares, so rebinding a read-write binding as it is grants both;
- a handler counts with its own `uses`, the authority it runs with on the boundary's behalf;
- the `uses` of a function value or lambda given as an argument count too, since the boundary can run it.

The examples of a boundary module grant it their `given` handlers, each with its own `uses`, and are checked the same way, at the `given` line.

## How to fix it

- The repair narrows the grant to the ceiling, with `with @x = @y[ops]` or a handler whose `uses` lie within it. It names the caller's binding for `@y`: `@x` itself or the only binding that permits the operations, as U3020's repair does; when several do, it lists them, since which one the boundary receives is a decision about trust.
- When the callee has several requirements of one capability, such as `uses @a: Prices[price]` and `uses @b: Prices[set]`, the repair gives one narrowed grant per requirement, each to the operations its own requirement declares: `with @a = @full[price], @b = @full[set]`. One grant of both operations to `@a` would still grant `@b` everything its binding permits.
- When the grants of the callee's requirements already lie within the ceiling, the excess comes from something else the call grants. The repair names the handler whose own `uses` bring it in, rather than repeat the grant already written.
- When the callee needs more than the ceiling, no grant of a binding keeps both, and the repair says so, naming the requirements whose operations the ceiling withholds. A handler whose own `uses` lie within the ceiling still keeps both, as U3020's repair says for the same requirement: a handler counts with its own `uses`, not with the operations it implements. Otherwise the consumer decides between the library and the ceiling.

Raising the ceiling is a decision about trust, never a repair, and `una fix` never applies an edit of U3021 nor writes `una.toml` or `ita.una`.

## Failing example

`una.toml`

```toml
[package]
name = "demo"
version = "0.1.0"
edition = "0.3"

[boundaries]
"demo.vendor" = ["Files[read]"]
```

`src/demo/store.una`

```una
module demo.store

pub capability Files
  op read(path: Text) -> Text
  op write(path: Text, data: Text) -> Unit
```

`src/demo/vendor.una`

```una
module demo.vendor

import demo.store (Files)

pub load(path: Text) -> Text
  uses @files: Files[read]
=
  @files.read(path)
```

`src/demo/app.una`

```una
module demo.app

import demo.store (Files)
import demo.vendor (load)

pub open(path: Text) -> Text
  uses @files: Files[read, write]
=
  load(path) with @files = @files
```

## Fixed example

`una.toml`

```toml
[package]
name = "demo"
version = "0.1.0"
edition = "0.3"

[boundaries]
"demo.vendor" = ["Files[read]"]
```

`src/demo/store.una`

```una
module demo.store

pub capability Files
  op read(path: Text) -> Text
  op write(path: Text, data: Text) -> Unit
```

`src/demo/vendor.una`

```una
module demo.vendor

import demo.store (Files)

pub load(path: Text) -> Text
  uses @files: Files[read]
=
  @files.read(path)
```

`src/demo/app.una`

```una
module demo.app

import demo.store (Files)
import demo.vendor (load)

pub open(path: Text) -> Text
  uses @files: Files[read, write]
=
  load(path) with @files = @files[read]
```
