# 0032. Runtime details the specification leaves open

- Status: Accepted
- Date: 2026-09-29
- Deciders: Owner (accepted on 2026-09-29), on a proposal by Owner (overnight run)

## Context

M7 elaborates checked programs to Core IR (`spec/09`), runs them on the Una Abstract Machine (`spec/11`) with the host capabilities of `spec/14 §3`, and adds `una run` and `una test` (`spec/13 §5`). The specification defines Core IR, the evaluation rules and the traces, but not how elaboration obtains the checker's resolutions, the text of `--dump-core`, how values appear in traces and outputs, the JSON of `una run` and `una test`, how grants combine and where their paths resolve, how `Files` normalizes paths, the format of the `Keys` key file, a few semantics of the prelude, or what the call depth counts.

Decision log entries: D-098 to D-109 (`docs/history/v0.1/open-decisions.md`).

## Decision

1. **Elaboration.** Pass 2 of the type checker records its resolutions by the span of each expression: callees and their type arguments, the parameter of each argument, fields, operations, variants, capability bindings, and the labeled type of each expression and binder. The elaborator applies `spec/09 §3` to the syntax tree with these records. Only declarations without diagnostics are elaborated. `una-core` depends on `una-syntax` for spans. A Core `let` binds a right-hand side or an expression, so the value of a handled statement or of a branching construct can be bound; a `when` over literals or ranges without `else` takes its last arm as the final branch, whose condition the exhaustiveness obligation proves.
2. **The Core dump.** `una check --dump-core <module> [path]` prints, on stdout, the Core IR of the module's declarations in the text syntax of `spec/09 §2`, with every binder's type, label and refinements; the diagnostics of the package still go to stderr, and the exit code follows them.
3. **Values in traces and outputs.** A value is a JSON string holding its Una form: `"42"`, `"\"Ana\""`, `"true"`, `"unit"`, `"Open"`, `"Some(3)"`, `"Registration(name: \"Ana\", event: ...)"`, `"[1, 2]"`; a `Hashed` value is `"hashed:<hex>"`, and a function `"<function>"`. An argument whose static label is above `public` is `"<redacted:level>"`, with the label's level only. Inside any rendered value, a field whose declared type is labeled above `public` is `<redacted:level>`; an operation's outcome is redacted by the label of the binder of its result; `unit` carries no information and is never redacted. An event's outcome is `{"kind":"ok","value":...}`, `{"kind":"fail","variant":...,"value":...}` or `{"kind":"aborted"}`.
4. **`una run`.** In human mode the program's printed lines go to stdout as it prints them, and U6001 and U6003 to stderr as diagnostics, with exit code 1. U6001 points at `main`'s name and names the variant, with the payload fields whose labels are `public`; U6003 points at the call that exceeds the depth. `--json` prints `{"schema":"una.run/1","tier":0,"status":...,"output":[...],"failure":...,"diagnostics":[...],"trace":[...]}` with keys in that order; `status` is `ok`, `failed` (U6001), `aborted` (U6003, or U8001 by rule 11) or `rejected` (the checks reported errors, which `diagnostics` holds, and nothing ran); `failure` is `null` or `{"variant":...,"fields":{...}}` with the `public` fields only.
5. **`una test`.** In human mode, one line per example on stdout, `example <module> "<name>" ... ok` or `... FAILED`, followed for a failed example by the file, line and text of the expectation that does not hold, when one is to blame, and the reason; then a blank line and `<n> examples: <p> passed, <f> failed`. Exit code 1 when an example fails. `--json` prints `{"schema":"una.test/1","tier":0,"diagnostics":[...],"examples":[...],"passed":p,"failed":f}`; `diagnostics` holds the errors of the checks, when nothing ran, or U6003 and U8001 of aborted examples; each example has `module`, `name`, `outcome` (`pass` or `fail`), `reason` (`null`, or why it fails), `expectation` (`null`, or `{"file":...,"line":...,"text":...}`), `result` (`{"kind":"ok","value":...}`, `{"kind":"fail","variant":...,"value":...}` or `{"kind":"aborted"}`) and `trace`.
6. **Grants.** The grants of `[run] grants` and of `--grant` flags add up. Relative paths of `una.toml` grants resolve against the package root, and those of flags against the current directory. A `Files` path is relative to the grant's prefix: it is normalized lexically, its existing part is resolved through the file system, and a path that ends outside the prefix, absolute, through `..` or through a link, fails with `FileError.Denied`, as does an operation that the grant's mode does not allow. The key file of `keys:<file>` is a TOML table of key names to base64 keys, loaded before the run starts; the first grant that names a key wins, and an unknown name fails with `KeyError.UnknownKey`. The binary, not the library, reads environment variables for `Env.get` (`compiler/conventions.md §1`).
7. **The prelude.** `.len` of `Text` counts Unicode scalar values; `is_digits` holds when every character is an ASCII digit, so it holds of the empty text; `trim` removes Unicode whitespace at both ends; `to_int` reads an optional `-` followed by ASCII digits; `starts_with` compares scalar values; `contains` and `==` are structural; `Text` orders by scalar values.
8. **Depth.** The call depth counts the calls of functions, predicates, lambdas, policies and handler operations in progress. The evaluator runs on a thread whose stack is sized from the maximum depth, and aborts with U6003 when that stack runs short before the depth does, so it never overflows.
9. **Examples.** The expectations of an example are checked in order, and the first that does not hold fails it; then a `do` line that failed with no `expect fails` line fails it too. An `expect` line that does not mention `result` runs even when `do` failed. `expect performed @x.op` holds when the trace has a completed or failed `op` event of the instance of `given @x`, and `expect not performed @x.op` when it has none. An example whose run aborts fails.
10. **Entry and startup.** The entry of `una run` is `[run] entry`, or the module of a single file. `una run` checks the package with the grants of `[run] grants` and `--grant` together as final grants, even when there are none, so U3012 reports before execution every `uses` of `main` that they do not grant. A package without `[run] entry`, an entry without `pub main() -> Unit`, a `--grant` value that is not a grant spec, an unreadable or invalid key file, and a `--max-depth` whose stack cannot be allocated are usage errors (exit code 2).
11. **Faults.** A fault that a checked and verified program cannot reach, such as a division by zero while obligations are not verified yet (ADR 0027), aborts the run with U8001 and exit code 3, at the name of the function in progress, or at 1:1 of the package root (ADR 0022).

## Consequences

- Elaboration never repeats the checker's resolution rules, so the two cannot disagree.
- Agents read `una run` and `una test` as JSON, with traces whose values they can parse as Una literals.
- `Files` grants hold against `..` and links, at the cost of resolving paths through the file system.
- Traces never show labeled data, even inside a public record; they show less than the example of `spec/11 §5` suggests when results are labeled.
- A division by zero before M8 is reported as an internal error, which it becomes once tier 1 runs first.

## Alternatives considered

- **An elaborator that resolves names and types again:** would duplicate the resolution of fields, methods and generic instantiations, and could drift from the checker.
- **Values as JSON objects:** a second representation of Una values for agents to learn, while the Una form is already defined.
- **Lexical `Files` confinement only:** a link inside the prefix could lead outside it.

## Amendment (2026-11-06): an operation's outcome rendered at its label (S-45)

- Status: Accepted (2026-11-06), by the project's decision of 2026-11-06 on the draft `docs/plan/0032-outcome-redaction-amendment-draft.md`.
- Issue: #1552 (S-45). Implemented in both engines by the pull request that closes #1552, with `spec/07 §4`, `spec/09 §4`, `spec/11 §5`, `spec/13 §8` and `spec/26 §6` rule 4.
- This amendment adds to the accepted text above, which is unchanged; where the two differ, this amendment governs.

Rule 3 says that "an operation's outcome is redacted by the label of the binder of its result", and both engines implemented it as a redaction of the `ok` value only: the outcome's kind (`ok` or `fail`), the failure's variant and its payload were written in clear. Since ADR 0085 (S-14) whether a `Files` operation fails is labeled data, and ADR 0085 rule 7, ADR 0094 rule 2 and `spec/27 §10` rule 4 label the failure decisions of `Http`, of operations a binding labels with `gives`, and of `Limit.acquire`. The checker held those labels at every operation site, but the trace writer never consulted them.

An adversarial review of #1551 (H1; issue #1552, S-45) showed the consequence once S-42 (`spec/26 §6` rule 4) hid the events of operations performed in quiet code: three `Files.write` under `if s > i`, `s` `internal`, no longer showed in the trace, but the later public `Files.read` of the same paths came out `[fail, fail, fail]` for `s = 0`, `[ok, fail, fail]` for `s = 1` and `[ok, ok, ok]` for `s = 3`, in both engines. A limiter's token that a hidden `acquire` took showed the same way in a later public `acquire`. Quiet code is one route, not the cause: a `Files.write` of an `internal` path at a `public` program counter, whose path the trace shows as `<redacted:internal>`, is recovered exactly from the outcomes of later public reads, in editions `0.1` to `0.4`; a request whose `internal` body the server decides on (S-15), and a failure of an operation a binding labels with `gives`, are others.

Rule 3 now reads, for a run's trace:

> **Outcomes.** An operation's outcome is rendered at its **outcome label** `L_out`: the label of the decision whether the operation fails and of its payload (`spec/07 §7` rule 4: the deciding arguments capped at `accepts`, the file-state label for `Files`, ADR 0085, the `gives` label, ADR 0094 rule 2, and `internal` for `acquire` of `std.limit`, `spec/27 §10` rule 4), joined with the labels of its failure type and of its result's binder. When `L_out` is above `public`, the event's outcome is `{"kind":"redacted","level":"<level>"}`, with the level of `L_out` only: whether the operation returned or failed, the failure's variant, its payload and the value are not written, and no text is built from the value, so a redacted outcome never raises the abort of `spec/11 §7` for an integer too long for text. When `L_out` is `public`, the outcome is rendered as before: `{"kind":"ok","value":...}` with the value redacted by the binder's label, or `{"kind":"fail","variant":...,"value":...}`. `aborted`, `interrupted`, `cancelled`, `stop`, `timeout` and the `aborted` of a task are not decisions of the operation and keep their kinds.

`L_out` is static: the checker computes it once per operation site, elaboration carries it in Core IR as the `outcome` label of the operation (`spec/09`, `spec/13 §8`), and the native backend embeds it in its description of the site. Whether an outcome is redacted therefore depends on no value. Both engines join it with the label of the binder of the result, so a binder annotated higher than the operation's result also redacts.

**Examples.** An example's trace keeps its outcomes in clear, as S-42 keeps the events of quiet code there: an example's data come from its source (ADR 0078), and `expect performed` and the reasons of a failed example read them. `una test --json` is therefore unchanged.

**Editions.** As S-42, the rule applies to a run in every edition this compiler accepts (`0.1` to `0.4`): the trace is the `public` view of a run in each (`spec/26 §6` rule 4), and gating it would keep the routes at a `public` program counter open in the older editions. The released lines (`v0.3.17`, `v0.1.13`) are a separate decision of the project.

**Soundness argument** (not a theorem; modeling it in F1 is future work). For an event that is recorded, its pc and effect floor `public` after S-42, the outcome the trace writes is the value the program receives. Its decision and payload carry the decision's label and its value the binder's label; T6 (`spec/07 §1`) says the parts labeled `public` are equal in two runs whose inputs agree at `public`. Writing exactly those parts, and the constant `redacted` with a static level otherwise, adds nothing a `public` observer of the program could not already see. With S-39 to S-44 for the occurrence of events, their `seq`, paths and ids, every recorded event is a function of `public` data, with the open exception of #1545 (slots and parks of quiet tasks) and the timing channels that `spec/27` reports.

### Choice

The other options were rejected: rejecting state-changing operations under a raised program counter rejects servers that act after branching on a network result and still leaves open the routes at a `public` program counter (an `internal` path, a write's own outcome, a server's decision, a `gives` label); host state labeled by the writer is ADR 0085 already, sound for the program and silent for the trace; undoing quiet writes changes a program's meaning and cannot undo a request; declaring the trace an observation above `public` gives up the premise of S-39 to S-44. A labeled audit trace (#1554) is a complement for accountability, not a fix.

The result binder's label is part of `L_out` although the kind of an outcome does not depend on the value: it is the conservative choice, and it covers decisions that the checker's decision label may under-approximate, such as an `Http` failure at a limit (`spec/27 §9` rule 5). Dropping it would show the kind of `Files.read`, `Env.get`, `Keys.hmac` and `Http` outcomes whose decision is `public`; that is a precision refinement for the project to decide, never a weaker rule silently.

### Consequences

- Nothing stops compiling, no check is weakened, and no edition changes its language: the change is in what a run's trace shows.
- **The cost is trace observability.** In a run's trace the outcome of every `Http` request (its result is `internal Response`), every `Files.read` (`internal Text`), every `Env.get` (`Option[internal Text]`), every `Keys.hmac`, every `Limit.acquire`, every operation a binding labels with `gives`, and every `Files` operation of a package whose file-state label is above `public`, is `redacted`. An operator no longer reads from the trace whether a request failed, or how. This deepens the accountability loss already reported for S-42; the labeled audit trace (#1554) is the planned remedy. Outcomes of `Console.print`, `Clock.now`, handler operations whose result and failure decisions are `public`, and `Files.write` in a package whose writes are all `public`, stay in clear.
- Consumers of trace outcomes must accept the kind `redacted`: the equivalence tests of both engines do, `una test`'s `expect performed` counts a redacted outcome as completed (examples are not redacted anyway), and external readers (the hunt's oracle, `docs/security/tcb.md` item 5, and the una-bench readers) need adjusting.
- Complexity: O(1) per operation site at check time (one label recorded), O(1) per event at run time (one test of a static level), O(S) space for S operation sites. No dynamic label tracking.
- The F1 importer reads operation nodes field by field and ignores `outcome`, which is sound: F1 has no trace rendering, and the key can only hide what the trace shows.
