# 0133. Own cryptography for TLS: a pure-Rust provider in place of `ring`

- Status: Proposed
- Date: 2026-11-01
- Deciders:
- Resolves: issue #1100 (part of epic #1097); slices 1 to 3 and 5 to 7 are implemented with this record and its follow-ups; the switch of the default provider (the end of slice 7) waits for the review of slice 8
- Related:
  - ADR 0074 (the HTTP client), which chose `rustls` with the `ring` provider and records that `ring` "holds assembly and C" (its Decision and Consequences), and its residual on macOS (item 7);
  - ADR 0124 (one binary), whose embedded Z3 is the one foreign-code exception of epic #1097;
  - ADR 0122 rule 38 and `docs/security/tcb.md` (Ed25519 for the registry client is already pure Rust);
  - ADR 0119 (`una-hash`, `getrandom` as the operating system's random source);
  - ADR 0058 (`unsafe` at the runtime boundary);
  - `docs/compiler/architecture.md §7` (the allowlist of external crates);
  - issue #1093 (own big integer), issue #1092 (symbol check on shipped artifacts).
- Target: the toolchain and the runtime (`una-http`, so `una`, `una-rt` and every program that uses `Http`). No construct of the language changes, so no edition changes (`spec/13 §7`).
- Amends, on acceptance and with the last slice: ADR 0074 (the TLS stack: the provider), `docs/compiler/architecture.md §7`, `docs/security/tcb.md` (the trusted base and the reference to `ring`).

> **In plain words.**
> - **Why.** `ring` compiles C and assembly (from BoringSSL). It is linked into every program that uses HTTPS. Una admits no foreign code (epic #1097).
> - **What.** A new crate, `una-crypto`, of pure Rust with `unsafe` forbidden, written from the specifications and checked against the RFC vectors and Google's Wycheproof vectors. A small adapter in `una-http` plugs it into `rustls` as its `CryptoProvider`.
> - **`rustls` stays.** It carries no foreign code (rule 3, verified).
> - **In slices.** This record covers all of it; slice 1 (SHA-2, HMAC, HKDF, ChaCha20-Poly1305, X25519) shipped with it, slices 2 and 3 (AES-GCM, Ed25519 verification), slice 5 (ECDSA P-256/P-384 verification) slice 6 (RSA PKCS#1 v1.5 and PSS verification) and slice 7 (the provider in `una-http`, behind the cargo features `own-crypto` and `own-provider`) follow. `ring` stays the default provider until the independent review of slice 8 allows the switch.

## Context

### What `ring` is in the tree

`rustls` 0.23.46 is built with `default-features = false, features = ["ring", "std", "tls12"]` (`Cargo.toml`). The `ring` feature enables `ring` 0.17.14 as the provider and as the signature backend of `rustls-webpki`. `ring` has a build script that compiles C and assembly (`cc`). `rcgen` also uses `ring`, in `una-http`'s dev-dependencies only (it makes the tests' certificates).

### What the provider has to give

`rustls::crypto::CryptoProvider` has five parts: `cipher_suites`, `kx_groups`, `signature_verification_algorithms` (used by `rustls-webpki` for the certificate chain and by the handshake for `CertificateVerify`), `secure_random` and `key_provider`. A cipher suite needs a hash, an HMAC, an HKDF (TLS 1.3) or a PRF over the HMAC (TLS 1.2), and an AEAD. The client needs no signing: `Http` is a client, and `una-http` serves nothing over TLS (`serve.rs` reads PEM only to hold the types).

### What the card lists

SHA-256/384/512, HMAC, HKDF; X25519; ChaCha20-Poly1305; AES-128/256-GCM; Ed25519; ECDSA P-256/P-384 verification; RSA PKCS#1 v1.5 and PSS verification. That is the set `rustls-webpki`'s verification algorithms and the TLS 1.3 and 1.2 suites of `ring`'s provider need, except ECDH on P-256 and P-384 (Question 2).

## Decision

### Crate and boundaries

1. **`una-crypto`** is a new workspace crate (`crates/una-crypto`): primitives only, with a byte-slice interface, no allocation in the hot paths, no `rustls` dependency. `#![forbid(unsafe_code)]` holds for the whole crate (it is also the workspace lint). Its one normal dependency is `zeroize` (rule 7); it has no build script, no `-sys` crate, no C, no assembly, no FFI.
2. **The adapter** (`CryptoProvider`, the suites, the key exchange group, the verification algorithms, `SecureRandom`) is a module of `una-http` (`crates/una-http/src/provider`), written in the last slice. `una-crypto` stays free of `rustls`, so it can be tested and reviewed alone and reused (the registry client may use its SHA-2 and Ed25519 later).
3. **`rustls` carries no foreign code, and stays.** Verified on 2026-11-01 for `rustls` 0.23.46, `rustls-webpki` 0.103.16, `rustls-pki-types` 1.15.1, `subtle` 2.6.1, `zeroize` 1.9.1 and `untrusted` 0.9.0 (`once_cell` and `webpki-roots` are Rust and data): none has a `.c`, `.cc`, `.h`, `.s` or `.S` file; the only build script is `rustls`'s, which does nothing unless the nightly-only `read_buf` feature is on (it is off here); the only `asm!` is the empty compiler barrier of `zeroize` (Rust inline assembly, no instructions emitted). With the `ring` feature removed, `cargo tree -p una-http -e normal` contains neither `ring` nor `cc` (checked). `rustls-webpki` then has no signature backend of its own, which is why the verification algorithms are ours (slices 3 to 6). `getrandom` remains for the random source: its operating-system calls are the same trusted code `una-hash` already uses (ADR 0119).
4. **`ring` leaves the shipped graph at the switch and stays only as a development reference.** In `una-crypto` it is a dev-dependency for differential tests (rule 12), and in `una-http` it stays a dev-dependency (`rustls` with its `ring` feature, and `rcgen`) because the test servers need signing and certificate generation, which a client provider does not provide. A dev-dependency never reaches a shipped build; the release gate checks the shipped artifacts' symbols (#1092). Open question 1 asks whether even that should be removed.

### Discipline

5. **Constant time.** For every secret (keys, nonces' derived state, plaintext, scalars, MAC keys, tag comparison operands): no branch, no memory index, no loop count, no shift amount, no division or remainder and no early exit depends on it. Comparison is `ct::eq`; selection is by masks (`mask64`, bitwise select); `core::hint::black_box` stops the optimizer from re-introducing a branch in comparisons and masks. Lengths, counters and the round number are public. AEAD open verifies the tag over the whole ciphertext before it decrypts a byte and leaves the buffer untouched on failure.
6. **Indices.** The workspace denies `clippy::indexing_slicing`. A module whose arrays are indexed by a loop counter bounded by a constant, or by a slice bound computed from public lengths, allows it for the module, with a comment naming this rule. A review of those modules checks that no index derives from a secret. Table lookups indexed by secret data are forbidden (this rules out the classic T-table AES, rule 14).
7. **Wipe.** What the code does: every type that holds secret state (hash state that absorbed a key, HMAC and Poly1305 keys, ChaCha20 state and key stream block, X25519 scalars and the ladder's and the inversion's named intermediates, and the powers of the state and the product temporaries of the AES S-box) is wiped when it is dropped or when its function ends, with `Zeroize` from the `zeroize` crate, which writes volatile; the compression functions read the hash buffer in place, with no copy of it. What it does not do, stated plainly: copies in registers and on the stack that the compiler makes of by-value temporaries inside the field and block functions cannot be wiped from safe Rust; arrays the crate returns (a tag, a shared secret, a derived key) are the caller's to wipe, since a function that hands an array over cannot. `zeroize` is pure Rust, already in the tree through `rustls`, and is allowed for `una-crypto` by this record (`architecture.md §7`); a hand-written wipe without a volatile write is removable by the optimizer. Its inline `asm!` (an empty compiler barrier) and its `unsafe` volatile write join the trusted base, which Open question 6 asks the project to confirm.
8. **Target limit.** The field arithmetic of X25519 (and later P-256/P-384) multiplies 64-bit words into 128 bits. That is constant time on x86-64 and AArch64, the targets Una ships; it is not guaranteed on 32-bit targets or on cores with data-dependent multipliers, which Una does not ship. Variable-time work is allowed only on public data and is labelled where it occurs (signature verification: the message, signature and public key are public).
9. **How constant time is tested.** Rust and LLVM give no constant-time guarantee, so three layers, none a proof: (a) the structural rules 5 to 7, enforced by lints and by review; (b) a statistical test per primitive in the dudect style (`tests/timing.rs`: two input classes that differ in a secret, interleaved at random, the slow tail cropped, Welch's t below 10), `#[ignore]` in the ordinary run and part of the release evidence, run on the release candidate on a quiet machine with `--release` (heavy evidence runs on the release candidate, not on every pull request); (c) the independent review of the last slice reads the disassembly of the compare, select and ladder routines for secret-dependent branches. The statistical test passed for `ct::eq`, the ChaCha20-Poly1305 and AES-GCM tag checks, X25519 and the AES-GCM key schedule, hash subkey and stream (fixed key and plaintext against random ones, 128- and 256-bit keys); Ed25519 verification handles public data only and has no timing test.
10. **Complexity and speed** (the project's rule: best average-case complexity, stated, with scaling tests). All primitives are linear in the input (`O(n)` hashing, MAC, AEAD, `O(L)` HKDF), X25519 is a fixed 255-step ladder (`O(1)`). `tests/perf.rs` (release builds) checks that 8 times the data costs between 4 and 16 times the time, and a throughput floor. Measured on the development Mac (Apple silicon, release, no hardware instructions): SHA-256 about 180 MiB/s, SHA-512 about 290 MiB/s, ChaCha20-Poly1305 about 420 MiB/s, AES-128-GCM about 55 MiB/s, AES-256-GCM about 45 MiB/s, X25519 about 33 microseconds, Ed25519 verification about 200 microseconds. These are enough for an HTTP client whose bodies are `Text` (ADR 0074); hardware acceleration (SHA extensions, AES instructions, NEON) needs `core::arch` intrinsics, which are `unsafe` in Rust, so it is out of scope and would need its own record (Question 3).
11. **Test vectors.** Each primitive is checked against (a) the vectors of its specification (FIPS 180-4, RFC 4231, RFC 5869, RFC 7748 including the iterated vectors, RFC 8439), and (b) the Wycheproof vectors of C2SP/wycheproof, licensed Apache-2.0 (the licence file is vendored beside them, the same licence as this repository). They are vendored under `crates/una-crypto/tests/vectors/wycheproof/` at commit `d17cc89fa5c8f4f4d378b5385ebf75da5d0926c9` (2026-10-23), one file per algorithm, and `tests/vectors/DIGESTS.sha256` pins the SHA-256 of each; `tests/vectors_pinned.rs` fails when a file differs from its pin, has none, or is missing (its checker is exercised by a negative test that deletes, alters and unpins files and adds an unpinned one). Updating means fetching the files at a named commit, regenerating the digests in the same change and re-running every test; a vector that a primitive rejects is a bug in the primitive, never a reason to drop the vector. Slices 2 and 3 vendor `aes_gcm_test.json` and `ed25519_test.json`; slice 5 vendors `ecdsa_secp256r1_sha256_test.json`, `ecdsa_secp256r1_sha256_p1363_test.json`, `ecdsa_secp384r1_sha384_test.json`, `ecdsa_secp384r1_sha384_p1363_test.json` and `ecdsa_secp384r1_sha256_test.json` (the pairings TLS and X.509 use; the SHA-512 and SHA-3 files of the Wycheproof set are not offered by the crate) and RFC 6979 Appendix A.2.5 and A.2.6 as `tests/vectors/rfc6979_ecdsa.json` (public keys and signatures, SHA-256 and SHA-384 rows, extracted from the RFC text; its digest is pinned the same way); slice 6 vendors the RSA files (rule 18). A test counts the vectors it ran and compares the count with the file's `numberOfTests`, so a silently skipped group fails. Vectors that the typed interface cannot express are skipped and counted: for ChaCha20-Poly1305 a nonce that is not 12 bytes (asserted invalid in the file); for AES-GCM other nonce sizes, 192-bit keys and tags shorter than 16 bytes (valid in the file; a truncated tag is still checked to be a prefix of the computed tag).
12. **Differential tests.** Against `ring` (SHA-2, HMAC, HKDF, ChaCha20-Poly1305, later AES-GCM, Ed25519, ECDSA, RSA) and `curve25519-dalek` (X25519; `ring` cannot take a chosen private key), with deterministic pseudo-random inputs around every block, length and limb boundary, as dev-dependencies only. Both are already in `Cargo.lock`; no crate is added to the tree.

### Algorithms

13. **Hashes and MACs.** FIPS 180-4 SHA-256, SHA-384, SHA-512 with data-independent compression; HMAC (RFC 2104) over a `Hash` trait; HKDF (RFC 5869) with the 255-block limit and an error, not a panic, beyond it. Lengths are checked, not assumed: `finalize_into`, `mac_into` and `hkdf::extract` refuse an output slice of the wrong length, and `hkdf::expand` refuses a pseudorandom key that is not exactly the hash length. `hmac::verify` accepts a full-length tag only; `hmac::verify_truncated` is the explicit opt-in for protocols that truncate (RFC 2104 §5), with a tag of at least half the hash length. The bit length of a message is kept modulo `2^64` (`2^128` for SHA-384/512), the wrap of FIPS 180-4's length field, unreachable in memory.
14. **AES-GCM (slice 2).** No table lookups indexed by secrets: AES is bitsliced. Four blocks are processed at once, the state being eight 64-bit planes (plane `b` holds bit `b` of the 64 state bytes). SubBytes computes the inverse in GF(2^8) as `x^254` with a chain of four bitsliced multiplications and seven squarings, then the affine map; ShiftRows and MixColumns are fixed lane permutations; the key schedule uses the same SubBytes. A test checks the bitsliced S-box against its arithmetic definition on all 256 inputs. GHASH multiplies with 64-bit integer multiplications on operands spread over every fourth bit (so partial sums cannot carry into each other), takes the high half from the bit-reversed product, and combines three of those in a Karatsuba step with a shift-and-XOR reduction; it relies on a constant-time integer multiplier (rule 8). Only the 96-bit nonce and the 128-bit tag of TLS are offered. It is slower than hardware AES by an order of magnitude and is accepted for that reason (rule 10; measured about 55 MiB/s for AES-128-GCM and 45 MiB/s for AES-256-GCM). Because of that cost, the provider orders ChaCha20-Poly1305 first when both are offered.
15. **Ed25519 verification (slice 3)** shares the field of X25519 (now `fe25519`), adds SHA-512, the group in extended coordinates (unified, complete addition; no division) and scalar reduction modulo the group order, and is strict (RFC 8032 and the Wycheproof EdDSA vectors; ADR 0122 rule 38 for the registry client). A signature verifies only when: `S` is below the group order; the key is a canonical encoding of a point, is not the identity and lies in the prime-order subgroup (`[L]A` is the identity), which refuses every small-order key and every key with a torsion component; `R` is not the identity encoding; and the canonical encoding of `[S]B - [k]A` equals the 32 bytes of `R`. **Cofactor behaviour:** the cofactorless equation is checked, and because the key is torsion-free, it implies the cofactored equation of RFC 8032 §5.1.7 and the reverse, so verifiers cannot disagree through the cofactor; `R` needs no separate decoding, since a non-canonical or torsion `R` cannot equal a canonical encoding of a point of the prime-order subgroup. The Wycheproof vectors flagged `SmallOrderPublicKey` and `MixedOrderPublicKey` (result `acceptable`: a cofactored verifier with lenient key rules may accept them) are therefore rejected, and a test asserts it. Verification uses public data only, so the group arithmetic is variable time (4-bit windows, a shared sequence of doublings); the cost is about 200 microseconds on the development Mac, one more scalar multiplication being the subgroup test. Signing is not part of the crate: the client needs only verification.
16. **ECDSA P-256 and P-384 verification (slice 5)** (`ecdsa`, on the fixed-size Montgomery arithmetic of `mont`). *Why not the big integer of #1093:* `una_core::bigint` is variable length and allocating, lives in the compiler's core crate (which `una-crypto` must not depend on), and its multiplication and reduction branch on operand values; a field of exactly 4 or 6 limbs is both faster and structured so that its operations do not branch on operands. `mont` is generic over the limb count (`Mont<N>`), with a coarsely integrated Montgomery product, masked carries and masked final subtractions, and a 4-bit-window Fermat inversion with a public exponent; it serves both the field and the scalar ring. Verification handles public data only (rule 8), so the group arithmetic (Jacobian coordinates, `a = -3`, explicit identity, doubling and opposite-point cases) is variable time and labelled.
    - **Interface.** `verify_asn1` (DER) and `verify_fixed` (`r || s`) for `Curve::{P256, P384}` and `HashAlg::{Sha256, Sha384}`, so all four pairings of `rustls-webpki` (`ECDSA_P256_SHA256`, `_P256_SHA384`, `_P384_SHA256`, `_P384_SHA384`) are one call. The key is the 65- or 97-byte uncompressed SEC 1 point only (compressed and hybrid forms are refused, as `ring` refuses them).
    - **Point validation.** Coordinates below the field prime and on the curve; the cofactor is 1, so on-curve is the subgroup test, and the identity has no uncompressed encoding.
    - **Signature parsing.** Strict DER: a `SEQUENCE` of exactly two `INTEGER`s, minimal definite lengths (the long form only for 128 and above, one length byte), no trailing bytes, no negative integer, no redundant leading zero, no empty integer. `r` and `s` in `[1, n - 1]`. The fixed form must be exactly `2L` bytes.
    - **High `s` is accepted** (the `(r, n - s)` twin of a signature verifies), as TLS, X.509, `ring` and `rustls-webpki` do; the module documents it and a test asserts it. A caller that needs unique signatures adds its own rule.
    - **Digest.** SHA-256 or SHA-384 of the message; the leftmost `L` bytes when longer than the order (P-256 with SHA-384), the whole digest as an integer when shorter (P-384 with SHA-256), then one conditional subtraction of `n` (FIPS 186-5 §6.4.2).
    - **Algorithm and complexity.** `w = s^-1`, `u1 = z w`, `u2 = r w`; `R = u1 G + u2 Q` by Shamir's trick: the two scalars share their `8L` doublings (256 for P-256, 384 for P-384), each is read in 4-bit windows against a table of the first 15 multiples of its point (`G`: built once; `Q`: 15 additions per call), and `x(R) mod n` must equal `r`. Constant group work (`O(1)`) and `O(|M|)` for the hash. Measured on the development Mac (release, scalar code): about 280 microseconds for P-256 and 380 for P-384 per verification; `ring` is faster (assembly), which is accepted (a handshake verifies a handful of signatures).
    - **Tests.** Wycheproof (2,002 vectors in five files, exact valid/invalid), RFC 6979 A.2.5 and A.2.6 (both pairings, both forms), a differential against `ring` (random keys, DER and fixed signing, mutated key, message, DER and fixed signature, truncation and extension: the verdicts of both libraries are equal in every case), keys equal to `G` and `-G` (private scalars 1 and `n - 1`, made with `ring`) which drive the equal-point and opposite-point branches of the group law, key and signature policy cases, and a scaling test (`tests/perf.rs`). Unit tests check the curve constants (`G` on the curve, `(n - 1) G = -G`, `n G` the identity, every table entry on the curve) and the Montgomery arithmetic.
    - **Review follow-ups (slice 6).** `Mont::pow` is documented as public-exponent only (its table is read at an index taken from the exponent), `Mont::new` carries debug assertions for its preconditions (odd modulus, nonzero top limb, greater than 1), and a constructed test covers a signature whose `R` has `x(R)` in `[n, p)`, where `r = x(R) mod n` differs from the coordinate: a point `R` with `x = n + t` is picked on the curve, `s = 1`, and the public key is solved as `Q = r^-1 (R - z G)`; the test fails if the final reduction is removed (checked).
17. **The provider (slice 7).** TLS 1.3: `TLS_CHACHA20_POLY1305_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_AES_128_GCM_SHA256`; TLS 1.2 (kept, the `tls12` feature is on today): the ECDHE-ECDSA and ECDHE-RSA suites with the same AEADs, in all nine suites ChaCha20-Poly1305 first (rule 14). Key exchange: X25519 only (Question 2). `SecureRandom` is `getrandom` (the operating system's source, the one `una-hash` uses; no new crate: `getrandom` and `libc` are already allowed for `una-http` by ADR 0074 and in the tree); `KeyProvider` refuses every key (a client provider; the test servers use `ring`, rule 4). The verification algorithms are the list `rustls-webpki` documents for its default provider (ECDSA P-256 and P-384 with SHA-256 and SHA-384, Ed25519, RSA PKCS#1 v1.5 with SHA-256/384/512 with and without the `NULL` parameters, RSA-PSS with SHA-256/384/512), the same 14 identifiers and the same scheme mapping, each backed by `una-crypto` with its stricter policy. `rustls`'s generic `HkdfUsingHmac` and `PrfUsingHmac` build the TLS 1.3 key schedule and the TLS 1.2 PRF on the provider's HMAC; the adapter adds the hashes (SHA-256 and SHA-384, with a forkable running state for the transcript), HMAC, the three AEADs' record protection for both protocol versions, the X25519 group and the algorithms above. QUIC is not offered (`quic: None`). The code is `crates/una-http/src/provider/` (`mod`, `hash`, `aead`, `kx`, `suites`, `verify`), 100% safe Rust, no `unsafe`.
    - **Selection, and why `ring` is still the default.** The switch merges only after this record is accepted and the independent review of slice 8 is done, as the card says. Until then the provider is explicit and opt-in, never a process-wide default: `una-http` has the features `ring` (on by default; enables `rustls/ring`), `own-crypto` (compiles `una_http::provider`) and `own-provider` (builds the process's `ClientConfig` on it). `client::tls_config` always calls `ClientConfig::builder_with_provider`; no code path calls `ClientConfig::builder()` or reads a process default provider, and a provider that cannot serve the default protocol versions leaves no configuration at all (every `https` request fails with `Error::Tls`, instead of falling back to another provider). The workspace `rustls` no longer has the `ring` feature; `ring` enters `rustls` and `rustls-webpki` only through `una-http`'s `ring` feature (and, in tests, a dev-dependency). The final change of the switch is therefore a one-line edit of `default = ["ring"]` to `default = ["own-provider"]`, and then the removal of the `ring` feature.
    - **No `ring` and no `cc` in the graph (verified).** `cargo tree -p una-http --no-default-features --features own-provider -e normal,build` lists `getrandom`, `rustls`, `rustls-pki-types`, `rustls-webpki`, `untrusted`, `subtle`, `once_cell`, `zeroize`, `una-crypto`, `webpki-roots`, `una-core` and its crates, `una-sys` and `libc`: neither `ring` nor `cc` (nor `find-msvc-tools` or `shlex`). With the default features the same command lists both, as today.
    - **Behaviour that differs from the `ring` provider** (all fail closed): no ECDH on P-256 and P-384 (a server that offers neither X25519 nor a way past it fails the handshake); the stricter key and signature policies of rules 15, 16 and 18 (Ed25519 keys outside the prime-order subgroup, RSA `e` below 65537, moduli below 2048 bits counted exactly, the `RSASSA-PSS` key type); no QUIC; no signing keys.
    - **Tests** (`crates/una-http/tests/provider_parts.rs` and `provider_tls.rs`, and the existing `tls.rs` and `local.rs` suites run on the provider with `--features own-provider`). *Each part against the `ring` provider:* the 14 verification algorithms (same list and mapping; valid signatures from `ring` for ECDSA P-256 and P-384, Ed25519 and RSA 2048, 3072 and 4096 under PKCS#1 and PSS with every hash; bit flips in the signature, message and key, truncation, extension, random signatures, empty message: the same verdict as `ring` in every case; every signature offered to every other algorithm is refused by both, apart from the `NULL`-less twin of the same PKCS#1 scheme, which accepts by design); SHA-256 and SHA-384 on inputs around the block sizes with split, forked and finished contexts, and the FIPS 180-4 `abc` digests; HKDF extract and expand on 20 salt, secret and info shapes, the 255-block limit, `hmac_sign`, and RFC 5869 case 1; the record protection of every TLS 1.3 suite in both directions (own encrypts and `ring` decrypts, and the reverse) for lengths 0 to 200 and at 1000, 4096, 16383 and 16384 bytes and five sequence numbers up to `u64::MAX - 1`, with the wrong sequence number, a flipped bit in the first, middle and last byte, a shortened record and a record shorter than the tag refused; the same for the TLS 1.2 suites with 256-bit keys (the 128-bit key cannot be built outside `rustls`, so AES-128-GCM of TLS 1.2 is covered by the handshakes); X25519 agreement with `ring` in both directions, the all-zero, order-4 and `p - 1` values and wrong lengths refused. *Whole handshakes in memory, suite by suite:* each of the nine suites against the certificate kinds it can run with (ECDSA P-256, ECDSA P-384, Ed25519, RSA-2048; 24 suite and certificate combinations, 96 handshakes over four pairings) as own client against a `ring` server, `ring` client against a server whose hashes, key exchange, records and random source are the own provider's (its certificate key is loaded by `ring`), own against own and `ring` against `ring` as a control, each with the negotiated suite and protocol version asserted and 1, 16,384 and 100,000 bytes of application data both ways; certificate chains signed by authorities with ECDSA P-256 and P-384, Ed25519 and RSA with SHA-256, SHA-384 and SHA-512. *Failure:* a bit flipped in the body of an application record (explicit nonce, ciphertext, tag), a replayed record, a shortened record and an out-of-order record are refused by every receiver, for every suite and each pairing, in both directions; every one of the last 40 (ECDSA, Ed25519) or 256 (RSA) bytes of a certificate, which hold the signature of the authority, flipped in turn, is refused with the same error as with `ring`, and flips elsewhere in the certificate give the same verdict; a provider without the algorithm of the chain (RSA only against an ECDSA chain and the reverse) refuses it as `UnsupportedSignatureAlgorithm`, also in a whole handshake; a handshake signature (TLS 1.2 and TLS 1.3 forms) with a flipped bit, for another message or under the wrong scheme (Ed25519, RSA, P-384, P-521 and SHA-1 schemes for a P-256 key) is refused; and for each suite every fourth (TLS 1.3) or every (TLS 1.2) bit position of the server's flight flipped in turn gives the same verdict as the `ring` client on the same flight layout (over 1,500 positions). *Public servers:* `the_own_provider_reaches_public_servers` (ignored, needs the network) handshakes with the roots compiled into `webpki-roots`; run on 2026-11-01 against six public hosts, all TLS 1.3 with `TLS13_CHACHA20_POLY1305_SHA256`, all with a valid chain. *Not yet:* the interop run against the pinned public roots as a gate, the size and symbol checks (#1092) and the removal of the `ring` feature, which belong to the switch.

18. **RSA PKCS#1 v1.5 and PSS verification (slice 6)** (`rsa`, on `mont::DynMont`). *Why not `una_core::bigint` (#1093):* the same reasons as rule 16 (it lives in the compiler's core crate, which `una-crypto` must not depend on, it allocates, and its multiplication branches on operand values), and the job is narrow: one modular exponentiation with a public exponent of at most 33 bits on public data. *Why not `Mont<N>`:* the modulus is 2048 to 8192 bits of any bit length in between, so the limb count (32 to 128) is known only at run time, and a const-generic instance for each possible count would multiply the code. `DynMont` is the same coarsely integrated Montgomery product with masked carries and masked final subtraction, over stack arrays of 128 limbs (1 KiB each, nothing allocated) with the used limb count `k` as a field; it is tested against `Mont<4>` and against `u128` arithmetic. Montgomery needs an odd modulus (`new` refuses an even one, and `n` that is not minimal or exceeds 8192 bits). *Complexity:* the product is `O(k^2)`; `R mod m` takes `64 k - bits` modular doublings, `R^2 mod m` is the Montgomery form of `2^(64 k)` by square-and-multiply on the exponent `64 k` (about `log2(64 k)` squarings), so setup is `O(k^2 log k)` and does not use 64 k doublings of `O(k)` each; a verification with `e = 65537` is the setup, 16 squarings, 1 product and 2 conversions, and any permitted `e` costs at most 33 squarings and 32 products. `tests/perf.rs` (release) checks that doubling the modulus costs between 2.5 and 7 times (4 expected; a cubic implementation would give 8) and that the message cost is linear. Measured on the development Mac (release, scalar code): about 60 microseconds (2048 bits), 250 (4096) and 1,100 (8192) per verification, including key parsing; `ring` is faster (assembly), accepted as for rule 16. The exponentiation is variable time in `e`, which is public (rule 8).
    - **Key policy** (`rustls-webpki`'s moduli, a stricter exponent): `RSAPublicKey` DER (what a webpki verifier is handed) or `SubjectPublicKeyInfo` with `rsaEncryption` and its `NULL` parameters (the `RSASSA-PSS` key type is refused), strict DER (minimal definite lengths of one or two length bytes, positive minimal integers, no trailing bytes, no BER); the modulus is odd and has between 2048 and 8192 bits (the exact bit length, where `ring` rounds up to whole bytes and so accepts 2041 to 2047); the exponent is odd with `65537 <= e < 2^33` (`ring` verifies with any odd `e` from 3 up to 33 bits). The signature has exactly the modulus length in bytes and is below `n`.
    - **PKCS#1 v1.5** (RFC 8017 §8.2.2): `EM = s^e mod n` as `k` bytes must equal, byte for byte, `0x00 0x01 0xff... 0x00 || DigestInfo` built from the message for SHA-256, SHA-384 or SHA-512 (the `DigestInfo` prefixes of §9.2, with the `NULL`). There is no parsing of `EM`, so no lenient, BER or missing-`NULL` form can be accepted: the Wycheproof `MissingNull` vector, flagged `acceptable`, is rejected, and a test asserts it. SHA-1 and SHA-224 are not offered.
    - **PSS** (§8.1.2, §9.1.2): MGF1 over the same hash as the message, **salt as long as the digest** (RFC 8446 §4.2.3 and `ring`'s own rule). The decoding checks, in order: the recovered value fits `emLen` bytes (a modulus of `8k + 1` bits has `emLen = k - 1` and the leading byte of the recovered value must be zero; tested with moduli of 2049, 2057 and 3073 bits), the length condition, the trailer `0xbc`, the zero bits at the top of the masked data block, the zero padding string, the `0x01` separator, and the recomputed hash. Signatures made with other salt lengths are valid PSS and are rejected (asserted, and `ring` rejects them too).
    - **Tests.** Wycheproof: `rsa_signature_{2048,3072,4096,8192}_sha{256,384,512}` (3,106 vectors; the `e = 3` groups are valid under the file and refused by the key policy, asserted as such), `rsa_pss_*` with SHA-256, SHA-384 and SHA-512 (1,215 vectors; groups whose salt length or MGF hash is not the one the policy admits are asserted to refuse their valid vectors; SHA-1 and SHA-224 vectors are skipped and counted). NIST CAVP FIPS 186-3 SigVer (`SigVer15_186-3.rsp` and `SigVerPSS_186-3.rsp`, SHA-256/384/512 rows reduced to the public fields by a script, the private factors dropped, `tests/vectors/nist_cavp_rsa.json`): 324 rows, with the exact accepted counts asserted (18 PKCS#1 and 9 PSS; 1024-bit rows and PSS rows with a salt other than the digest length are refused by policy). Known answers for 16 test keys (moduli of 2048, 2049, 2050, 2056, 2057, 3072, 3073, 4096, 6144 and 8192 bits and exponents 65537, 65539, 2^32 + 1, 2^33 - 1 accepted; 3, 65535 and 2^33 + 1 refused) made with plain big-integer arithmetic and `hashlib` (`tests/vectors/rsa_test_keys.json`; OpenSSL 3.6.3 generated the keys of whole-byte size and a short script the keys of `8k + 1` bits, which OpenSSL does not produce; the keys are test-only). Differential against `ring`: `ring` signs (2048, 3072, 4096 bits; it signs no others) and ours verifies; bit flips, truncation, extension, prefix, complement, empty, message changes, the range edges (`0`, `1`, `n - 1`, `n`, `n + 2`, all ones), signatures of the other scheme or hash and mutated keys (`n` bit flips, `e` variants) give the same verdict in both on thousands of cases; the known answers of every size are verified by `ring` too and their mutations compared. Invalid vectors of groups outside the policy (another salt length or MGF hash) are asserted to be rejected as well, with one named exception, `rsa_pss_2048_sha256_mgf1_0_test.json` tc 69 ("s_len changed to 32"), a correct signature with the 32-byte salt that the policy requires, which the test asserts to verify. `DynMont::to_be` reports whether the value fits the output (every bit above it is checked in every build) and `recover` refuses a value that does not fit. Policy tests for components and for every DER and SPKI deviation listed above; random garbage never panics.
    - Open question 7 lists the policy choices where this module is stricter than `ring`.

## Consequences

- The shipped graph loses `ring`, `cc` and every assembly object of `ring`; the trusted base gains `una-crypto` (about 1,350 lines for slice 1) and the adapter, both safe Rust with the review burden of cryptography. This is the point of the card, and also its risk: an own implementation has to earn trust by vectors, differential tests, timing evidence and review, which is why slice 8 is not optional.
- Speed on bulk data drops against `ring` (rule 10 and 14). HTTP bodies are small text; the handshake cost is dominated by X25519 (33 microseconds) and signature verification.
- `unsafe_code` stays forbidden in the new crate; the `zeroize` dependency is an existing one.
- Nothing is switched by slices 1 to 7: `ring` remains the default provider, so no shipped behaviour changes yet. The own provider is available (`own-provider`) and tested against `ring` in both directions; the switch is slice 7b.
- `cargo test -p una-http --features own-provider` runs the whole existing HTTP suite on the own provider.

## Alternatives considered

- **A. Keep `ring`.** Rejected: it is the foreign code the epic removes.
- **B. `rustls` with RustCrypto crates (`rustls-rustcrypto`).** Pure Rust and a smaller job, but it adds many crates to the supply chain (`sha2`, `hmac`, `hkdf`, `aes-gcm`, `chacha20poly1305`, `x25519-dalek`, `p256`, `p384`, `rsa`, `ed25519-dalek` and their trees), some of which with their own `unsafe` and their own optimizations, and several of which (`rsa`) carry known timing advisories. The epic's rule is an implementation of our own, written from the specification and validated against public vectors. It stays the fallback if an own implementation of a verification algorithm (RSA first) cannot meet the review (Question 4).
- **C. `aws-lc-rs`.** A larger C code base with a CMake build (ADR 0074 H). Rejected.
- **D. Provider in `una-crypto`.** Rejected: it would tie the primitives' review and reuse to `rustls`' trait surface and version.
- **E. T-table AES with a cache-timing mitigation.** Rejected by rule 6: it leaks by cache timing, and a mitigation needs hardware instructions.

## Open questions

1. **Dev-only `ring`.** May `ring` stay a dev-dependency (differential tests; `rcgen` and the test servers), outside every shipped build? Removing it entirely means a test-certificate generator and a signing server of our own.
2. **ECDH on P-256 and P-384.** Not implemented in slice 5: the card does not list it and the question is open. `ring`'s default provider offers them. A client with X25519 only fails against a server that supports neither X25519 nor TLS 1.2 fallback to it, which is rare. Add them (a constant-time scalar multiplication on a secret scalar, which needs a complete-formula or ladder implementation on top of `mont` and its own timing evidence, a new slice) or accept X25519 only?
3. **Hardware instructions.** Accept the slower software primitives (rule 10), or open a record for `core::arch` intrinsics in one audited module (which needs `unsafe`)?
4. **Fallback for RSA.** The own RSA verification passes its vectors and differential tests (rule 18). If the independent review of slice 8 does not accept it, may it be replaced by a vetted pure-Rust crate as a documented exception, or does the card wait?
5. **Name of the crate** (`una-crypto`) and the placement of the adapter in `una-http` (`crates/una-http/src/provider`, built with the `own-crypto` feature; it is implemented there).
6. **`zeroize` in the trusted base.** `zeroize` contains `unsafe` code and one `asm!` (an empty compiler barrier, Rust inline assembly, no foreign code). It is already linked through `rustls` today. May `una-crypto` depend on it directly, or should the crate own a wipe, which in safe Rust cannot be guaranteed against the optimizer?
7. **RSA key policy, stricter than `ring`.** Rule 18 refuses public exponents below 65537 (`ring` verifies with `e = 3`), moduli below 2048 bits counted exactly (`ring` counts whole bytes), and the `RSASSA-PSS` key type in `SubjectPublicKeyInfo` (webpki's `RSA_PSS_*` algorithms are for `rsaEncryption` keys). Certificates from the public web satisfy all three. Confirm, or relax a point (for instance to accept `e = 3` against a private PKI)?
8. **The switch.** The default stays `ring` until this record is accepted and the independent review (slice 8) is done. Confirm the plan: flip `default = ["own-provider"]`, then remove the `ring` feature and re-check the symbols of the shipped artifacts (#1092); and confirm that X25519 only (Question 2) is acceptable at the moment of the switch, since it is the one capability the own provider lacks against `ring`'s defaults.
