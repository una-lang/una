# 0073. JSON

- Status: Accepted
- Date: 2026-10-07
- Deciders: the coordinator under the owner's delegation (2026-10-07, N-24), pending the owner's review; proposal by Owner (Una-2)
- Resolves: issue #238 (Beta)
- Amends: a new chapter `spec/23-json.md`; `spec/14 §1` (the prelude); the guides with the implementation

## Context

Real programs exchange JSON: configuration files, web APIs, logs. Today an Una program can neither read nor write it. It would have to scan text by hand with the functions of `spec/22`, which is slow to write and easy to get wrong.

The language constrains the design in several ways:
- **Numbers.** Una has no floating-point type (ADR 0068 D5). `Int` is unbounded (ADR 0004).
- **Kinds and maps.** Recursive kinds are allowed in edition 0.2 (`spec/03 §2` rule 5). `Map[Text, V]` is ordered by its keys (ADR 0069), which gives a deterministic order for free.
- **Labels.** An unlabeled position of a type is `public`, and a value flows into a constructor field only if it is labeled below the field's declared label (`spec/07 §7` rules 1 and 2). A prelude function's result is labeled with the join of its arguments' labels (`spec/14 §1`). A field access or a pattern binding takes the field's declared type, with its top label raised by the scrutinee's (`spec/07 §7` rule 3).
- **Failures.** They are declared kinds, as `ParseError` of `parse_int` (ADR 0070 X5): a function fails, and `attempt` gives the `Result`.
- **Limits.** Releasing, comparing, rendering and tracing a value MUST NOT recurse on the native stack (ADR 0060). Memory is bounded by `--max-memory`, and going over it aborts with U6003 (`spec/11 §7`).
- **Performance rule.** An ADR states the time and space complexity of what it adds, and the hot paths get scaling tests that fail on quadratic growth (CLAUDE.md).
- **Parity.** The interpreter and native code MUST agree on every output, failure and trace (`spec/16 §5`).

## Decision

### J1. The value: a prelude kind `Json`

In edition 0.2 the prelude declares a recursive sum kind:

```una
pub kind Json =
  | Null
  | Bool(value: Bool)
  | Int(value: Int)
  | Decimal(text: JsonNumber)
  | Str(value: Text)
  | Array(items: List[Json])
  | Object(fields: Map[Text, Json])
```

- **Numbers.**
  - A JSON number with no fraction and no exponent is `Int`, exact at any size: `12345678901234567890` stays exact.
  - Any other number is `Decimal`. Its `text` is the number exactly as it appears in the input, after the grammar of RFC 8259 §6 has validated it, so `1.50`, `1.5e3` and `-0.0` keep their spelling.
  - Una has no float to convert to. A program that needs the value parses `text` itself.
  - Writing a `Decimal` writes its `text`. Its type is the refined `pub kind JsonNumber = Text where is_json_number(it)`, with the opaque prelude predicate `is_json_number(t: Text) -> Bool`, true when `t` matches the number grammar of RFC 8259 §6. Parsing makes such texts, and a program makes one with `checked` (`spec/11 §4`), so a `Decimal` never holds anything else.
- **Objects** are `Map[Text, Json]`. Their keys are ordered by Unicode scalar values, as every `Map[Text, _]` is (ADR 0069). The order of the input is not kept.
- **Names.** `Json`, `JsonNumber` and `JsonError` become prelude names of edition 0.2. A user kind with any of these names is U1002, as for `Map` (ADR 0069 M10). The variant names `Int`, `Bool` and `Decimal` are qualified by their kind when ambiguous, as for any sum.

### J2. The functions

| Function | Contract |
| --- | --- |
| `parse_json(t: Text) -> Json fails JsonError` | `t` is one JSON text (RFC 8259) |
| `to_json(j: Json) -> Text` | the canonical form of J4 |
| `quote_json(t: Text) -> Text` | `t` as a JSON string literal, with the escapes of J4 |

- They are called with method syntax, as the functions of `spec/22` are: `line.parse_json()`, `value.to_json()`.
- Programs read a `Json` with `when` and the `Map`, `List` and `Option` functions they already have, for example `fields.get("name")`. No path or query language is added.

### J3. Parsing

- **Grammar.** RFC 8259, strictly: one value with optional whitespace around it. There are no comments, no trailing commas, no `NaN` or `Infinity`, and no single quotes. A number has no leading zeros (`01`) and no `+` sign. A byte order mark is a syntax error.
- **Strings.**
  - The escapes are `\" \\ \/ \b \f \n \r \t \uXXXX`. A `\u` pair of surrogates gives one scalar value.
  - A lone surrogate is a syntax error, since a `Text` holds only scalar values.
  - A raw control character below U+0020 is a syntax error, as RFC 8259 requires.
- **Duplicate keys.** Two equal keys in one object (after unescaping) are the failure `DuplicateKey`. RFC 8259 leaves this undefined, and parsers that keep the first or the last value disagree, which attackers exploit. Una rejects it.
- **Depth limit.** At most 512 nested arrays and objects. One more is the failure `TooDeep`.
  - The parser is iterative, with a stack of its own on the heap, so the limit is not there to protect the native stack (ADR 0060). It bounds the work an untrusted input can cause, and makes that bound part of the contract.
  - The limit is a constant of the language, the same in both engines. It is not a flag.
- **Failures.** In the prelude:

  ```una
  pub kind JsonError = Syntax(at: Int) | TooDeep(at: Int) | DuplicateKey(at: Int)
  ```

  - `at` is the position of the offending character, counted in Unicode scalar values, as the positions of `spec/22 §1` are.
  - A failure carries no part of the input, such as the duplicated key. Its message cannot leak data that its position does not already reveal.
  - The first error in reading order is the one reported, so the failure is deterministic.
- **Size.** There is no size limit beyond `--max-memory`. The parser allocates as it goes, and a run over the budget aborts with U6003 as any other run does (`spec/11 §7`).

### J4. Writing: one canonical form

`to_json` writes the compact canonical form:
- no whitespace;
- object keys in the map's order;
- `Int` in decimal, `Decimal` as its `text`, `true`, `false` and `null`.

Strings escape `"` and `\`, and every scalar value below U+0020 as `\b \f \n \r \t`, or as `\u00XX` with lowercase hex for the others. They also escape U+007F, U+2028, U+2029 and the bidirectional controls U+202A to U+202E and U+2066 to U+2069 as `\uXXXX`. Every other scalar value is written as itself, in UTF-8.

The result is valid JSON, and it depends on the value alone. `to_json(parse_json(t))` is a fixed point after one round: writing the parsed value of a canonical text gives that text back.

These escapes are JSON's, not the Una literal escapes of ADR 0068. Interpolating a `Json` (`"{j}"`) still writes its Una form, as for any value (ADR 0068). `to_json` is how a program gets JSON.

### J5. Labels

- **Parsing.** The result of `parse_json` and its failure are labeled like the text, by `spec/14 §1`. With `Files.read` returning an `internal Text`, the parsed `Json` is `internal`. Every value a `when` binds from it is `internal` too, since a pattern binding's top label is raised by the scrutinee's (`spec/07 §7` rule 3).
- **The positions of `Json` are unlabeled, so `public`.** A labeled value cannot enter a `Json` constructor: `Json.Str(value: token)` with a `secret` `token` is U4001 at the argument (`spec/07 §7` rule 2). This is the conservative choice. A secret leaves through a policy, whose `via` function builds the `Json` (`spec/07 §5`), or through `quote_json`.
- **`quote_json(t)`** is labeled like `t`. A program that must send a secret in a JSON body writes it with interpolation:

  ```una
  let body = "{\"token\":{token.quote_json()}}"
  ```

  The body is then `secret`, and the sink that receives it checks its `accepts`, the HTTP request of ADR 0074 for example (`spec/07 §7` rule 4). The secret is never hidden inside a value that looks `public`.
- **Writing.** `to_json(j)` is labeled with the deep label of `j`: its top label, since its positions are `public`.

### J6. Complexity

Let n be the length of the input text, or of the output text.
- **Parsing** takes O(n) time for scanning, unescaping and number validation, plus the building of each object's map. An object of k keys takes O(k log k): the keys are collected, sorted, checked for duplicates in one pass, then built into the map in bulk. When the keys arrive in order, as `to_json` writes them, the sort is a single linear pass (Rust's stable sort detects runs). So parsing is O(n + Σ k log k), summed over the objects of the input, each with k keys: O(n) for canonical input, and O(n log n) in the worst case, one object whose n keys arrive unordered. The ordered map is the decided trade (N-24): programs mostly look values up in parsed JSON, and an ordered map gives O(log k) lookups and a canonical output, against the O(n) parsing and O(k) lookups of keeping the input order (alternative D).
- **Space** is O(n). The parser's own stack holds at most 512 frames.
- **Writing** is O(n) time and space. Each map is visited in order, with no sort, and the output is built in one growing buffer.
- **Depth.** No operation on a `Json` recurses on the native stack: parsing, writing, releasing, comparing, rendering and tracing (ADR 0060).
- **Tests.** Scaling tests from 10^4 to 10^6 for parsing and writing, in both engines: long arrays, long strings, wide objects with sorted keys, and objects nested to the limit. Each fails on quadratic growth. Natively they assert a deterministic counter (copies or allocations) wherever the runtime exposes one, with timing only as a second check, wide in margin.

### J7. One implementation for both engines

The parser and the writer are a module of `una-core`, `json.rs`, over a small tree type of their own. Both engines call it, and convert the tree to their own values: interpreter values, or `una-rt` heap objects. So parity holds by construction. The differential test (`spec/16 §5`) and the conformance cases check it.

**No new dependency.** The code is about 500 lines of safe Rust, in the trusted base with the rest of `una-core` (charter §3).

### J8. Determinism and traces

`parse_json` and `to_json` are pure prelude functions, with no host operation and no trace event. Their results depend on their arguments alone.

### J9. Scope

- Edition 0.2 only.
- No new syntax, keyword or diagnostic code. U1002, U4001 and U3007 apply as they already do.
- Typed decoding into user kinds is not part of this ADR (alternative A below). It can be layered on top later.

## Consequences

- Programs can read and write JSON with exact integers, a deterministic output, a bounded depth, a stated complexity, and labels that a secret cannot slip past.
- `Decimal` keeps non-integer numbers exact but uninterpreted. A program that needs arithmetic on them parses `text` itself, until Una has a decimal type.
- Object key order is not kept across a round trip. A program that must keep it has no way to: that is the price of a canonical order.
- Building a `Json` from labeled data takes a policy, or `quote_json` and interpolation. That is deliberate friction where data crosses a trust boundary.

## Alternatives considered

- **A. Typed decoding into kinds** (`parse_json[T](t) -> T`), mapping fields by name. This is the most ergonomic for known shapes. But it needs reflection over kinds that the language does not have, rules for optional fields, extra fields and renames, and generic machinery that interacts with labels (ADR 0067). It is better as a later ADR on top of J1, which remains the representation for unknown shapes.
- **B. Numbers as `Text` only** (`Number(text: Text)`). This is simpler, but every integer, the common case, would need parsing again. **C. Numbers as `Int` only, with non-integers rejected.** This would make valid JSON unreadable, and real APIs send decimals.
- **D. Objects that keep input order** (`Object(fields: List[Entry])`). That gives O(n) parsing always, but lookup is O(k), duplicate detection still needs a sort or a hash, and the written output then depends on the producer's order. The canonical order of J1 makes `to_json` a function of the value's meaning.
- **E. Last or first duplicate wins.** Rejected: parser differentials over duplicate keys are a known attack. A failure is explicit, and the program can see it.
- **F. `serde_json`.** It is already in Cargo.lock, used by `una-rt`, `una-interp` and `una-cli` for traces and documents. But it keeps the last of duplicate keys silently, recurses on the native stack (with a limit of 128 that cannot be made part of Una's contract), and has no exact-integer mode without its `arbitrary_precision` feature, which would change the crate's behavior for every other user in the workspace. Wrapping it would mean reimplementing most of J3. Rejected for the language feature. It stays for the tool's own documents.
- **G. A label-polymorphic `Json[T]`**, with strings of type `T` (`Json[secret Text]`), so a type argument carries the labels as in `spec/07 §7` rule 1. It is clever, but every signature would have to write the parameter, and it covers only the string positions. The conservative J5 is simpler, and the HTTP sink checks the label anyway.
- **H. A depth limit as an abort (U6003)** rather than a failure. Rejected: the depth of an untrusted input is data, and a program must be able to refuse bad input without aborting.

## Amendment of 2026-10-07: variant names (N-25)

Decided by the coordinator under the owner's delegation (N-25), pending the owner's review; found by Owner (Una-2) while implementing.

J1's variants `Bool(value: Bool)` and `Int(value: Int)` cannot be declared:
- A variant named `Int` or `Bool` takes the place of the built-in type of that name in its module, so `Int(value: Int)` is U2002 ("`Int` is a variant of …, not a type").
- J1 also said the names would be "qualified by their kind when ambiguous". Una has no qualified constructor syntax, so that sentence is wrong and is withdrawn.

The kind is:

```una
pub kind Json =
  | Null
  | Boolean(value: Bool)
  --- An exact integer: a JSON number with neither a fraction nor an exponent. Other numbers are `Decimal`.
  | Number(value: Int)
  | Decimal(text: JsonNumber)
  | Str(value: Text)
  | Array(items: List[Json])
  | Object(fields: Map[Text, Json])
```

- `Integer` is not used, since it is a built-in constraint name of edition 0.2 (U1002).
- Every other rule of J1 to J9 applies with `Boolean` for `Bool` and `Number` for `Int`.
- A user variant named like a variant of `Json` or `JsonError` shadows it in its module, as a user `Some` shadows `Option`'s, and that module then cannot construct or match the prelude variant.

## Amendment of 2026-10-07: findings of the independent check (N-27)

Decided by the coordinator under the owner's delegation (N-27), pending the owner's review, after the independent check of the implementation (#291).

1. **Failures decided by the argument are labeled** (F1).
   - Whether `parse_json(t)` fails, and where, depends on the value of `t`, so its failure carries the labels of `t`, as its result does (`spec/22 §5` rule 2 states the same for `parse_int`).
   - `attempt` of it gives a `Result` labeled like `t`.
   - `if error use` runs under a program counter raised by those labels, and its value carries them.
   - `if error pass` and `if error fail` are U4002 when they are not `public` (`spec/07 §3` rule 3).
   - The same holds for every prelude function that declares its own failure and whose result carries its arguments' labels. The host operations are not affected: the arguments that decide their failures accept only `public`.
2. **`Decimal` holds only fractions and exponents** (F2). `is_json_number` is true only for a JSON number with a fraction or an exponent. So `Number` and `Decimal` are disjoint, and every `Json` survives a round trip: `checked("5", is_json_number(it))` fails.
3. **Integer literals are bounded** (F3). Converting d digits to an exact integer takes O(d²), so `JsonError` gains `NumberTooLong(at)`, for an integer of more than 4300 digits, CPython's limit, at its first character. A `Decimal` keeps its text, so it has no such limit. Writing an `Int` that the program built with more digits stays O(d²): that is a known limit, stated in `spec/23 §6`.
4. **A `JsonNumber` in a signature is its refinement** (F4). The clause of a prelude kind is now elaborated in the prelude's records. Before, a user module elaborated it as `false`, so a parameter of type `JsonNumber` made every claim about it hold vacuously, and every call was refuted.
5. **Surrogate errors follow `spec/23 §3` rule 5** (F5). The position is the first character that cannot continue a valid escape: `"\uD800` at 7, `"\uDC00` at 4.

Note (2026-10-16): `Decimal` keeps its text. In edition `0.3`, `as_f64` and `json_number` (ADR 0114 rule 10) convert between a number and an `F64`.

## Amendment (2026-11-09): `Json` values that carry labeled data (J5)

- Status: Accepted (2026-11-10), by the project's decision of 2026-11-10 on issue #917. The accepted text of this record above this amendment is unchanged; where the two differ, this amendment governs. It applies in edition `0.4` and later; editions `0.2` and `0.3` keep J5 as written (rule 4).
- Issue: #917. Design: `docs/plan/0073-json-labels.md`.

**Why.** Under J5 a labeled value cannot enter a `Json` constructor. A program that answers with data above `public` (a server that echoes request data, a tool that writes an `internal` configuration) must then either declassify through a policy or write the JSON by interpolation with `quote_json`, which loses the structure and the escaping of `to_json`. Neither is needed for soundness: the label can travel on the value.

**The change.** In edition `0.4` and later, a constructor of `Json` accepts arguments at any label, and its result is labeled with the join of every label of its arguments. The positions of `Json` stay `public`; the top label carries what entered. Reading and writing are unchanged. Alternative G stays rejected.

In detail:

1. A `Json` value has one label, its top label. The positions of `Json` stay `public` in its type, so `Json` remains the representation of J1 and no signature changes.
2. A call of `Boolean`, `Number`, `Decimal`, `Str`, `Array` or `Object` is labeled with the join of every label of every argument (`spec/07 §7` rule 3: list elements, map keys and values, the top labels of nested `Json` values) and of nothing else. `Null` is `public`; so are `Array([])` and `Object` of an empty map. A constructor under a raised program counter is raised by the branch join (`spec/07 §7` rule 2), as any expression is. Refinements are kept: `Decimal` still requires `is_json_number`.
3. Only the prelude kind `Json` gains this rule. User kinds and the other standard-library kinds keep their declared labels. `JsonError` and `JsonNumber` are unchanged.
4. Editions `0.2` and `0.3` keep J5 as written.

**What does not change.**

- Reading: a pattern binding or field access takes the field's declared type raised by the scrutinee's top label (`spec/07 §7` rule 3), so every part of a `secret Json` is `secret`.
- Writing: `to_json(j)` carries the labels of `j`; `quote_json(t)` is labeled like `t`.
- Sinks: a `secret Json` passed where `Json` (public) is declared is U4001; given to `Console`, or to a reply body above what it accepts, it is U4003. Equality of two `Json` values is labeled with both top labels. No diagnostic code is added: the U4001 at the constructor moves to where the labeled value reaches a lower declared type or sink.

**Security.** Every label that enters a `Json` is joined into its top label, and every way out (a field, a pattern binding, `to_json`, equality) is raised by that top label, so no flow refused today becomes observable at a lower label. The rule is coarser than a label per position (a public field beside a secret one reads as secret), never finer. Labels are static: Core IR, the interpreter and the native backend are unchanged, and a labeled `Json` operation argument is redacted in traces by its static label (`spec/11 §5`).

**Cost.** O(n) in the size of the constructor's argument types per call, as the field flow already is; no new fixpoint. `to_json` stays linear in the size of the value.

**Rejected.** G, `Json[T]` (every signature must name a parameter; it covers strings only), as above; a `Json` kind per label (a duplicate API, whose conversions need policies anyway); a label per position (a larger change to the representation for a finer rule that no program here needs yet).

**Note for the spec.** Once this amendment is accepted, `spec/23 §5` rule 2 states the rule for edition `0.4`, `spec/07 §7` rule 2 names the exception, and `spec/14 §1` "Result labels" lists the constructors; until then those places carry a Proposed note.

## Amendment (2026-11-26, Proposed, #1223): writing an `Int` has no digit bound

A pointer, Proposed with the amendment it points to. The amendment of ADR 0004 of 2026-11-26 supersedes the last sentence of rule F3, "Writing an `Int` that the program built with more digits stays O(d²): that is a known limit, stated in `spec/23 §6`": `to_json` writes an `Int` of any size in O(M(d) log d), after reserving the bytes of its text against the memory budget. The rest of rule F3, `NumberTooLong` for an integer of more than 4300 digits when parsing, is unchanged.
