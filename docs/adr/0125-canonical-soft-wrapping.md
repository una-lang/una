# 0125. Canonical soft wrapping at legal argument and element separators

- Status: Accepted
- Date: 2026-10-23
- Deciders: Una project (owner approved this decision on 2026-10-23)
- Resolves: issue #1113
- Amends: ADR 0020 rule 2; `spec/15 §2`

## Context

ADR 0020 rule 2 joins lines continued inside brackets and states that no line width applies. Long calls, signatures, and collections consequently remain difficult to review even when they contain legal places to continue. The repository corpus confirms this is a real, bounded problem: among 3,562 source lines in the measured examples and guide snippets, 89 lines have at least 80 Unicode scalar values, 50 at least 88, 30 at least 100, and 13 at least 120. The longest measured line is 221 scalars in `examples/pantry/src/pantry/main.una:6`; a fold call in that example is 152 scalars. These counts use Unicode scalar values, exclude blank and comment-only lines, and are a snapshot rather than a promise about future source.

`una fmt` and `una check` share one canonical form. A width policy therefore changes canonical output and can produce U7001 differences. It must be mechanical, preserve syntax and comments, and not split indivisible tokens or arbitrary expressions.

## Decision

1. The formatter uses a soft line-width target of 100 Unicode scalar values, counting indentation and every character in the rendered line. The target is not a hard maximum: a line may exceed it when no legal delimiter separator can keep it within the target or when an indivisible token or comment is longer.
2. Automatic line breaks are permitted only after a comma that separates arguments or elements inside parentheses or square brackets, where the grammar accepts a continued line. The formatter does not wrap at operators, before a comma, inside a token, or at arbitrary whitespace. It greedily keeps the latest legal separator whose preceding line fits the target; if no separator before overflow fits, it uses the first available legal separator so subsequent items can continue on their own lines.
3. A wrapped continuation is indented two spaces deeper than the indentation of the delimiter containing the chosen separator. Each nested parenthesis or square-bracket delimiter adds two spaces. If a delimiter group wraps, its closing delimiter is written on its own line at the indentation of its opener; a comma following that close stays on the same line. The normal two-space indentation rule still applies.
4. If a logical line contains a comment, its existing physical line breaks and comment placement take precedence over automatic wrapping. The formatter does not move, split, or rewrite a comment to meet the target.
5. The policy applies identically in all editions. It changes formatting only; it does not change the grammar, token spelling, AST, diagnostics other than canonical-form U7001 differences, or edition semantics. `una fmt` rewrites eligible lines and `una check` checks the resulting canonical text.
6. The formatter processes each output line in O(n) time and O(n) additional space in its token and character count, storing the comma-separated segments and rendered output. The greedy pass measures each segment once; it does not search globally for an optimal layout. It does not query terminal dimensions and has no width option.
7. Existing examples and source files are not mass-reformatted as part of this change. Any repository-wide canonical migration is a separate, reviewable change.

## Consequences

Calls and collections with legal separators become easier to scan and produce stable output independent of editor width. Wrapped groups visibly return their closing delimiter to the opener's indentation. A long atom, string literal, comment, or expression without an eligible comma remains long. Comment-bearing logical lines can exceed the target to preserve their source placement. The new canonical rule can cause U7001 for existing overlong lines with eligible separators; a formatter migration must be reviewed separately.

The width and continuation rule are now language-wide canonical-form requirements, rather than editor preferences. All formatter implementations must count Unicode scalar values and use the same separator and indentation rules.

## Alternatives considered

- **Keep unlimited lines.** This preserves every existing canonical file but leaves the measured long calls and collections unchanged.
- **Hard-wrap at 100 or split arbitrary tokens and expressions.** This would require splitting tokens, changing expression layout at non-delimiter boundaries, or rejecting source that the grammar accepts; it is not selected.
- **Break at any whitespace or operator.** This permits line layouts whose validity or grouping is harder to determine and does not meet the approved restriction to legal argument and element separators.
- **Use display columns or terminal width.** Display width depends on Unicode rendering and terminal state; terminal-dependent output would not be canonical across environments.
- **Apply wrapping only in a future edition.** Formatting is edition-independent and does not alter parsing or semantics; edition-specific behavior would create unnecessary canonical differences.
- **Mass-reformat the repository with the implementation.** This would mix implementation and mechanical migration, obscuring the behavior change; migration is deferred to a separate review.

## Amendment (2026-10-25): edition scope, the measured line and outermost-first breaks

Review of the implementation found that the decision above could not reproduce the formatter's output: the width it measured, the choice among separators at several nesting levels, the indentation of closers and the effect of a trailing comment were not defined. It also found that applying the rule to every edition would change the canonical form of released editions. The project decided the following. The decision above stays as written; where this amendment differs, this amendment applies.

1. **Edition scope.** Soft wrapping is the canonical form of edition 0.4 only. Editions 0.1 to 0.3 keep their canonical form exactly as before this ADR (ADR 0020 rule 2 as accepted): every logical line without a comment is one line, whatever its width, so code of a released edition that was canonical stays canonical and gets no new U7001. The formatter reads a file's edition from the keyword set it was lexed with, which `una fmt`, `una check` and the editor take from the package's manifest. This replaces rule 5's "applies identically in all editions" and the reason given for rejecting "Apply wrapping only in a future edition".
2. **Groups and levels.** A group is a pair of `(` and `)` or of `[` and `]` on the logical line, outside text interpolation. Its level is the number of groups of the logical line that hold it, itself included, so an outermost group has level 1. A separator is a comma directly inside a group, and its level is its group's. A comma inside a text interpolation is never a separator, since a text literal holds no line break.
3. **The measured line.** A printed line starts at the start of the logical line, right after the separator that ended the printed line before it, or at the closer of a wrapped group. Without a break, it runs to the closer of the next wrapped group or to the end of the logical line. Its width is two scalars per indentation level plus every Unicode scalar value of its text as printed on one line, including the closers of groups that do not wrap and the tail after its last separator.
4. **Outermost first.** When a printed line is wider than 100, it ends at a separator instead, which wraps that separator's group. Of the separators of the line whose text up to and including them fits within 100, the one with the lowest level is chosen, and the latest of those on a tie. Inner groups therefore break only when no separator of an outer group keeps the line within the target. When no separator fits, the line ends at its first separator. A line without separators stays whole and may exceed the target. Rule 2's "latest legal separator whose preceding line fits" is this choice restricted to one level.
5. **Indentation by nesting depth.** For a logical line at indentation level `d`, the line after a separator of level `l` is indented at level `d + l`, and the closer of a wrapped group of level `l` starts a line at level `d + l - 1`, followed on that line by the text after it. The closer of a wrapped group of level 1 is thus at the logical line's own level, that of level 2 one level deeper, and so on, whether or not the outer groups wrap. This defines rule 3's "indentation of its opener".
6. **Comments.** A logical line with a comment inside it or at its end keeps its source line breaks, each continuation line one level deeper than the line, and does not wrap. A comment after a wrapped call therefore no longer joins the call back into one line. This extends rule 4 to a comment at the end of the line.
7. **Cost.** Each printed line is found by one scan from its start, which stops at the closer of a wrapped group, at the end of the logical line, at the first piece past the target once a separator has been seen, or at the first separator after the target. Every token of a file without errors is at least one scalar wide, so a scan reads at most 102 tokens beyond the separator it chooses, and the next line reads only those again: at most `n + 102 * lines` tokens for `n` tokens, linear in the length of the line. Whether each group is wrapped is one flag per group, by its number. The formatter's tests count this work on long lists and deep nesting.
8. **What remains of rule 7.** The repository migrates only sources, examples and documentation of edition 0.4 to the new form. Every source, example, guide snippet, fixture and snapshot of editions 0.1 to 0.3 keeps its text and its diagnostic positions. The stable editions are untouched.
9. **Obligations and contracts.** Obligation identity follows the edition (`spec/12 §8`). Editions 0.1 to 0.3 keep their goal normalization exactly: white space collapses, so their ids are preserved by construction, and the hypotheses an obligation shows are its source text as written, as before. In edition 0.4, white space that holds a line break right before a `)` or `]` token is also erased, in the goal, in each hypothesis, and in the header and clauses that `una contract` shows, so wrapping a line changes neither an obligation's id nor the text shown for it. This normalization lexes the text once and passes over its closers once: linear time and space.
10. **Migration.** A change of canonical form across editions is legitimate, and the upgrade path is `una migrate`. `una migrate` to edition 0.4 applies the canonical form of edition 0.4 to every module it migrates that parses in edition 0.4, after it writes the project files and before its check of the edition (`spec/30 §8`). For a module that was canonical in its own edition, the rewrite changes only white space. The edition invariant is therefore stated over migrated packages: every edition 0.3 package, migrated to edition 0.4 by `una migrate`, checks as it does in edition 0.3, its diagnostics at the same characters, except for the differences that the editions define.
