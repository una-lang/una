# Release gates

Status: Normative for the project's workflow (#232). GitHub Actions is not used. Merges, tags and releases rest on local runs whose results are recorded, so anyone can see what was checked, on which commit, and with which outcome.

## 1. The rules

1. **A merge into `main`** needs a `scripts/local-ci.sh` PASS on macOS on the pull request's exact tip, written into the pull request body with the SHA.
   - Linux is not checked per pull request. The next gate run confirms it on `main` (`scripts/local-ci.sh --linux`, in Docker), and a Linux FAIL there is reported at once and fixed before anything else merges.
   - Except when the pull request changes what the Linux run runs: `scripts/local-ci.sh`, `scripts/local-ci/` (its Docker image), or a script that a step of it calls, such as `scripts/formal.sh` or `docs/reviews/formal-m2-replay/check.sh`, or makes a step need a tool it did not need before. Such a pull request also needs a `scripts/local-ci.sh --linux-arm64` PASS (native, a few minutes) on its exact tip, written into its body with the SHA (#605). A step that needs a tool the image lacks passes on macOS, which has it, and fails only in the container: #528's replay needed `python3`, and the first gate run of v0.3.8 failed on it (#606).
2. **A tag** `v<version>` needs a run of `scripts/release-gates.sh` in which every gate is PASS, on the gated SHA: the commit of `main` after the release pull request.
   - Its public summary (§3) is committed as `docs/validation/<version>.md` before the tag is made.
   - **The tagged commit is the record commit**, not the gated SHA, since `install.sh` reads the summary from the tag's tree, and gating the record commit again would be circular. So:
     - The tagged commit's own change, against its first parent, is exactly the summary file and, until the repository is public, the full record as `docs/releases/<version>-validation.md`.
     - Between the gated SHA and the tagged commit, only files under `docs/` change: `git diff --name-only <gated> <tag>` lists nothing else. The code, build files, scripts and `install.sh` of the tag are then those of the gated SHA.
     - Anything else that merges in between, such as a change of code, needs a new gate run, and the gated SHA becomes that commit.
   - A tag whose summary has a FAIL or is INCOMPLETE is not made.
   - Every tag and release also needs an explicit approval, recorded in the release issue before the tag.
3. **A release** publishes the archives that the `release` gate built (`OUT/clone/target/local-release/v<version>/`), whose digests the summary lists. The archives are reproducible (#679): two builds of one commit give the same bytes for each target, which the `reproducible` gate checks with a second build from cold. A published archive can therefore be rebuilt from its commit and checked against the summary's digest. The summary and the published `.sha256` files MUST agree.
4. **`.github/workflows` is not a gate.** The files stay in the repository, but no merge, tag or release waits for them or reads their results.

## 2. The gates

`scripts/release-gates.sh SHA OUT [GATE...]` runs the gates on exactly one commit, given as a full 40-digit SHA. It runs all of them when none is named.

- It makes a fresh clone of the commit for the run, `OUT/clone`, from the remote `origin` (or `UNA_GATES_SOURCE`).
- Before every gate, it checks that the clone is still that commit, with no change and no untracked file.
- A failing gate does not stop the next one.

**The hunt gate** (#767). A fixed, seeded run of the security hunt's generators: seed 767, every operator, 50 programs per operator in each of its editions, and the sample below, so 6,288 programs, each rebuilt from its seed and checked against its digest. An operator runs in editions `0.1` and `0.2` (`EDITIONS`, since #767), except the operators of families B and Q, which run in `0.2` and `0.3` (`OPERATOR_EDITIONS`, #813). Every other operator also runs some of its programs in edition `0.3` (#818): its first 10 by seed (`SAMPLE_COUNT`), and the first program of each further form, its variant, that its edition `0.2` programs have (`sample_indices`), and, for each form that only its edition `0.1` programs have, the first seed past the run's 50 whose edition `0.2` program has it, run in edition `0.3` only (`sample_forms`): 688 programs. So every form the fixed run gives an operator, in any of its editions, also runs in `0.3`, a unit test pins that no form is out of reach (today three, of F7 and T4, come from seeds past the run's), and a regression of an older rule on edition `0.3`'s code paths, which the edition gates, is run. Each sample program is its edition `0.2` program with the same seed, the same class, expected codes, form, varied literals and files but for its edition, which a unit test checks for every one, and another that every form is in the sample. Before it was pinned, a probe of the 688 (2026-10-16) compared each with its edition `0.2` twin, by the verdict of tier 0, of the full check and of a run: none differed. Units of measure, refined elements and U3025/U3026 are not run yet (#818). Measured on an Apple M1 Max (10 cores, 32 GB), four compiler runs at a time, the run of 5,100 programs took 106 seconds on a quiet machine, and 151 seconds under another load (2026-10-15); the full gate of 5,600 programs, with the native sample, the re-check comparison and families B and Q, took 205 to 215 seconds under a load average of 3.6 to 20 from other work (2026-10-16), and with the edition 0.3 sample of every form, 6,288 programs, 226 to 253 seconds in four runs of the same programs and compiler, the slower ones under more load (2026-10-16; load average at the start and the end of each): 228 seconds (1.9, 3.8), 226 (2.2, 4.4), 247 (3.5, 6.3) and 253 (4.9, 8.3). Its budget on macOS is 270 seconds (`TIME_BUDGET_MACOS`), checked by the gate, 17 seconds, about 6%, above the slowest measured run (with each run in a directory of its own and the gate's shared proof-cache key, #793, it took 252 and 253 seconds at a load of about 5, 2026-10-17). On Linux (`hunt-linux-arm64`, #793) the budget is 390 seconds (`TIME_BUDGET_LINUX`): in Docker Desktop's VM on the same Apple M1 Max, where every run also starts the Landlock launcher, two quiet runs of the gate took 362 and 359 seconds at a load of about 4 to 5 (2026-10-17), and 390 is the slower plus 7%, rounded up to 5 seconds. A platform with no budget pinned is an error of the gate. Each budget is never a limit on what the gate covers: every check and run has a time limit of its own, so a hang ends there, and the budget guards against slowness that adds up over the run. A run over the budget is resolved by measuring again, on a quieter machine, or by raising the budget on a measurement, never by shrinking the run or its sample.

- **Must-reject:** a program built to break a flow rule must be rejected by `una check --tier 0`. An accepted one is a finding.
- **Must-keep:** two refactors that keep every label (a rename, a reordering of declarations) must not turn a rejected program into an accepted one.
- **The two-run oracle:** for an accepted program with a literal labeled above `public`, the literal is replaced by up to five other values of its type, in a fixed order, and every variant runs on the interpreter (`una run --json`) twice, each run in a directory of its own. What an observer below the literal's label sees, at `public` and at `internal`, must be the same in every variant that completes (`spec/07 §1`):
  - `status`, every `output` line, `failure` (its variant and its public fields), and the diagnostics by severity, code and message: `una run --json` redacts what a message renders above `public`, so a message that differs between variants is a leak, the class of S-28 (#874);
  - the `trace` events of the operations whose `accepts` the observer sees, as the model defines what an observer sees, in order. The `accepts` of host operations is the prelude's, pinned by a test; that of the program's own capabilities comes from its Core export. An operation the oracle cannot classify is an error, and an `accepts` it cannot read exactly counts as visible;
  - of each such event, every field but `seq`, which numbers the hidden events too, and `outcome`, which is what the host returned to the program, an input of the run and not something the program sends; the arguments that decide it are compared. Of `Keys.hmac`, only `key_name`, its one sink, is compared.

  Every variant that completes is compared with the program's first end that completed, the base's or a variant's, so an aborted base hides nothing. An argument of a visible event that the run redacted at a level above the observer is a finding by itself, whatever the other variants show: the run says that a value above what the operation accepts reached it. A program whose policy releases to `public` is set aside and counted, since the release explains a difference.
- **The comparison with the model's re-check** (#791): every program that `una check --tier 0` accepts is exported (`una --json core`) and read by the formal model's checker, `una-core-check`. The gate builds the checker with the pinned Lean, its version checked (`scripts/lean-env.sh`, shared with `scripts/formal.sh`), after the `formal` gate, and a Lean panic aborts it. A declaration the re-check rejects is a finding. What it compares is fixed by the run:
  - **Compared:** a program counts as compared only when the re-check accepts at least one of the program's own (`app.*`) functions. At least 1,002 programs (measured: 1,114) and 1,598 accepted declarations (measured: 1,776).
  - **What it does not read:**
    - a document the re-check reads as a whole fallback, every line `not re-checked` for one reason, compares nothing, so the count of such documents is pinned per reason, exactly;
    - so is the count of the program's own declarations it does not re-check, per reason, such as a `via` function, a `handler` declaration or an operation with a condition (ADR 0092), which the model's fragment does not cover.

    A change in either count fails the gate until the pins say so.
  - **`unknown`:** an outcome the comparison cannot judge. The expected ones are pinned by name with their reason (`PINNED_UNKNOWN`): today seven programs that use the primitive `fixed`, four in edition `0.2` and the edition `0.3` twins of three of them, in the sample, outside the fragment by design. Any other `unknown`, and a pinned one that is no longer unknown or is unknown for another reason, fails the gate.
  - **Residual programs:** these are programs where a secret may abort a step, which the full check's obligations guard. They are compared with the pinned solver, and their count is pinned (63: 13 of F8 and 50 of Q2). Their full check stops a solver query at 30 seconds (`--solver-wallclock 30`), half its limit of 60: a query the solver does not decide is U5002, which makes the row invalid, a gate error, and so does a check that reaches its limit.
    - A residual row whose own comparison is not clean is an error, and so is one the full check does not decide, or decides by another code.
    - One the full check accepts with a public print after the step is a finding.
  - **Tier-0 verdicts:** each program's verdict must agree with the must-reject driver's.
  - **Scope:**
    - the comparison reads only what `una check` accepts, at tier 0;
    - it does not export rejected declarations (no `--with-rejected` step);
    - the reverse comparison, a declaration the checker rejects and the model accepts (#514), stays out of the gate.

  It found S-27 (#799) on its first run, and adds about 45 seconds.
- **The native sample** (#792, `scripts/security-hunt/hunt/native.py`). A sample of the oracle's programs also runs as native executables. The sample is stratified, and fixed by the run's names: the programs whose name's SHA-256 starts with a byte below 20, about 8% of the oracle's programs and 5% or more of those it compares, and, for every family with a compared program, the one whose name has the lowest SHA-256, so that no family the oracle compares is left out of the sample by chance; the families it compares are pinned, and a family that drops out fails the gate. In it, every variant the interpreter ran is built with `una build` and run with the same limits, and the two engines must agree on everything the run shows (`spec/16 §5`), as the native equivalence test compares them (`crates/una-cli/tests/native.rs`):
  - the exit code and the standard output line for line;
  - the standard error: empty on a run that ends `ok`; otherwise its first line is the error, `[<code>] Error: <message>`, equal to the run document's, and every other line a place, `  at <file>:<line>:<column>`, or the note that names the explanation of its code;
  - the trace, every event and field, the result of each `Clock.now` aside; a redacted argument is compared as written, its label included;
  - a run that starts tasks by the rule of `spec/19 §8` rule 4: the output a merge of each task's lines in its own order, each line quoted as the trace writes it (`una_core::quote`); on an ordered run, one that neither fails nor cancels a task, the trace equal to the interpreter's and the output, as a multiset, the document's; on a run that is not ordered, the trace the interpreter's in order with the extra events those of tasks that started after a failed one, and the output the document's plus only the lines those events printed. A line whose printed form the trace redacts is not matched against the trace, and which task prints first is outside the model (`spec/19 §6` rule 7), so only each task's own order is compared;
  - a run the interpreter ends with U6003, U6004 or U6005 by the rule of `a_copy_between_tasks_over_the_budget_is_u6003_in_both_backends`: where each engine runs out is not exact (ADR 0061), so the executable must end with the same exit code, error and standard output, and one engine's trace, its `seq` aside, must be a prefix of the other's, so that an effect one engine makes before its abort and the other never makes is a divergence; the place of the abort is not compared. A variant whose interpreter run reached the time limit is not compared, and the result says so.

  A difference is a backend divergence, a finding. A sampled program whose policy releases to `public`, which the oracle sets aside, still runs natively, every variant, since a declassification is where redaction could differ between the engines. A sampled program that is not compared must say why: the checks reject it, so nothing runs, or it is pinned as not compiled; any other is an error, and so is an error of a sampled program's native comparison. A variant whose interpreter run reached the time limit, its full check deciding, would be listed as not compared, but any such kill fails the gate (`MAX_TIMEOUTS_DECIDED`, below), so a passing gate has none. A sampled program the native backend does not compile must be pinned by name, with its reason, in `scripts/security-hunt/native-unsupported.txt`; any other build failure is an error, and so is a pinned program that compiles. Measured on the fixed run: 45 programs sampled, 5 of them in the edition 0.3 sample, all seven families with oracle programs present (B, C, H, K, P, Q and T, pinned), C with task runs compared by the rule above; 40 compared natively, those whose policy releases to `public` among them, with 184 variants (floors: 36 programs and 165 variants); and 5 not compared because the checks reject them, each listed with its reason (two closed calls of B2 and three programs of T12); no program left uncompiled and no divergence.
- **Tasks** (#807). Family C's operator C6 gives the oracle programs that `together` could let a secret decide: a `together for` over a public list of secret elements, a secret computed in one branch beside a public one, secrets sent by tasks to an operation that accepts `secret`, a block under a public condition, and a fan-out whose number of tasks the secret decides, its tasks calling only such an operation; each prints public output that must not move with the secret. Three more forms are closed calls that a correct checker rejects, so the oracle sets them aside: a list whose length the secret decides, its result's length printed to the console, which accepts only `public` (U4003); a fan-out whose number of tasks the secret decides, each calling an operation `public` sees (U4003); and a task failing on its secret element, the failure passed to `main` (U4002). Each closed call carries its code: the must-reject driver reports one the checks accept as a finding, and one rejected by another code, there or in the oracle's run, is an error, since it tests nothing of its rule. A checker that wrongly accepted one would let the oracle see the secret, a finding. A seventh form, a failure the secret decides kept in its task by `attempt`, is rejected by the checks (U4002, a `fail` under a secret condition), so it is a must-reject probe. In edition `0.1`, `together` is reserved, and each program is a must-reject probe of that (U0103).
- **Edition 0.3** (#813). Two families run in edition `0.3`, each with its edition `0.2` programs as the edition gate's probes, which must be rejected: an unknown table `[boundaries]` or `[contracts]` (U7002), or `where` in a `uses` or a narrowed rebinding, which do not parse (U0101). One probe holds a `[contracts]` lock and no `where` anywhere, so only U7002 can satisfy it.
  - Family B, authority boundaries (ADR 0093): B1's must-reject programs break a boundary's rules: a capability taken by name, as a function value or by a handler install (U3020), a grant beyond the ceiling, by a binding, a functional argument or a handler (U3021), and a release reachable from the boundary (U3024). B2 gives the oracle calls into a boundary granted within its ceiling while the caller holds a secret; its closed call grants a public operation into the boundary from a function called under a secret branch (U4002), which the oracle sets aside.
  - Family Q, conditions on operations and contract locks (ADR 0092): Q1's must-reject programs are what tier 0 rejects of a condition (U0101, U2012, U2013, U2014, U2016, U3006, U3023 and, in a `[boundaries]` ceiling, U7002). In the ceiling probe everything but the ceiling's `where` resolves, its capability public and imported by the boundary, so its U7002, a code with many sources, can come only from the condition (a canary checks it). Q2's programs are what only the full check decides: tier 0 accepts them, and the full check must reject each refuted one with its expected code and no other, U5002 included (U5001, or U3023 for a header whose condition does not imply its lock's), and must prove each of its twins: a refuted program the full check accepts is a finding, and one it rejects with another code, or a twin it rejects at all, is an error. So a full check that rejected every conditioned use fails the gate. Q3 gives the oracle a conditioned public operation whose condition is on a public parameter beside a secret sent to an operation that accepts it; its closed call conditions the public operation on the secret (U4003), which the oracle sets aside.
  - The oracle's and the native backend's runs check with the pinned Z3 (`verification.lock`), since `una run` and `una build` do the full check. A program whose check there ends with an obligation the solver did not decide (U5002, a `unknown: wallclock` among them) or without the solver (U5003) is a gate error, never a program set aside as rejected by the checks. Each of those runs and builds stops a solver query after 10 seconds (`--solver-wallclock 10`), half the run's time limit of 20 seconds, so an undecided query ends as U5002 before the limit kills the run. A run killed at its limit anyway, its check slower in total, has its full check run on its own, at the check's limit of 60 seconds: the kill counts as an abort only when that check accepts the program with every obligation decided, and is a gate error otherwise.
- **Termination is recorded, not judged.** A pair of variants where one completes (`ok` or `failed`) and the other aborts with U6003, U6004 or U6005 is outside the noninterference guarantee (`spec/07 §1`, ADR 0061). The gate prints such pairs, `summary.json` lists them, and the record carries their count. It also counts the runs killed at their time limit whose full check, run on its own, decided (`timeouts_decided`): each is a comparison the oracle does not make, so the gate fails when there is one (`MAX_TIMEOUTS_DECIDED`, 0; the measured run had none), and one whose full check does not decide is an error. So a pair where one variant reaches the run's time limit, also outside the guarantee, fails the gate either way, and only the pairs of U6003, U6004 and U6005 are recorded. Two variants that complete with different statuses are compared as public output.
- **It fails closed.** The gate fails:
  - on any finding;
  - on a generator's error: a lexical or syntax code (U0xxx) on a generated program, or on either side of a must-keep pair, that does not expect it; a must-reject program with no expected code; or a must-reject program rejected without one of its expected codes (by code, not place). So a program that does not parse never counts as a rejection, a kept pair or a program set aside;
  - on any check or run that ends in another way: a timeout of `una check`, an internal error, unreadable output, a signal, a completed run with a diagnostic other than its failure's errors, a variant the checks reject, or an oracle run or native build whose check the solver did not decide (U5002, U5003);
  - on two runs of one variant whose documents differ in any byte, exit code or timeout;
  - when a driver judged a number of cases other than the pinned one, or none, or the oracle's comparisons are under their floors, the global ones or a family's;
  - when the oracle sets aside, as rejected by the checks, a program without one of its expected codes, or a number of programs of a family other than the pinned one;
  - when the edition 0.3 sample has no seed for a form of the fixed run (`sample_forms`);
  - when any run is killed at its time limit, its full check deciding (`MAX_TIMEOUTS_DECIDED`, 0), since each such kill is a comparison the oracle or the native comparison does not make;
  - when the whole gate takes more than its platform's budget, 270 seconds on macOS and 390 on Linux (`TIME_BUDGETS`), or no budget is pinned for its platform, a guard against slowness that adds up over the run, never a limit on what it covers;
  - when its output directory is not empty.
- **Its size.**
  - **Pinned counts:** 6,288 programs judged by must-reject, 10,851 (program, refactor) pairs by must-keep (the reorder refactor applies only to a module with two declarations or more, so the 8 programs of Q1's ceiling probe, whose modules hold one each, have the rename alone), 637 programs with a varied literal by the oracle, and 6,288 programs by the re-check comparison (`PINNED` in `scripts/security-hunt/hunt/gate.py`, checked against the generators by a unit test).
  - **Floors on the oracle**, about 90% of the measured run, against a run that compares little: only comparisons of two complete variants count. At least 432 programs with such a comparison (measured: 481), 1,700 such comparisons (measured: 1,889), and 105 live programs (measured: 117). Families B, C and Q, whose programs are few beside the others', have floors of their own, so that most of their comparisons cannot be lost above the global ones (`MIN_FAMILY_COMPARED`): B at least 32 programs and 162 comparisons (measured: 36 and 180), C 35 and 175 (39 and 195), Q 34 and 171 (38 and 190). The forms of each operator that the oracle compares, and those it finds live, are pinned exactly (`ORACLE_FORMS`, `LIVE_FORMS`), so losing a whole form, or every live program of one, fails above the floors; and so is the count, per family, of programs it sets aside because the checks reject them, each with one of its expected codes (75: B 14, C 20, Q 12, T 29): the closed calls of B2, C6 and Q3, and the must-reject programs of T12 that have a varied literal. A program is live when two of its complete variants differ at the literal's own level, where every event is visible with its outcome: its literal decides something, so its comparisons are not vacuous. The run document redacts every value above `public`, so liveness sees only what a literal decides in the control flow, such as whether an operation runs: of the measured run's programs, those of H3 and C6's secret-sized fan-out (the number of its tasks' events) are live, and those of B2, K4, P1, Q3, T8 and C6's other forms, whose secret reaches only redacted values, are not counted live although they may be compared well; an unredacted runner (#794) is to make them live. 156 programs were set aside: 81 whose policy releases to `public` and 75 the checks reject.
- **Canaries.** Planted faults run through the same code, and a canary that is not caught fails the gate:
  - a program the checks accept, labeled must-reject, which the must-reject driver must report;
  - a program that prints a public literal its manifest marks as secret, whose variants the oracle must tell apart at `public`; and another whose literal, public in the code and marked secret, decides how many tasks of a `together for` call an operation `public` sees, while its output is constant, so the oracle must see the leak in the tasks' trace alone;
  - an open program that does not parse, which must be a generator's error by its code alone;
  - in edition `0.3`: a must-reject program expecting U3021, a call into a boundary granted within its ceiling, which the checks accept and the driver must report; Q1's ceiling probe with a plain ceiling, `Log[write]`, which the checks must accept, so that the probe's U7002 can come only from its `where`; and a program whose literal, marked secret, decides by the branch around it whether a conditioned public operation runs, while its output is constant: the oracle must see the leak in the trace alone, and its runs must have the solver, without which the operation's obligation would make the canary an error (U5003). The leak is the branch's, not the condition's;
  - a program that calls an operation accepting `secret` under a secret branch, which the gate plants as accepting `internal`: the oracle must report it at `internal` only;
  - a program that sends a secret to an operation accepting `secret`, which the gate plants as accepting `public`: every variant shows the same redacted argument, and the oracle must report the redacted sink by itself;
  - two Core documents the re-check must reject, v0.3.14's exports of S-27's two cases (`docs/reviews/formal-m2-replay/core-s27`): each, read as a program's export, must be a finding whose one rejected declaration is `app.main.main`, for its reason; and the fix's export of the first, a control, must read clean with `app.main.main` accepted;
  - a program of the native sample whose executables are all built from its base, so that every variant's native run prints the base's value: the native comparison must report a divergence on the variants and none on the base;
  - the sandbox's own canary (#793), on macOS and on Linux: a run writes in its own directory, and each of these attempts must give exactly its backend's refusal (`SANDBOX_EXPECTED`): a write in a sibling run's directory, in `/tmp` and to the gate's proof-cache key, a connection to a loopback port that a listener outside the sandbox holds open and a bind (`EACCES` from Landlock, `EPERM` from `sandbox-exec`); a signal to the gate (`EPERM` on both); and on Linux also a read of the sibling's file (`EACCES`) and a connection to its abstract Unix socket (`EPERM`). A second run, given that port as its mock's, must connect to it, and nothing denied may exist afterwards;
  - a program whose `main` fails with a public code and a secret value, of which `una run --json` shows only the code, in its failure and its message; planted so that each variant's message also shows its own literal, the oracle must report a leak at `public` from the message alone (#874);
  - three pairs of a program and a changed copy, each run on the interpreter and natively, where the program against itself must agree and against its copy must be a divergence: one whose copy differs in the argument of an event only, one whose `together` tasks print lines with braces and quotes and whose copy prints another line in one task, one whose copy's tasks print their line twice on an ordered run, and one that recurses past `--max-depth` (U6004) and whose copy prints another line before it. The task program is written by hand, so that its lines hold the escapes the comparison must get right.
- **Evidence:** `OUT/hunt/summary.json` (the verdict, the seed, the case counts, the `una` tip, the findings, errors, termination pairs and canaries) and one result file per driver. The record's `## Hunt` section summarizes it.
- **Scope.** On macOS every compiler run is under `sandbox-exec`, with one writable directory, no network and a clean environment; on Linux the gate runs as `hunt-linux-arm64` (below). There is no unsandboxed fallback on either. The oracle varies source literals only, runs the interpreter, and natively its sample, and observes at `public` and at `internal`; host inputs and the files a program writes are not part of the gate yet (#782).

**The Linux sandbox** (#793). `scripts/hunt-linux.sh --linux-arm64 OUT TIP` runs the same gate, with the same pins, on Linux. It builds the release `una` and the re-check's executable in the image and volumes of `scripts/local-ci.sh`, then starts the gate in a second container, which is the sandbox of the gate as a whole:

- no network (`--network none`: loopback only), a read-only root with a `tmpfs` for `/tmp`, the checkout, the target directory, Z3 and Lean mounted read-only, and `OUT` the only writable mount;
- the caller's user, never root, no capability (`--cap-drop ALL`), `--security-opt no-new-privileges`, an init process that reaps orphans (`--init`), at most 1,024 processes and 6 GiB of memory, 30 minutes in all, and a clean environment (`env -i`) with the marker `UNA_HUNT_SANDBOX=container`.

Every run of the gate, on either platform, has a directory of its own, made for it (`sandbox.fresh_dir`), and it is the only one it may write: the packages it checks are read from their own directory, and a document it reads is copied into its directory first. No cache crosses runs: a package is read-only to the runs that check it, so `una` keeps no proof cache there, and a run's proof cache, if any, stays in its own directory. Every run reads one proof-cache key, made by the gate once, outside every run's directory, which no run can write (the sandbox canary checks it): the key protects the integrity of a proof cache's entries, and with no cache shared between runs, a key every run can read gives none of them a way to reach another, where a key made in each run's fresh `HOME` cost about 6 ms a run (measured 2026-10-17). A run starts only while the key is the file the gate made, unchanged, and the gate reads it again at its end: a key that went missing or changed fails the gate, so `una` never falls back to a key of its own. A run starts a process group of its own with no input, and the group is killed when the run ends or reaches its time limit; a process that leaves the group (`setsid`) is not killed with it, and if it still holds the run's output open five seconds after the group is killed, the gate fails. On Linux, Landlock confines each run, the compiler, the executables it builds and the re-check (`scripts/security-hunt/hunt/landlock.py`), as `sandbox-exec` does on macOS. The process restricts itself, after `PR_SET_NO_NEW_PRIVS`, and then executes the run, which can never lift the restriction:

- every file right of the kernel's Landlock ABI is handled: the run may write, create, remove, rename and link only under its own directory, which is opened without following a link and must have the device and inode recorded when it was made; it may read and execute only there, in the directories of its tools (`una`, the re-check, Z3 and Lean) and of its `PATH`, in its working directory, in its executable's own directory and in the system's (`/usr`, `/lib`, `/lib64`, `/bin`, `/sbin`, `/etc`, `/proc`), never the root and never the gate's output; among devices it may write only `/dev/null`, and read only it, `/dev/urandom`, `/dev/random` and `/dev/zero`;
- TCP is handled: the run may connect only to the mock server's port and bind no port;
- abstract Unix sockets and signals are scoped to the run's own domain: it cannot signal the gate or another run.

Landlock does not mediate UDP or a connection to a Unix socket that already exists in the file system; in this container no such socket or UDP listener is reachable, and "TCP only to the mock" is not "no other network". On macOS, the profile of `sandbox-exec` denies writes outside the run's directory, the network and signals to processes outside the run's own (`(deny signal (target others))`), and does not confine reads.

The gate refuses to run, before any run starts, unless all of these hold inside its container (`sandbox.container_problems`): the marker, the container runtime's `/.dockerenv`, no capability in any set (effective, permitted, inheritable, ambient and bounding), no-new-privileges set, a user and a group other than root, the root mounted read-only, no network interface up but loopback (the kernel's fallback devices, such as `gre0` or `sit0`, are listed but down) and no route but through it, so no default route, a TCP connection to a public address (IPv4 and IPv6) that fails with `ENETUNREACH`, and Landlock at ABI 6 to 8. Below ABI 6 Landlock cannot scope signals and abstract sockets, and the gate does not run there rather than rely on `--network none` alone; above ABI 8, a later ABI adds rights the gate does not handle yet (the upstream `include/uapi/linux/landlock.h`, read on 2026-10-17, lists a file right of ABI 9 over Unix sockets and rights of ABI 10 over UDP), and it does not run there until they are. A ruleset is never applied in a reduced form ("best effort"): a failed Landlock call stops the run before it executes, and the gate fails. The sandbox canary above checks that the restriction is enforced, not only applied. The container can read its mounts' host paths (`/proc/self/mountinfo`), so `scripts/hunt-linux.sh` fails the gate when its evidence holds the checkout's path or the caller's home. Measured with Docker Desktop's kernel 7.0.14-linuxkit on arm64 (2026-10-17, UTC): Landlock ABI 8.

The pinned Z3 comes from `UNA_GATES_Z3`, else this checkout's `target/z3`, else the clone's `target/z3`. If none is there, the `build` gate installs it with `scripts/install-z3.sh`.

**The dependency audit** (#770). The `deps` gate fails closed on each of these:
- `cargo-deny` is missing or at another version than `supply-chain/tools.lock` pins. Install it with `cargo install --locked cargo-deny@<version>`. The log records its version and the SHA-256 of its binary. That digest is a record, not a pin: `cargo install` builds are not reproducible, so the gate compares only the version.
- The advisory database cannot be fetched, offline included: the gate fails and is never skipped. A fetch can also succeed and leave an old database, from a cached clone or a stalled mirror, so the gate fails when the database's last commit is more than 7 days old by the current UTC time, and prints its age. The commit and date of the database it fetched go into the record and the public summary, so the run can be repeated against the same advisories.
- An advisory of that database applies to a package of `Cargo.lock`, a yanked version or an unmaintained crate included. `deny.toml` ignores none. An ignore needs its own pull request with a reason, an expiry date and a recorded ruling, and a finding is reported before any ignore is written. A fix updates the dependency (S-26, #779).
- A license outside `deny.toml`'s allowlist, a wildcard version requirement on a registry crate, or a package from any source but crates.io. One exception admits NCSA, the permissive license of the libFuzzer that `libfuzzer-sys` 0.4.13 vendors for the fuzz targets, for that crate at that version only, and a test checks that `deny.toml` admits NCSA nowhere else. The workspace's own crates depend on each other by path; `allow-wildcard-paths` admits those, and only because every workspace crate has `publish = false`.
- A package of `Cargo.lock` with no source that is not a member of the workspace, by name and version (`cargo metadata --no-deps`), or a member whose manifest is outside the repository: a path dependency outside the workspace, or a vendored copy, has no source and no checksum, so neither cargo-deny's sources check nor the record would see it.
- A crates.io package of `Cargo.lock` that `supply-chain/crates.tsv` does not list with the same version and checksum, or a line of the record that `Cargo.lock` no longer has. `crates/una-cli/tests/dependencies.rs` checks this offline, so `scripts/local-ci.sh` catches a new or moved dependency before the gate does. A change to the record is the review: its pull request names each crate added or moved and why, and someone other than its author reviews it. The record started with the 158 crates of `Cargo.lock` when the gate was added, after S-26's update, as the baseline, not as a review of each of them.

**The fuzz targets** (#766). `fuzz/` is a crate outside the workspace, with its own `Cargo.lock`, so the workspace's builds never see it. It depends on `libfuzzer-sys`, which vendors and builds libFuzzer, and no fuzzing tool is installed: `scripts/sanitize.sh` builds it with the checking toolchain and the flags it states (libFuzzer's coverage of edges and comparisons, AddressSanitizer, debug assertions, overflow checks, and `--cfg una_fuzz`, which alone exposes the two hooks of `una-rt` the targets call). What the targets call, outside a run: `literal`, `una_rt_int_literal` and `una_rt_text_literal` on any bytes; `json`, `una_rt_parse_json` and `una_rt_to_json` on any text, against the parser of `una-core`, failures included; `words`, the 87 entry points of the export table but its 10 host effects, and 13 outside it (`una_rt_retain`, `una_rt_release`, `una_rt_push`, `una_rt_enter`, `una_rt_leave`, `una_rt_budget`, `una_rt_poll`, `una_rt_stopped`, `una_rt_operation_begin`, `una_rt_operation_end`, `una_rt_event_arg`, `una_rt_event_end`, `una_rt_together_status`), each call's result joining the words the next calls take. Not called: `una_rt_closure` and `una_rt_push_op` (addresses of compiled code), `una_rt_together` and `una_rt_together_for` (they run such code), `una_rt_start` and `una_rt_main_failed` (a run's start and end), and the host effects. The `sanitize` gate fails closed on each of these:
- A target not instrumented with AddressSanitizer, or with its runtime inactive.
- The canary target, whose crash is planted behind the input `una!`, not reported, or its input not minimized back to `una!`: the self-check that the harness reports a crash.
- A crash, an AddressSanitizer report, a panic, an input that runs over 10 s, or over 4 GiB of memory, in `literal`, `words` or `json`. The gate prints where the input is kept, the input minimized from it and the command that replays it, all under `target/fuzz/<target>/`. Only the seeds of `fuzz/seeds/` are committed, never what the fuzzer adds. A previous run's reproducers are not deleted: the next run moves them aside, under the time it moved them.
- A target that runs fewer inputs than its count. Each runs a fixed number of inputs with a fixed seed, so the size of the run does not depend on the machine; its time limit, 600 s, is a ceiling only, and libFuzzer stopping at it is a failure, read from its final statistics. The counts were measured so that each target takes about a minute: on the release machine (macOS, Apple silicon), 120 s runs with the gate's seed and flags ran `literal` at 5,929 inputs a second, `words` at 6,009 and `json` at 7,568, with the machine's load average between 4 and 11 from other work, so the counts are 350,000, 350,000 and 450,000. The canary's crash was found after 29,154 inputs, below a second.
- A target below its coverage floors: the counters of the instrumented code libFuzzer loads, and the edges (`cov`) and features (`ft`) its run ends with, each floor nine tenths of a measured run's value, so a target that returns early on every input, or a runtime built without libFuzzer's counters, fails. Measured at the gate's sizes on the release machine (load average about 3 from other work): `literal` 271,382 counters, cov 555 and ft 844; `words` 271,998, 4,971 and 18,839; `json` 271,616, 2,360 and 8,183. A runtime without libFuzzer's counters has some hundreds of counters, as the canary alone does.
- A target built by `fuzz/Cargo.toml` that the script does not run, or the reverse.
- A path dependency of `fuzz/Cargo.toml` that is not a workspace crate at its place under `crates/`, by `cargo metadata` (`crates/una-cli/tests/dependencies.rs`): the fuzzed code is the workspace's own.
- A crates.io package of `fuzz/Cargo.lock` that is neither in `supply-chain/crates.tsv` nor in `supply-chain/fuzz-crates.tsv` (the `deps` gate, with cargo-deny run on `fuzz/Cargo.toml` too).

At the end, the script removes the Docker volumes that `--linux` and `--linux-arm64` made for the clone's target directory, so volumes do not pile up.

**The job count in the containers** (#701). By default, Cargo inside a container runs one job per CPU of the Docker VM. On a VM with 8 GB and 10 CPUs, ten rustc and linker processes at once have run it out of memory: the kernel killed the linker with signal 9, the test binaries did not link, and no test ran.

`scripts/local-ci.sh --linux` and `--linux-arm64` therefore pass a job count into the container, which `scripts/container-jobs.sh` computes:
- The build runs one job per 2 GiB of the VM's memory (`docker info`'s `MemTotal`), at most one per CPU and at least one. That is 3 jobs on the VM above.
- A `CARGO_BUILD_JOBS` set on the host can lower that count, never raise it. A higher value, such as one meant for the host's own builds, is capped, and the run says so.
- `RUST_TEST_THREADS`, when set on the host, goes in too.

The run prints the job count before the container starts, and the container's peak memory (`memory.peak` of its cgroup) at the end. The job count changes only the build's peak memory and its time, never what is built or tested.

Why 2 GiB: a measured run of `--linux-arm64`, cold, on that VM (7834 MiB, 10 CPUs) with 5 jobs (one per 1.5 GiB) passed with a peak of 6841 MiB, 87% of the VM. That figure includes page cache, which the kernel reclaims before it kills a process, but the margin is narrow. These runs are evidence: a linker killed for memory costs a full rerun and leaves a failed run in the record, which outweighs the slower build of 3 jobs. A lower `CARGO_BUILD_JOBS` set on the host is passed in as it is, for a one-off run that wants even less memory. The VM's memory is the host's setting, and the script does not change it.

**Reproducible archives** (#679). The binaries were already reproducible: `scripts/release.sh` remaps the build's paths (#382), and the linkers derive the macOS binary's `LC_UUID` and the Linux binary's build ID from its content, so both are equal when the inputs are. Two builds of one commit, from fresh clones at different paths and cold target directories, gave byte-identical binaries on `aarch64-apple-darwin` and, in Docker, on `aarch64-unknown-linux-gnu`. Three things made two archives of one commit differ, and `scripts/release.sh` now fixes each:

- each tar entry had the time the files were copied, so every entry now takes the commit's time, `SOURCE_DATE_EPOCH` when it is set, else `git log -1 --format=%ct`. A build that finds neither stops;
- each entry named the account and group that built it, so every entry is now owned by `0:0` with no user or group name, which `scripts/check-release.sh` checks;
- the gzip header had the packing time, so `gzip -n` now stores none.

The entries are also packed in byte order of their paths, with modes 755 for directories and `una` and 644 for the other files, so the order of a directory listing and the umask do not matter. On macOS, extended attributes, ACLs and resource forks are left out. The containers of the Linux builds cannot read the commit's time when the checkout is a worktree, so `scripts/local-release.sh` and `scripts/local-ci.sh` pass `SOURCE_DATE_EPOCH` in. The `reproducible` gate costs a second `release` gate, so a full run of the gates takes about that much longer.

## 3. The record

The script writes into `OUT`:

- `results.tsv`: a header line, then one line per gate run, tab-separated: `gate`, `sha`, `result` (`PASS` or `FAIL`), `seconds`, `log_sha256`.
- `logs/<gate>.log`: each gate's full output. Its SHA-256 is in `results.tsv` and in the record.
- `record.md`, the full validation record:
  - the commit, its subject, the run's date, platform, `rustc` and Docker, and the SHA of the script that ran;
  - a table of the gates, with result, seconds and log digest;
  - the archives that the `release` gate packed, with their SHA-256;
  - the dependency audit: the `cargo-deny` version and the advisory database's commit and date that the `deps` gate used;
  - the verdict:
    - `PASS (every gate)`;
    - `FAIL (<gates>)`;
    - `INCOMPLETE (not run: <gates>)`.
- `summary.md`, the public summary, which `scripts/release-summary.py` writes from `record.md` by a fixed template (#717):
  - the commit, the run's date, operating system and architecture, and the `rustc` and Docker versions;
  - the table of the gates, with result and seconds;
  - the archives with their SHA-256;
  - the dependency audit's tool and advisory database, as in the record;
  - the verdict, as in the record.

  Nothing else of the record is copied: no subject, no notes, no log digest. Each field is checked against its shape before it is written, and a field out of shape stops the summary, so no free text reaches it. The summary must not match the privacy pattern: `UNA_PRIVACY_PATTERN` when it is set, else the macOS Keychain item `una-privacy-pattern`, which `scripts/release-gates.sh` reads into a shell variable that it never exports, unsetting the caller's variable, so that no gate inherits it, and hands only to the summary step; it never prints, logs or writes it. Without either, the script stops before any gate; `UNA_GATES_UNCHECKED=1` runs the gates without the pattern: such a run's summary opens with "Unchecked: written without the privacy pattern; not for publication", and no publish command is printed.
- `release-notes.md`: the summary, then the version's `CHANGELOG.md` section that `scripts/local-release.sh` wrote.

For a tag, `summary.md` is committed as `docs/validation/<version>.md`, unchanged. The full record and the logs stay private. `docs/validation/repacked.md` lists the macOS archives of v0.3.3 to v0.3.13, which were packed again after their release, each with its gated and its published digest and the check that paired them, and the withdrawn macOS archives of v0.3.0 to v0.3.2.

## 4. The procedure for a release

1. Merge the release pull request under rule 1, and note the SHA of `main`. The release pull request sets the version, regenerates `fuzz/Cargo.lock`, which pins the workspace's crates at that version (`cargo +<checking toolchain> metadata --manifest-path fuzz/Cargo.toml`, #766; the supply-chain test fails until it does), runs `scripts/changelog-assemble.sh`, which writes every fragment of `changelog.d/` under `## Unreleased` in a fixed order (the issue number, then the file name) and removes the fragments (#744), and renames `## Unreleased` to `## v<version>` with the release's introduction, leaving an empty `## Unreleased` above it.
2. Run `scripts/release-gates.sh <sha> <out>` on that SHA, with Docker running and nothing else using it.
3. If the verdict is PASS and the summary was written with `UNA_PRIVACY_PATTERN` set, commit `<out>/summary.md` as `docs/validation/<version>.md` (and, until the repository is public, `<out>/record.md` as `docs/releases/<version>-validation.md`) in a pull request that changes nothing else, under rule 1.
4. Check rule 2 on the merged record commit: its own change is the summary, and `git diff --name-only <gated> <record commit>` lists only files under `docs/`. Once the release is approved, tag `v<version>` on the record commit and push the tag.
5. Publish the archives from `<out>/clone/target/local-release/v<version>/`, checking that their digests match the summary's, with the `gh release create` command that `scripts/release-gates.sh` prints at its end (`scripts/release-publish.sh`). A pre-release, a version with a suffix such as `0.4.0-alpha.1`, is published with `--prerelease --latest=false`. The summary is the release's notes, followed by the `CHANGELOG.md` section, and is attached as `una-<version>-validation.md`. No command is printed for an unchecked summary, and an unchecked summary is not published.

Once tagged, a release's `## v<version>` section of `CHANGELOG.md` is frozen: its release notes were published from the tag, and `scripts/check-released-sections.sh` fails when the section on a branch differs from the tag's (#645). A correction to a released version, a security advisory included, goes in a changelog fragment whose bullet starts `- **Errata for v<version>: …**`, and ships with the next release's notes. Changing a released section needs a decision recorded as an ADR, which also changes the check.
