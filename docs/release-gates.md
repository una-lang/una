# Release gates

Status: Normative for the project's workflow (#232). GitHub Actions is not used. Merges, tags and releases rest on local runs whose results are recorded, so anyone can see what was checked, on which commit, and with which outcome.

## 1. The rules

1. **A merge into `main`** needs a `scripts/local-ci.sh` PASS on macOS on the pull request's exact tip, written into the pull request body with the SHA.
   - Linux is not checked per pull request. The next gate run confirms it on `main` (`scripts/local-ci.sh --linux-arm64`, in Docker), and a Linux FAIL there is reported at once and fixed before anything else merges.
   - Except when the pull request changes what the Linux run runs: `scripts/local-ci.sh`, `scripts/local-ci/` (its Docker image), or a script that a step of it calls, such as `scripts/formal.sh` or `docs/reviews/formal-m2-replay/check.sh`, or makes a step need a tool it did not need before. Such a pull request also needs a `scripts/local-ci.sh --linux-arm64` PASS (native, a few minutes) on its exact tip, written into its body with the SHA (#605). A step that needs a tool the image lacks passes on macOS, which has it, and fails only in the container: #528's replay needed `python3`, and the first gate run of v0.3.8 failed on it (#606).
2. **A tag** `v<version>` needs a run of `scripts/release-gates.sh` in which every required gate (§2, "The shipped targets") is PASS, on the gated SHA: the commit of `main` after the release pull request.
   - Since 2026-11-11 (#1903, #1939) the required gates are those of the gate machine and of each shipped target, and the emulated `linux` gate is required only when `x86_64-unknown-linux-gnu` ships; see the dated note "The `linux` gate leaves the required set" in §2, which reads ADR 0124 rule 31's "each target" as each shipped target.
   - Its public summary (§3) is committed as `docs/validation/<version>.md` before the tag is made.
   - **The tagged commit is the record commit**, not the gated SHA, since `install.sh` reads the summary from the tag's tree, and gating the record commit again would be circular. So:
     - The tagged commit's own change, against its first parent, is exactly the summary file and, until the repository is public, the full record as `docs/releases/<version>-validation.md`.
     - Between the gated SHA and the tagged commit, only files under `docs/` change: `git diff --name-only <gated> <tag>` lists nothing else. The code, build files, scripts and `install.sh` of the tag are then those of the gated SHA.
     - Anything else that merges in between, such as a change of code, needs a new gate run, and the gated SHA becomes that commit.
   - A tag whose summary has a FAIL or is INCOMPLETE is not made.
   - The run may be the nightly one. The complete gate set runs every night on the head of `main` (the maintainers' scheduler starts `scripts/release-gates.sh` on that commit, from a fresh clone, as any run), so a release starts no run of hours during the day: when the night's run of the gated SHA has every gate PASS, it is the run this rule asks for, with the same record and summary. A night that did not run, or ran another commit, counts for nothing; the gated SHA is then run on its own.
   - Every tag and release also needs an explicit approval, recorded in the release issue before the tag.
3. **A release** publishes the archives that the `release` gate built (`OUT/clone/target/local-release/v<version>/`), whose digests the summary lists. The archives are reproducible (#679): two builds of one commit give the same bytes for each target, which the `reproducible` gate checks with a second build from cold. A published archive can therefore be rebuilt from its commit and checked against the summary's digest. The summary and the published `.sha256` files MUST agree.
4. **`.github/workflows` is not a gate.** The files stay in the repository, but no merge, tag or release waits for them or reads their results.
5. **Version numbers** (ADR 0139). Release R0.N is tagged `v0.N.0`, and its patches `v0.N.x`. When R0.N closes edition `0.N`, its release pull request carries the stabilizing record of ADR 0121 rule 15 (as its amendment of 2026-11-06 extends it), and the gates that rule names pass before the tag. A toolchain release (R0.7, R0.9) closes no edition.

## 2. The gates

`scripts/release-gates.sh SHA OUT [GATE...]` runs the gates on exactly one commit, given as a full 40-digit SHA. It runs the required gates (below) when none is named. Its exit status follows the record's verdict (§3): 0 for `PASS (every gate)`, 1 for `FAIL`, 3 for `INCOMPLETE`, such as a run of some gates; 2 for a run refused before any gate, and 129 or 143 after a `HUP` or `TERM`.


- It makes a fresh clone of the commit for the run, `OUT/clone`, from the remote `origin` (or `UNA_GATES_SOURCE`).
- Before every gate, it checks that the clone is still that commit, with no change and no untracked file.
- A failing gate does not stop the next one.
- The gates may be run in groups, each a run of its own on the same `OUT`, after a first run with `clone` (#1017), one at a time: a run holds `OUT/release-gates.lock` (a directory made atomically, holding the run's pid) from its start to its exit, and a second run on that `OUT` while it is held stops with exit code 2 before any gate. A lock whose run is gone (its pid no longer exists) is taken over. Known limits: the lock follows the pid of the run alone, so after `kill -9` of that pid a gate that was already running keeps running and the next run, which takes the lock over, undoes a tag that gate may still be using (a false FAIL, never a false PASS): stop a run through its process group, never with `kill -9` on its pid. A `TERM` or `HUP` sent to the run lets the gate in progress end first and then exits with 143 or 129 before the next gate; a hung gate is stopped by signalling its process group. `OUT` is named by its physical path, every link resolved, so `/tmp/x` and `/private/tmp/x`, or a gates directory reached through a link, are one `OUT`. Their order still matters where a gate uses another's output: `reproducible` and `toolchain-free` need the archives of `release`, `hunt` runs after `formal`, and `timing-channels` wants no Docker gate running beside it. What no group order can change is which tags the clone holds, below.

**The schedule** (#2181). The gates run one at a time, in the order of the list, except one: by default (`UNA_GATES_PARALLEL=1`, or the variable unset) `sanitize` runs beside `build` and `deps`. `UNA_GATES_PARALLEL=0` runs every gate in sequence in the one clone, as every run did before #2181; any other value stops the run with exit code 2 before any gate. No gate is removed, relaxed or skipped, and each runs the same command on the same commit:

- A gate runs beside others only when its result does not depend on the machine's load and it can have a clone and a target directory of its own. `sanitize` qualifies: Miri, a fixed count of fuzz inputs from fixed seeds, and the native equivalence test under AddressSanitizer, one test at a time with no clock in its verdict; it reads no tag. It runs in `OUT/clone-sanitize`, a local clone of `OUT/clone` (the same objects and tags) checked out at the SHA and checked to be exact before the gate, as `OUT/clone` is, so its `target/` is its own and no build of `build` or `deps` in `OUT/clone` can replace what it runs, nor it theirs. What making that clone printed is `OUT/logs/clone-sanitize.log`; the gate's log is `OUT/logs/sanitize.log`, as before. The Z3 library's cache is filled once before the two start, so they never both build it. When `sanitize` passes its clone is deleted; when it fails, all but its `target/debug` is kept (the fuzzer's inputs and the logs under `target/sanitize`).
- It starts at the first of `build` or `deps` (or at its own place, if it is named first), and every other gate waits for it to end: none of them runs beside anything. `mac` and `linux-arm64` run the timing oracles and the cryptography's timing tests (the step "Timing channels" of `scripts/local-ci.sh`, below), which need a quiet machine as `timing-channels` does; `hunt` and `hunt-linux-arm64` judge each compiler run against a timeout; `limits` and its Linux legs measure memory, CPU and wall-clock limits; `owner-replay` runs under a watchdog; `solver-identity` compares the solver's answers, which a time limit could change; `release` and `reproducible` make the clone's release tag, which `build`, `mac` and the Linux legs read; and the Docker gates of one architecture share its target volume. When neither `build` nor `deps` is named, `sanitize` runs in its place, in `OUT/clone`.
- `results.tsv` lists the gates in the order they were named, whatever the order they end in: each row is written to `OUT/rows/` as its gate ends and copied in order, and `OUT/rows/` is deleted at the end of the run. The record, the summary and the verdict are written once every gate, `sanitize` included, has ended; a `FAIL` of `sanitize` fails the run as before, and a `sanitize` that ended with no row (killed) is a `FAIL`. A `TERM` or `HUP` lets `sanitize` end too, as the gate in progress, and keeps every row written, in order.
- Time and disk, from the green nightly run of 2026-11-21 (19 647 s of gates): `build` and `deps` took 2 397 s and `sanitize` 3 802 s, so the plan saves up to about 40 minutes, less what the two lose to each other and what `sanitize` spends building its own target from cold (it reused `OUT/clone/target` before). That run's `OUT/clone/target` reached 22 GB, of which `sanitize` wrote about 3.7 GB (`target/sanitize`, `target/fuzz`, `target/miri`). The estimate for `OUT/clone-sanitize/target` is 11 to 13 GB (those 3.7 GB and a debug build of `una-cli` and its tests). While the two run, `OUT/clone` holds what `build` wrote (about 16 GB) and no Docker gate has run yet: about 29 GB at that point, against a peak of the whole run of about 42 GB (the free space fell from 156 GB to 114 GB). Once `sanitize` passes its clone is deleted, and `OUT/clone` no longer holds its 3.7 GB, so the later peak falls by as much. The plan does not raise the run's peak.
- A larger plan, which #2181 aims at (`mac`, `linux-arm64` and `hunt-linux-arm64` beside `sanitize`), needs the timing steps of `mac` and `linux-arm64` moved into gates that run alone, and `sanitize` and the hunt given target directories of their own; that changes what those gates run, so it needs its own decision.

**The installer's default version** (#2101). The public install command reads `install.sh` from `main`. The release pull request merges before its tag exists, so it leaves `DEFAULT_VERSION` of `install.sh` and the install lines of `README.md` at the last published release; a pull request right after the publication moves them to the new version. A test holds `DEFAULT_VERSION` to one of the two: the workspace version, or the release before it in `CHANGELOG.md`.

**The shipped targets** (#1903). `scripts/release-targets.txt` is the one list of the targets a release ships, one target triple per line, read through `scripts/release-targets.sh`, which fails closed: a list that cannot be read, lists no target, has a line that is not a bare triple, lists a target twice, or lists one that no release script builds stops every reader. `scripts/local-release.sh` builds the archive of each listed target and of no other, fails unless the tag's commit lists the same targets as the checkout it runs from, and fails unless its output holds exactly one archive per listed target; `scripts/release.sh` and `scripts/check-release.sh` refuse any other target; the `reproducible` and `toolchain-free` gates take each listed target's archive and fail on an archive of another target, the record's verdict is FAIL (naming `archives`) when the archives it lists are not exactly one per listed target (§3), and the tests of `supply-chain/z3.lock` (a `[library]` digest for each listed target and for no other) and of `install.sh` (it offers no target that is not listed) read it. `scripts/site-bundle.sh` writes the list into the docs bundle's manifest as `targets`, an array of triples; the key is additive, so the schema stays `una.site-bundle/1`, as for `feature_catalog`, and a consumer treats a bundle without it (an older release's) as not saying which targets ship. The required gates are those of the gate machine, an arm64 Mac (`clone`, `build`, `deps`, `mac`, `release`, `reproducible`, `determinism`, `native`, `timing-channels`, `owner-replay`, `sanitize`, `docs`, `formal`, `hunt`, `solver-identity`, `limits`, `toolchain-free`), and those of each listed target: `linux-arm64`, `hunt-linux-arm64` and `limits-linux-arm64` for `aarch64-unknown-linux-gnu`; `linux` and `limits-linux` for `x86_64-unknown-linux-gnu`. The record's verdict is INCOMPLETE while a required gate has not run. For 0.4.0 the list is `aarch64-apple-darwin` and `aarch64-unknown-linux-gnu`: no `x86_64-unknown-linux-gnu` archive is built, since that target needs a native x86-64 Linux host for the evidence of ADR 0124 rule 31 (#1442).

**The `linux` gate leaves the required set (2026-11-11, #1903).** 0.4.0 ships no `x86_64-unknown-linux-gnu` archive, so the emulated `linux` gate is not required: under Rosetta no seccomp filter installs (ADR 0124 probe P1, #1442), so that leg cannot run any test that starts the solver child, nor `scripts/check-release.sh`, and ADR 0124 rule 31 requires `limits` and the confinement cases natively on each target. Linux is checked natively instead by `linux-arm64`, `hunt-linux-arm64`, `limits-linux-arm64` and the Linux leg of `toolchain-free`, on the one Linux target shipped. The `linux` gate stays in the script and can still be run by name. Shipping x86_64 again is one line in `scripts/release-targets.txt`, which makes `linux` and `limits-linux` required; it also needs that target's `[library]` digest in `supply-chain/z3.lock`, built on a native x86-64 Linux host, and a native run of `limits-linux`, which refuses to run under emulation, so until such a host runs the gates (with its record in the evidence) the verdict cannot be PASS. On a host whose Docker engine is x86-64, `scripts/local-ci.sh --linux` runs the `linux/amd64` container natively, with no emulation marker (#1939, the `linux` row below), so `linux` and `limits-linux` can pass there; that mode is tested with a stand-in `docker` only, and has not run on a native x86-64 host yet.

This reads ADR 0124 rule 31, which opens with "Every existing gate keeps running" and requires `limits` and the confinement cases "natively on each target", as each target a release ships: the `linux` gate keeps running, by name, and is required again with its target. The rule itself is unchanged (no amendment). The sign-off is the project's recorded decision of 2026-11-10: Linux is part of the 0.4 release, and the gates may change as it needs, failing closed, with none weakened. Every gate that was required before stays required for each shipped target; the coverage that `linux` alone gave is that of the `x86_64-unknown-linux-gnu` artifact, which 0.4.0 does not ship.

**The clone's release tag (#1017).** `scripts/local-release.sh` needs the tag `v<version>` on the gated commit, so the `release` and `reproducible` gates make it in `OUT/clone`, and the gates that read tags, the released sections of `CHANGELOG.md` and the security advisories' releases of `mac`, `linux` and `linux-arm64`, would see that version as released if it stayed. In the order of a full run those gates come first; in a run split into groups, `linux-arm64` after `release` failed its "Security advisories' releases" step. So `scripts/release-gates-tag.sh` guarantees:

- The tag lives only while its gate runs. When the gate ends, whether it passes, fails or is stopped by a signal (`INT`, `TERM`, `HUP`), a tag the clone did not have is deleted, and a tag it had from its source (a past release's commit gated again) is put back on the object it named, an annotated tag as itself. The tag is listed in the clone's `.git` before it is made, so a run killed with no chance to undo it (`SIGKILL`, a crash) is undone at the start of the next run on that `OUT`, before any gate; a run that cannot undo it stops with exit code 2, unless its first gate is `clone`, which makes the clone again.
- It touches the gates' own clone only. Every step refuses unless the clone is `OUT/clone`, its `.git` a directory there (not a link, nor a worktree's `.git` file) with no `commondir` file, git reads that `.git` as both the repository and the home of its refs (`rev-parse --absolute-git-dir` and `--git-common-dir`), and the marker the `clone` gate writes into it (`.git/una-release-gates-clone`) names `OUT`'s physical path. Git runs with that `.git` named explicitly and none of the variables of `RELEASE_GATES_GIT_VARIABLES` in `scripts/release-gates-tag.sh` (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`, `GIT_CONFIG`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_SHALLOW_FILE`, `GIT_GRAFT_FILE`, `GIT_REPLACE_REF_BASE`, `GIT_NO_REPLACE_OBJECTS`, `GIT_QUARANTINE_PATH`, `GIT_PREFIX`) nor any `GIT_CONFIG_KEY_<n>` or `GIT_CONFIG_VALUE_<n>`, which the script also unsets for every gate. Only a ref under `refs/tags/` named `v<digit>…` changes; nothing is pushed or fetched, so the clone's source, the repository's remote and any real repository's tags are never touched.

`scripts/release-gates-tag-test.sh`, run by `crates/una-cli/tests/release_gates.rs`, checks each of these on repositories it makes in a temporary directory.

An `OUT` whose clone was made before #1017 has no marker, and may hold a tag that an old `release` gate left there: run the `clone` gate again on it before any other gate.

**The timing oracles** (#1145). Every test of `crates/una-cli/tests/timing_channels.rs` is a security oracle: it runs native programs that differ only in `secret` input, on the real clock, and requires the same observable outcome, such as whether a request under a `for ever within` deadline times out. Each is `#[ignore]`d, since the ordinary test run shares the machine with other tests, and runs only in two named places, one test at a time (`--test-threads=1`), with the same command, `cargo test --release --locked -p una-cli --test timing_channels -- --ignored --test-threads=1 --nocapture`. They run in release form: `--release` builds `una` and the test, and the test's helpers then build the release runtime that the executables link, since timings of the debug runtime, with its checks of reference counts, are not meaningful. Each oracle compares its two inputs' 20 runs each with the Mann-Whitney U rank test (`crates/una-cli/tests/common/rank.rs`), timeouts ranked above every time, and fails at a two-sided p below 0.001; a control compares one input with itself and must pass, so noise alone that would fail the test shows as a failed control. The places it runs:

- the step "Timing channels (security oracles)" of `scripts/local-ci.sh`, right after the tests, on a native host: macOS (so the `mac` gate) and `--linux-arm64` (so the `linux-arm64` gate). Under emulation, the `--linux` container through Rosetta (`UNA_LOCAL_CI_SERIAL`) or a shell that Rosetta translates, the real clock measures the emulator rather than the runtime, so the step is skipped there, and the run says so;
- the gate `timing-channels`, right after `native` and before `sanitize`: no Docker gate runs then, so the machine is as quiet as a gate run gets, as step 2 of the procedure asks.

The step adds a release build of `una-cli` and `una-rt` to each `scripts/local-ci.sh` run, on macOS in the checkout's `target/release` and in `--linux-arm64` in the container's target volume of that checkout, beside the debug build of the tests. Measured on the release machine (Apple M1 Max) on 2026-10-25, with 2 build jobs and another process holding a core, it took about 3 minutes and left a `target/release` of about 0.6 GB; the oracle's runs then take under a minute. The cost on `--linux-arm64` was not measured yet. `--nocapture` keeps every run's time and outcome, and the statistics, in the step's output.

**The timing and scaling tests of the cryptography** (#2119, ADR 0133 rules 9 and 10). `una-crypto` has two test files that the ordinary test run does not exercise, and both run where the timing oracles run, after them, in the same release build: in the gate `timing-channels`, in one log and one result, and in `scripts/local-ci.sh` as the steps "Timing channels (cryptography: timing)" and "Timing channels (cryptography: scaling)", skipped under emulation with the oracles.

- `crates/una-crypto/tests/timing.rs`, `cargo test --release --locked -p una-crypto --test timing -- --ignored --test-threads=1 --nocapture`: five statistical tests in the manner of dudect, each `#[ignore]`d. A test times two classes of input that differ only in a secret (the position of the first byte that differs in `ct::eq`, the byte of a rejected tag that differs in ChaCha20-Poly1305 and in AES-GCM, the scalar of X25519, the key and the plaintext of AES-GCM), 20,000 samples in a random interleaving after 2,000 discarded ones (one call each; for `ct::eq`, whose call takes tens of nanoseconds, 64 calls), drops the slowest 5% of each class, and fails when the absolute value of Welch's t statistic reaches 10. `--nocapture` keeps each statistic (`timing t = ...`) in the log. Every test samples in one way (#2153): the two classes share one state, and the input of the sample's class is written into it before the clock is read, by the same work for both classes with no branch on the class, so the timed region holds the routine under test and nothing else. It is evidence, not a proof: a pass says that this run saw no difference, and a failure names a routine to read before the release.
- `crates/una-crypto/tests/perf.rs`, `cargo test --release --locked -p una-crypto --test perf -- --test-threads=1 --nocapture`: five tests of throughput floors and of how the time grows with the size (the hashes and the AEADs linear in the message, one X25519, the verification of Ed25519, ECDSA and RSA). Each returns at once under `debug_assertions`, so the ordinary `cargo test --workspace` passes them without measuring anything; before #2119 no script ran them in release.

Before #2119 no gate ran either file, so a change to the constant-time code of `una-crypto` reached a release with no timing evidence unless someone ran the tests by hand. In the gate the three commands always run, so a failed oracle does not hide the cryptography's statistics, and the gate fails when any of them fails. Measured on the release machine (Apple M1 Max) on 2026-11-19, while a gate run and other builds held the machine (load average about 8): the test build of `una-crypto` in release took 8 seconds from cold, the five timing tests 1.4 seconds together, and the five scaling tests 8.7 seconds, so the gate grows by about 20 seconds. On that loaded machine the scaling tests passed, and four of the timing tests passed in both of their runs (|t| at most 3.9). The test of `ct::eq`, as it was, failed in 5 runs of 8, with t between -11.6 and 14.5, of both signs: its two classes were two buffers in two allocations, so their alignment and cache placement differed with the secret, by an amount and a sign that changed from one process to the next. #2119 changed its sampling and neither its claim nor its limit: the two classes are now one buffer, made to differ in its first byte or in its last before each sample, outside the timed region, a sample is 64 calls, well above the clock's resolution, and the first 2,000 samples are discarded. Run 20 times alone at a load average of about 80, it passed 20 times, with |t| at most 5.8; with an early-exit comparison in place of `ct::eq` (in the test only, not committed) it failed every time, with t above 6,500. #2153 moved the other four tests to that sampling, with their claims and the limit unchanged, after an early run of the release gates failed in `linux-arm64` on the AES-GCM seal test (`aes-128-gcm seal t = -33.87`): its timed region held the preparation of the input, a copy out of a table of about 70 KB for the random class and zeros for the fixed class, so the statistic measured that copy; on macOS it passed, negative in 10 runs of 10. No dependence on the key or the plaintext was found in the implementation. Measured on 2026-11-19 on the same machine under load (load average about 35 to 50): on macOS, 10 runs of the file, every test of both signs and |t| at most 4.1; in the `linux/arm64` container, 5 runs, |t| at most 2.8, where the earlier sampling gave -32.4, -30.0 and -36.8 for AES-128 in 3 runs. With a difference planted in the timed region (in the test only, not committed), 3 runs each: an early-exit scan of the plaintext before the AES-128 seal gave t of 39 to 44, an early-exit comparison of the tag before each rejection 40 to 56, a branch per bit of the X25519 scalar 35 to 52, and a branch per bit of the AES-256 key -274 to -325; an early-exit scan of the 32 bytes of the AES-256 key gave only 7.9 to 10.1, at the limit, so a difference of that size, a few tens of nanoseconds, can pass. The numbers of a loaded machine remain weaker evidence than the gate's own run on the quiet machine it asks for, and a red result there is a finding to read.

A test added to the file without `#[ignore]` would run in the ordinary test run, where its verdict depends on the load; one ignored anywhere else would run nowhere. Neither is allowed, with one exception: `every_timing_oracle_program_checks` (#1947) reads no clock and runs `una check` on every program the oracles build, run or check, in each variant they use, requiring the accepted ones to check and the `secret` twins to be refused with the diagnostic and position their oracle asserts, so that the ordinary test run and the check of each pull request fail on an oracle program that a change of the language made stale, which the ignored oracles would otherwise show only as a compile error in this step, measuring nothing. `crates/una-cli/tests/release_gates.rs` checks that it is the only test of the file without the attribute.

**The owner-replay model.** The replay of an owner's chain in the registry client (`crates/una-project/src/tlog/owner.rs`) has a contract, `spec/30 §14` rule 5, "The replay's contract", as ADR 0122 Amendment 14 states it for this release. Three test-only modules check it, in that crate's test build, where a model of signatures stands in for Ed25519 on a test's own thread: `tlog/owner/reference.rs`, a literal reference of the amendment, written from its decisions and sharing no code with the replay; `tlog/owner/contract.rs`, the oracle, which reads only who signed what, the theft and the answers of the system under test, and never computes taint, voidness or which claims count; and `tlog/owner/alphabet.rs`, which generates the chains: registrations of 3 to 5 keys at every threshold the key floor allows, the owner's additions, revocations and claims before and after the theft, the theft at every position, the attacker's every entry signed by every non-empty subset of the keys it holds (one stolen key, and two in a separate mode), the owner's response by its claim or by an addition and then its claim, up to four attacker moves after it, and every entry kind this release does not replay. Each chain is read by the product and by the reference, and every question the oracle asks (whether a registry logs an entry, the verdict, how each release and yank stands at every position, the keys and threshold) must get the same answer from both; one reading in 509 is replayed again with Ed25519 and must give the model's history. The ordinary test run does this on every chain to depth 3, with the named rows: the known shapes of the design's table, the rules of acceptance one by one and the response at the floor. The gate runs, in release form, each test once under a supervisor: the named rows; every chain to depth 4 (four configurations: caps of claims 2, 3 and 64 with one stolen key, and 64 with two); every chain to depth 5 from the narrow alphabet's registration, three keys at threshold 2 (the least owner at the key floor, where a response needs an addition first unless the owner added a key before), every other move kept, in the same four configurations; and seeded walks of depths 6 to 9 (160,000 walks a seed: seeds 11 and 23 with one stolen key, seed 11 with two). A test killed by a signal, or by the 60-minute watchdog, fails the gate, and so does a run that did not report exactly one passing test or whose summary line (`owner-replay: <run> chains <N> responses <M> walks <W> unsupported <U> failures 0`, or `owner-replay: named rows shapes <S> failures 0`) does not carry the counts the script records, which a change to the model updates with its reason. Each bounded run also asserts that every coverage counter of the alphabet is at least one. Exhaustive depth 5 on the whole alphabet takes longer than the gate's budget; it is a soak outside the release gates (card #2018), with the walks of seeds 37 and 41 with one stolen key and 23 with two (`the_replay_agrees_with_the_reference_to_depth_five`, `the_replay_agrees_with_the_reference_on_more_seeded_walks`).

- **Must-reject:** a program built to break a flow rule must be rejected by `una check --tier 0`. An accepted one is a finding.
- **Must-keep:** two refactors that keep every label (a rename, a reordering of declarations) must not turn a rejected program into an accepted one.
- **The two-run oracle:** for an accepted program with a literal labeled above `public`, the literal is replaced by up to five other values of its type, in a fixed order, and every variant runs on the interpreter (`una run --json`) twice, each run in a directory of its own. What an observer below the literal's label sees, at `public` and at `internal`, must be the same in every variant that completes (`spec/07 §1`). Since S-41 and S-42 (`spec/11 §5`, `spec/26 §6` rule 4; #1514, #1515, #1544) a run's trace leaves out every operation performed in quiet code, under a program counter above `public`, and those of a handler instance that quiet code installed, so each variant also runs once as an example, the probe (#1911, `oracle.run_probe`, `docs/plan/security-hunt-oracle.md` §12): the entry module gets a handler of `Console` that does nothing and a test that gives it as `@console` and runs `main()`, and the trace of `una test --json`, which keeps the operations performed in quiet code (`spec/08 §2` rule 7), joins every observer's view, projected by `accepts` as the run's trace is, and the liveness view. A program whose `main` needs a host capability other than `Console` has no probe (U3014: an example cannot use host capabilities), and the programs without one are pinned by reason and count (`PINNED_PROBE_UNAVAILABLE`); a probe that errs, aborts while the run completed, or is available for the base and not for a variant is an error:
  - `status`, every `output` line, `failure` (its variant and its public fields), and the diagnostics by severity, code and message: `una run --json` redacts what a message renders above `public`, so a message that differs between variants is a leak, the class of S-28 (#874);
  - the `trace` events of the operations whose `accepts` the observer sees, as the model defines what an observer sees, in order. The `accepts` of host operations is the prelude's, pinned by a test; that of the program's own capabilities comes from its Core export. An operation the oracle cannot classify is an error, and an `accepts` it cannot read exactly counts as visible;
  - of each such event, every field but `seq`, which numbers the hidden events too, and `outcome`, which is what the host returned to the program, an input of the run and not something the program sends; the arguments that decide it are compared. Of `Keys.hmac`, only `key_name`, its one sink, is compared.

  Every variant that completes is compared with the program's first end that completed, the base's or a variant's, so an aborted base hides nothing. An argument of a visible event that the run redacted at a level above the observer is a finding by itself, whatever the other variants show: the run says that a value above what the operation accepts reached it. A program whose policy releases to `public` is set aside and counted, since the release explains a difference.
- **The comparison with the model's re-check** (#791): every program that `una check --tier 0` accepts is exported (`una --json core`) and read by the formal model's checker, `una-core-check`. The gate builds the checker with the pinned Lean, its version checked (`scripts/lean-env.sh`, shared with `scripts/formal.sh`), after the `formal` gate, and a Lean panic aborts it. A declaration the re-check rejects is a finding. What it compares is fixed by the run:
  - **Compared:** a program counts as compared only when the re-check accepts at least one of the program's own (`app.*`) functions. At least 1,002 programs (measured: 1,114) and 1,598 accepted declarations (measured: 1,776).
  - **What it does not read:**
    - a document the re-check reads as a whole fallback, every line `not re-checked` for one reason, compares nothing, so the count of such documents is pinned per reason, exactly;
    - so is the count of the program's own declarations it does not re-check, per reason, such as a `via` function, a `handler` declaration or an operation with a condition (ADR 0092), which the model's fragment does not cover.

    A change in either count fails the gate until the pins say so.
  - **`unknown`:** an outcome the comparison cannot judge. The expected ones are pinned by name with their reason (`PINNED_UNKNOWN`): today seven programs that use the primitive `fixed`, four in edition `0.2` and the edition `0.3` twins of three of them, in the sample, outside the fragment by design. Any other `unknown`, and a pinned one that is no longer unknown or is unknown for another reason, fails the gate.
  - **Residual programs:** these are programs where a secret may abort a step, which the full check's obligations guard. They are compared with the pinned solver, and their count is pinned (63: 13 of F8 and 50 of Q2). Their full check stops a solver query at 30 seconds (`--solver-wallclock 30`), half its limit of 60: a query the solver does not decide is U5002, which makes the row invalid, a gate error, and so does a check that reaches its limit.
    - A residual row whose own comparison is not clean is an error, and so is one the full check does not decide, or decides by another code.
    - One the full check accepts with a public print after the step is a finding.
  - **Tier-0 verdicts:** each program's verdict must agree with the must-reject driver's.
  - **Scope:**
    - the comparison reads only what `una check` accepts, at tier 0;
    - it does not export rejected declarations (no `--with-rejected` step);
    - the reverse comparison, a declaration the checker rejects and the model accepts (#514), stays out of the gate.

  It found S-27 (#799) on its first run, and adds about 45 seconds.
- **The native sample** (#792, `scripts/security-hunt/hunt/native.py`). A sample of the oracle's programs also runs as native executables. The sample is stratified, and fixed by the run's names: the programs whose name's SHA-256 starts with a byte below 20, about 8% of the oracle's programs and 5% or more of those it compares, and, for every family with a compared program, the one whose name has the lowest SHA-256, so that no family the oracle compares is left out of the sample by chance; the families it compares are pinned, and a family that drops out fails the gate. In it, every variant the interpreter ran is built with `una build` and run with the same limits, and the two engines must agree on everything the run shows (`spec/16 §5`), as the native equivalence test compares them (`crates/una-cli/tests/native.rs`):
  - the exit code and the standard output line for line;
  - the standard error: empty on a run that ends `ok`; otherwise its first line is the error, `[<code>] Error: <message>`, equal to the run document's, and every other line a place, `  at <file>:<line>:<column>`, or the note that names the explanation of its code;
  - the trace, every event and field, the result of each `Clock.now` aside; a redacted argument is compared as written, its label included;
  - a run that starts tasks by the rule of `spec/19 §8` rule 4: the output a merge of each task's lines in its own order, each line quoted as the trace writes it (`una_core::quote`); on an ordered run, one that neither fails nor cancels a task, the trace equal to the interpreter's and the output, as a multiset, the document's; on a run that is not ordered, the trace the interpreter's in order with the extra events those of tasks that started after a failed one, and the output the document's plus only the lines those events printed. A line whose printed form the trace redacts is not matched against the trace, and which task prints first is outside the model (`spec/19 §6` rule 7), so only each task's own order is compared;
  - a run the interpreter ends with U6003, U6004 or U6005 by the rule of `a_copy_between_tasks_over_the_budget_is_u6003_in_both_backends`: where each engine runs out is not exact (ADR 0061), so the executable must end with the same exit code, error and standard output, and one engine's trace, its `seq` aside, must be a prefix of the other's, so that an effect one engine makes before its abort and the other never makes is a divergence; the place of the abort is not compared. A variant whose interpreter run reached the time limit is not compared, and the result says so.

  A difference is a backend divergence, a finding. A sampled program whose policy releases to `public`, which the oracle sets aside, still runs natively, every variant, since a declassification is where redaction could differ between the engines. A sampled program that is not compared must say why: the checks reject it, so nothing runs, or it is pinned as not compiled; any other is an error, and so is an error of a sampled program's native comparison. A variant whose interpreter run reached the time limit, its full check deciding, would be listed as not compared, but any such kill fails the gate (`MAX_TIMEOUTS_DECIDED`, below), so a passing gate has none. A sampled program the native backend does not compile must be pinned by name, with its reason, in `scripts/security-hunt/native-unsupported.txt`; any other build failure is an error, and so is a pinned program that compiles. Measured on the fixed run before families D and Y: 45 programs sampled, 5 of them in the edition 0.3 sample, all seven families with oracle programs present (B, C, H, K, P, Q and T, pinned), C with task runs compared by the rule above; 40 compared natively, those whose policy releases to `public` among them, with 184 variants (floors: 36 programs and 165 variants); and 5 not compared because the checks reject them, each listed with its reason (two closed calls of B2 and three programs of T12); no program left uncompiled and no divergence. Families D and Y (#1001) add 9 programs of D2 to the sample, 54 in all, and family D to the pinned families: run alone, 6 of them were compared natively, with 36 variants, path and vendored registry dependencies both, and 3 closed calls not compared; no divergence.

**The Linux sandbox** (#793). `scripts/hunt-linux.sh --linux-arm64 OUT TIP` runs the same gate, with the same pins, on Linux. It builds the release `una` and the re-check's executable in the image and volumes of `scripts/local-ci.sh`, then starts the gate in a second container, which is the sandbox of the gate as a whole:

- no network (`--network none`: loopback only), a read-only root with a `tmpfs` for `/tmp`, the checkout, the target directory, Z3 and Lean mounted read-only, and `OUT` the only writable mount;
- the caller's user, never root, no capability (`--cap-drop ALL`), `--security-opt no-new-privileges`, an init process that reaps orphans (`--init`), at most 1,024 processes and 6 GiB of memory, 30 minutes in all, and a clean environment (`env -i`) with the marker `UNA_HUNT_SANDBOX=container`.

Every run of the gate, on either platform, has a directory of its own, made for it (`sandbox.fresh_dir`), and it is the only one it may write: the packages it checks are read from their own directory, and a document it reads is copied into its directory first. No cache crosses runs: a package is read-only to the runs that check it, so `una` keeps no proof cache there, and a run's proof cache, if any, stays in its own directory. Every run reads one proof-cache key, made by the gate once, outside every run's directory, which no run can write (the sandbox canary checks it): the key protects the integrity of a proof cache's entries, and with no cache shared between runs, a key every run can read gives none of them a way to reach another, where a key made in each run's fresh `HOME` cost about 6 ms a run (measured 2026-10-17). A run starts only while the key is the file the gate made, unchanged, and the gate reads it again at its end: a key that went missing or changed fails the gate, so `una` never falls back to a key of its own. A run starts a process group of its own with no input, and the group is killed when the run ends or reaches its time limit; a process that leaves the group (`setsid`) is not killed with it, and if it still holds the run's output open five seconds after the group is killed, the gate fails. On Linux, Landlock confines each run, the compiler, the executables it builds and the re-check (`scripts/security-hunt/hunt/landlock.py`), as `sandbox-exec` does on macOS. The process restricts itself, after `PR_SET_NO_NEW_PRIVS`, and then executes the run, which can never lift the restriction:

- every file right of the kernel's Landlock ABI is handled: the run may write, create, remove, rename and link only under its own directory, which is opened without following a link and must have the device and inode recorded when it was made; it may read and execute only there, in the directories of its tools (`una`, the re-check, Z3 and Lean) and of its `PATH`, in its working directory, in its executable's own directory and in the system's (`/usr`, `/lib`, `/lib64`, `/bin`, `/sbin`, `/etc`, `/proc`), never the root and never the gate's output; among devices it may write only `/dev/null`, and read only it, `/dev/urandom`, `/dev/random` and `/dev/zero`;
- TCP is handled: the run may connect only to the mock server's port and bind no port;
- abstract Unix sockets and signals are scoped to the run's own domain: it cannot signal the gate or another run.

Landlock does not mediate UDP or a connection to a Unix socket that already exists in the file system; in this container no such socket or UDP listener is reachable, and "TCP only to the mock" is not "no other network". On macOS, the profile of `sandbox-exec` denies writes outside the run's directory, the network and signals to processes outside the run's own (`(deny signal (target others))`), and does not confine reads.

The gate refuses to run, before any run starts, unless all of these hold inside its container (`sandbox.container_problems`): the marker, the container runtime's `/.dockerenv`, no capability in any set (effective, permitted, inheritable, ambient and bounding), no-new-privileges set, a user and a group other than root, the root mounted read-only, no network interface up but loopback (the kernel's fallback devices, such as `gre0` or `sit0`, are listed but down) and no route but through it, so no default route, a TCP connection to a public address (IPv4 and IPv6) that fails with `ENETUNREACH`, and Landlock at ABI 6 to 8. Below ABI 6 Landlock cannot scope signals and abstract sockets, and the gate does not run there rather than rely on `--network none` alone; above ABI 8, a later ABI adds rights the gate does not handle yet (the upstream `include/uapi/linux/landlock.h`, read on 2026-10-17, lists a file right of ABI 9 over Unix sockets and rights of ABI 10 over UDP), and it does not run there until they are. A ruleset is never applied in a reduced form ("best effort"): a failed Landlock call stops the run before it executes, and the gate fails. The sandbox canary above checks that the restriction is enforced, not only applied. The container can read its mounts' host paths (`/proc/self/mountinfo`), so `scripts/hunt-linux.sh` fails the gate when its evidence holds the checkout's path or the caller's home. Measured with Docker Desktop's kernel 7.0.14-linuxkit on arm64 (2026-10-17, UTC): Landlock ABI 8.

The pinned Z3 comes from `UNA_GATES_Z3`, else this checkout's `target/z3`, else the clone's `target/z3`. If none is there, the `build` gate installs it with `scripts/install-z3.sh`.

- A target built by `fuzz/Cargo.toml` that the script does not run, or the reverse.
- A path dependency of `fuzz/Cargo.toml` that is not a workspace crate at its place under `crates/`, by `cargo metadata` (`crates/una-cli/tests/dependencies.rs`): the fuzzed code is the workspace's own.
- A crates.io package of `fuzz/Cargo.lock` that is neither in `supply-chain/crates.tsv` nor in `supply-chain/fuzz-crates.tsv` (the `deps` gate, with cargo-deny run on `fuzz/Cargo.toml` too).

**The fuzz smoke run** (#1430). `scripts/fuzz-smoke.sh` is a smaller run of the same fuzz targets, for the `fuzzing` check of the engineering harness. It is not a release gate and never replaces the `sanitize` gate, which keeps the full counts and floors. The targets, their counts and floors, the flags, the seed and the steps live in one file, `scripts/fuzz-targets.sh`, which both scripts source, so a target added there runs in both. The smoke run builds the targets with the checking toolchain, fails if that toolchain is missing or differs, checks that the targets are exactly those of `fuzz/Cargo.toml` and each is instrumented with AddressSanitizer active, runs the canary (its crash must be reported and minimized to `una!`), and then runs each target from its committed seeds, with the gate's fixed seed, for a twentieth of its count (at least 2,000 inputs, a floor that does not bind today, since the smallest smoke count is 15,000), with a ceiling of 300 s. It fails on a crash, an AddressSanitizer report, a panic, an input over 10 s or 4 GiB, a target that ran fewer inputs than asked, or coverage below its smoke floors: the counters floor unchanged, since the counters of the code libFuzzer loads do not depend on the count, and the `cov` and `ft` floors a quarter of the gate's, never below 1, since a shorter run reaches less of them (a first run reached `ft` 8,782 in `words`, whose gate floor is 16,955) while a target that returns early on every input still falls below them. The registry targets keep their placeholder floors of 1, as in the gate. Its build and runs go under `$CARGO_TARGET_DIR/fuzz-smoke` (or `target/fuzz-smoke`). macOS only, like the gate.

**The Linux archive smoke** (#1906). Not a gate: evidence of the release validation for the `aarch64-unknown-linux-gnu` archive, beside `scripts/check-release.sh`, which runs in the build container. `scripts/linux-archive-smoke.sh ARCHIVE OUT` takes the archive `scripts/release.sh` packed and, in clean linux/arm64 containers of the system `UNA_SMOKE_DISTRO` names (`ubuntu-24.04`, the default, `ubuntu-22.04`, `debian-12` or `almalinux-8`, each pinned by digest, #2105) with no Rust, no Z3, no checkout and no network, as uid 1000: installs it with `install.sh` from a local mirror (`file://` URLs and a stand-in validation summary that lists the archive's digest; the installer installs 0.4.0 and later, so an earlier archive is packed again under 0.4.0 (or under `UNA_SMOKE_VERSION`, which also serves an archive of `main` as the next release, so that the installer applies that release's glibc floor) with only its top directory renamed, and the installed `una` is compared byte for byte with the archive's); runs `una --version` and `una check --tier 1`, `una test` and `una run` on every package under `examples/`, with `examples/health` served; checks that `una build` without a C compiler stops with "cannot run the system linker `cc`" and that `una run` still works after it, and that with gcc as `cc` every executable prints what `una run` prints; checks that the installer refuses Alpine (musl) and Debian 9 (glibc 2.24, below every floor) and installs nothing, and that `una check` refuses root with U5003; and records the libraries and symbol versions `una` needs (`readelf -d`, `-V`), the digests, and the opens the solver child's confinement answers with `EACCES` (#1455), under `strace`. It prints one `PASS`, `FAIL` or `NOTE` line per item and exits 1 on any `FAIL`. It builds two small images of that system (curl; curl, gcc, the C library's development files, binutils, strace) once, with the network, and creates no Docker volume.

**The glibc floor** (#2105). The Linux `una` is a dynamic glibc executable, and the loader of an older glibc refuses an executable that names a later symbol version, so the versions `una` asks for decide the oldest system it runs on. `scripts/check-release.sh` reads the floor from `install.sh` (`glibc_floor`, the version below which the installer refuses a system, so the two cannot differ) and runs `scripts/glibc-floor.sh` on the packed `una` and on an executable it builds from `examples/hello`: the highest `GLIBC_` symbol version each asks the loader for (`objdump -T`), weak references included, must be at or below the floor, and each prints a line `glibc: <file>: highest symbol version GLIBC_<version>, floor <floor>`. The same scan at the floor 2.17, the first glibc of AArch64, must fail, as its canary. The Z3 library and the C++ runtime are linked into `una`, so their needs are read with it. The floor is 2.28, the glibc of the image the archive is built in (`scripts/local-ci/Dockerfile.release`, AlmaLinux 8 with GCC 13 from gcc-toolset-13, #2105; the tests, the formal track and the hunt stay in the Ubuntu 24.04 image of `scripts/local-ci/Dockerfile`, since the pinned Lean toolchain needs glibc 2.29 and the Z3 project's Linux executable 2.38, and `scripts/local-ci.sh --linux-arm64` packs and checks the archive in a second container of the release image), which an executable linked there cannot exceed; measured on 2026-11-26, the `una` built there asks for `GLIBC_2.17`, `GLIBC_2.18`, `GLIBC_2.25` and `GLIBC_2.28`. Through 0.5.1 the image was Ubuntu 24.04 and the floor 2.39: the archive of 0.4.1 reached it with C23's entry points of glibc 2.38 (`__isoc23_strtol`, `__isoc23_strtoul`, `__isoc23_sscanf`), from Z3's objects and `libstdc++.a` compiled against that image's headers, and, weakly, `pidfd_spawnp` and `pidfd_getpid` of 2.39, from Rust's standard library. `install.sh` keeps the floor 2.39 for `UNA_VERSION` 0.4.0 to 0.5.1. Before glibc 2.34 threads and `dlsym` are libraries of their own, so a `una` built on 2.28 also names `libpthread.so.0` and `libdl.so.2`, which `scripts/load-commands.txt` lists as glibc's. The archive of #2105 was tested, with the smoke above, on Ubuntu 22.04 (glibc 2.35), Debian 12 (2.36) and AlmaLinux 8 (2.28); that it runs on the other systems with glibc 2.28 or later (Ubuntu 20.04, Debian 10 and 11, RHEL 8 and later and their rebuilds) is inferred from the symbol versions it needs, not tested.

**The Docker backend** (#1082). The gates that use Docker (`linux`, `linux-arm64`, `release`, `reproducible`, `hunt-linux-arm64`, `limits-linux-arm64`, `limits-linux` and `toolchain-free`) run on Docker Desktop's context `desktop-linux`. Another container runtime on the same machine can be the active context, and the gates must not run there. So when a requested gate needs Docker, the script refuses before any gate, with exit code 2, unless `DOCKER_CONTEXT`, or else the active context (`docker context show`), is `desktop-linux` and `DOCKER_HOST`, which would override the context, is unset. It then exports `DOCKER_CONTEXT=desktop-linux` for every gate, so a change of the active context during the run does not move a gate. The record names the context and the server's version (`docker version`).

At the end, a run that used Docker removes the Docker volumes that `--linux` and `--linux-arm64` made for the clone's target directory, so volumes do not pile up.

**The job count in the containers** (#701). By default, Cargo inside a container runs one job per CPU of the Docker VM. On a VM with 8 GB and 10 CPUs, ten rustc and linker processes at once have run it out of memory: the kernel killed the linker with signal 9, the test binaries did not link, and no test ran.

`scripts/local-ci.sh --linux` and `--linux-arm64` therefore pass a job count into the container, which `scripts/container-jobs.sh` computes:
- The build runs one job per 2 GiB of the VM's memory (`docker info`'s `MemTotal`), at most one per CPU and at least one. That is 3 jobs on the VM above.
- A `CARGO_BUILD_JOBS` set on the host can lower that count, never raise it. A higher value, such as one meant for the host's own builds, is capped, and the run says so.
- `RUST_TEST_THREADS`, when set on the host, goes in too.

The run prints the job count before the container starts, and the container's peak memory (`memory.peak` of its cgroup) at the end. The job count changes only the build's peak memory and its time, never what is built or tested.

Why 2 GiB: a measured run of `--linux-arm64`, cold, on that VM (7834 MiB, 10 CPUs) with 5 jobs (one per 1.5 GiB) passed with a peak of 6841 MiB, 87% of the VM. That figure includes page cache, which the kernel reclaims before it kills a process, but the margin is narrow. These runs are evidence: a linker killed for memory costs a full rerun and leaves a failed run in the record, which outweighs the slower build of 3 jobs. A lower `CARGO_BUILD_JOBS` set on the host is passed in as it is, for a one-off run that wants even less memory. The VM's memory is the host's setting, and the script does not change it.

**The containers' user** (#1394). The image of `scripts/local-ci/` runs as an unprivileged user, `una`, with uid and gid 1000, never as root: the solver child refuses to run as root (ADR 0124 rule 7, U5003 "the solver must not run as root"), so a root container failed every test that verifies, and the confinement is not relaxed for the container. The user owns the toolchain's directories (`/opt/cargo`, `/opt/rustup`) and the mount points of the volumes (`/work/target`, `/opt/cargo/registry`, `/opt/z3`, `/opt/z3-cache`, `/opt/lean`), so a new volume starts owned by it, and the run of `scripts/local-ci.sh --linux` and `--linux-arm64` names it too (`--user 1000:1000`). A volume that a root container made before is handed over by `scripts/container-volumes.sh`, which `scripts/local-ci.sh`, `scripts/hunt-linux.sh` and `scripts/local-release.sh` run before their containers: one short container as root, with no network, that changes the owner of every entry of those volumes that another owner holds, and nothing on a volume that is already the user's, so the volume names and their builds are kept. The checkout's bind mount needs no such step: Docker Desktop lets the container's user write it. The steps, their environment and the serial and retry settings are unchanged.

**Reproducible archives** (#679). The binaries were already reproducible: `scripts/release.sh` remaps the build's paths (#382), and the linkers derive the macOS binary's `LC_UUID` and the Linux binary's build ID from its content, so both are equal when the inputs are. Two builds of one commit, from fresh clones at different paths and cold target directories, gave byte-identical binaries on `aarch64-apple-darwin` and, in Docker, on `aarch64-unknown-linux-gnu`. Three things made two archives of one commit differ, and `scripts/release.sh` now fixes each:

- each tar entry had the time the files were copied, so every entry now takes the commit's time, `SOURCE_DATE_EPOCH` when it is set, else `git log -1 --format=%ct`. A build that finds neither stops;
- each entry named the account and group that built it, so every entry is now owned by `0:0` with no user or group name, which `scripts/check-release.sh` checks;
- the gzip header had the packing time, so `gzip -n` now stores none.

The entries are also packed in byte order of their paths, with modes 755 for directories and `una` and 644 for the other files, so the order of a directory listing and the umask do not matter. On macOS, extended attributes, ACLs and resource forks are left out. The containers of the Linux builds cannot read the commit's time when the checkout is a worktree, so `scripts/local-release.sh` and `scripts/local-ci.sh` pass `SOURCE_DATE_EPOCH` in. The `reproducible` gate costs a second `release` gate, so a full run of the gates takes about that much longer.

## 3. The record

The script writes into `OUT`:

- `results.tsv`: a header line, then one line per gate run, tab-separated: `gate`, `sha`, `result` (`PASS` or `FAIL`), `seconds`, `log_sha256`.
- `logs/<gate>.log`: each gate's full output. Its SHA-256 is in `results.tsv` and in the record.
- `record.md`, the full validation record:
  - the commit, its subject, the run's date, platform, `rustc` and Docker, the Docker context and server version, the SHA of the script that ran, and the shipped targets (§2);
  - a table of the gates, with result, seconds and log digest;
  - the archives that the `release` gate packed, with their SHA-256; once there is any archive, or the `release` gate passed, they must be exactly one per shipped target, or the verdict is FAIL and names `archives` (#1903);
  - the runtime strip: for each target, the `strip` that removed the debug sections of the runtime built into `una` (#1359), as `scripts/release.sh` printed it in the `release` gate's log, on a line `strip: <target>: <tool>`: on macOS the Xcode toolchain's `strip -S`, by `xcrun`, named by its Xcode release and build (or the Command Line Tools' version), on Linux GNU strip's version line with `--strip-debug -D`, each with the SHA-256 of the `strip` binary;
  - the Linux toolchain: for each Linux target, the Debian packages and the files that the linker puts into `una`, as `scripts/check-toolchain.sh` printed them in the `release` gate's log once each matched `supply-chain/z3.lock` (#1926, #1958), on lines `toolchain: <target>: <package> <version>` and `toolchain: <target>: <file> sha256 <digest>` (#1971);
  - the musl inputs: for each Linux target, each musl file embedded into `una` with its SHA-256, as `scripts/release.sh` printed it in the `release` gate's log once it matched `supply-chain/musl.lock`, on a line `musl: <target>: <file> sha256 <digest>` (#1971);
  - for these three sections, each line is copied only in its expected shape, once and sorted, read under `LC_ALL=C` so that an invalid byte elsewhere in the log stops nothing. A line with the prefix in any other shape, a control character such as a carriage return included, is not copied, and the section ends with a line `- Not copied: <n> of the <m> lines ...` instead, which the summary refuses for the runtime strip (#1971);
  - the dependency audit: the `cargo-deny` version and the advisory database's commit and date that the `deps` gate used;
  - the verdict:
    - `PASS (every gate)`;
    - `FAIL (<gates>)`;
    - `INCOMPLETE (not run: <gates>)`, over the required gates (§2).
    - `ACCEPTED BY THE OWNER`, written by hand into the record committed for a tag, never by the script: the owner's recorded decision to release a commit whose gates did not all pass, followed by the gates' result and the reason. The installer (`install.sh`) accepts this line like `PASS (every gate)`; it still checks the archive's digest against the record.
- `summary.md`, the public summary, which `scripts/release-summary.py` writes from `record.md` by a fixed template (#717):
  - the commit, the run's date, operating system and architecture, and the `rustc` and Docker versions;
  - the table of the gates, with result and seconds, each row as the record names its gate. A record made before #2081 names the documentation gate `site`, and the summary accepts that row in place of a `docs` row and copies it unchanged: the documentation gate of such a record is its `site` row. A record that names both `site` and `docs` is refused, since no run writes both;
  - the archives with their SHA-256;
  - the runtime strip, as in the record;
  - the dependency audit's tool and advisory database, as in the record;
  - the verdict, as in the record.

  Nothing else of the record is copied: no subject, no notes, no log digest, no Linux toolchain or musl lines. Each field is checked against its shape before it is written, and a field out of shape stops the summary, so no free text reaches it. The record's lines end at `\n` only: a record that holds any other character at which Python ends a line, such as a carriage return, is refused, so that no copied line can pose as a heading or a field (#1971). The summary must not match the privacy pattern: `UNA_PRIVACY_PATTERN` when it is set, else the macOS Keychain item `una-privacy-pattern`, which `scripts/release-gates.sh` reads into a shell variable that it never exports, unsetting the caller's variable, so that no gate inherits it, and hands only to the summary step; it never prints, logs or writes it. The neutrality pattern of the public pages is read the same way, from `UNA_NEUTRALITY_PATTERN` or the Keychain item `una-neutrality-pattern` (#789). Each pattern is held in a shell variable that is never exported, and reaches the one step that applies it on a pipe, file descriptor 3, never in an environment or an argument, which other processes of the machine could read: the privacy pattern the summary step, the neutrality pattern the `docs` gate's command, which hands it to the docs bundle on a pipe of its own. Neither is ever printed, logged or written, and the script refuses to run under a trace (`set -x`), drops the shells' startup files (`BASH_ENV`, `ENV`) and writes no core file. **Both patterns are extended regular expressions (`grep -E`), the one dialect of every check, and each must contain the alternative `una-pattern-canary`**, which the script checks matches before any gate: a pattern that matches nothing (a typo, a pattern grep rejects, a blank value, or the hexadecimal that `security -w` prints for a value it cannot print as text) stops the run rather than passing every page. Without either pattern, the script stops before any gate; `UNA_GATES_UNCHECKED=1` runs the gates without them: such a run's summary opens with "Unchecked: written without the privacy pattern; not for publication", and no publish command is printed.
- `release-notes.md`: the summary, then the version's `CHANGELOG.md` section that `scripts/local-release.sh` wrote.

For a tag, `summary.md` is committed as `docs/validation/<version>.md`, unchanged. The full record and the logs stay private. `docs/validation/repacked.md` lists the macOS archives of v0.3.3 to v0.3.13, which were packed again after their release, each with its gated and its published digest and the check that paired them, and the withdrawn macOS archives of v0.3.0 to v0.3.2.

## 4. The procedure for a release

1. Merge the release pull request under rule 1, and note the SHA of `main`. The release pull request sets the version, regenerates `fuzz/Cargo.lock`, which pins the workspace's crates at that version (`cargo +<checking toolchain> metadata --manifest-path fuzz/Cargo.toml`, #766; the supply-chain test fails until it does), runs `scripts/changelog-assemble.sh`, which writes every fragment of `changelog.d/` under `## Unreleased` in a fixed order (the issue number, then the file name) and removes the fragments (#744), and renames `## Unreleased` to `## v<version>` with the release's introduction, leaving an empty `## Unreleased` above it.
2. Let the nightly run validate that SHA: merge the release pull request during the day, and the night's run of `scripts/release-gates.sh` on the head of `main` is the release's run (rule 2). To run it at once instead: `DOCKER_CONTEXT=desktop-linux scripts/release-gates.sh <sha> <out>` on that SHA, with Docker Desktop running and nothing else using it.
3. If the verdict is PASS and the summary was written with `UNA_PRIVACY_PATTERN` set, commit `<out>/summary.md` as `docs/validation/<version>.md` (and, until the repository is public, `<out>/record.md` as `docs/releases/<version>-validation.md`) in a pull request that changes nothing else, under rule 1.
4. Check rule 2 on the merged record commit: its own change is the summary, and `git diff --name-only <gated> <record commit>` lists only files under `docs/`. Once the release is approved, tag `v<version>` on the record commit and push the tag.
5. Publish the archives from `<out>/clone/target/local-release/v<version>/`, checking that their digests match the summary's, with the `gh release create` command that `scripts/release-gates.sh` prints at its end (`scripts/release-publish.sh`). A pre-release, a version with a suffix such as `0.4.0-alpha.1`, is published with `--prerelease --latest=false`. The summary is the release's notes, followed by the `CHANGELOG.md` section, and is attached as `una-<version>-validation.md`. No command is printed for an unchecked summary, and an unchecked summary is not published.

**The release notes** (#2134). `CHANGELOG.md` is the engineering record; `docs/release-notes/<version>.md` is what a user of the language reads. The release pull request adds the notes of its version: the title `# Una <version>`, a short summary, then `## Highlights`, `## Changes that may need an edit`, `## Security` and `## Platforms`, and a last line that links the release's section of `CHANGELOG.md`. The notes state only what the release ships, and each example in them is real: `crates/una-cli/tests/guide.rs` checks every code block and compares every output shown with what this `una` prints, as it does for the guides, and fails when the version of `Cargo.toml` has no notes file. The docs bundle ships the notes, under the neutrality check, and the website shows them above the full list.

Once tagged, a release's `## v<version>` section of `CHANGELOG.md` is frozen: its release notes were published from the tag, and `scripts/check-released-sections.sh` fails when the section on a branch differs from the tag's (#645). A correction to a released version, a security advisory included, goes in a changelog fragment whose bullet starts `- **Errata for v<version>: …**`, and ships with the next release's notes. A released section changes only by a recorded amendment (#2111): a card that states the reason, and one line of `scripts/released-sections-amended.txt`, which holds the tag, the SHA-256 of the amended section (the script prints it for a section that differs) and the card. The check then passes that tag only while its section is the recorded text, and names it `amended`; an amended section edited further fails, as do a record whose section is identical to its tag, a line out of shape, two lines for one tag and a tag the check does not read. The tag and the release notes published from it keep the original text.
