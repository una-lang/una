# The trusted computing base: a risk profile

Every Una guarantee holds "assuming the trusted base behaves as specified" (charter §3). The build report counts part of that base: its `tcb` section lists a package's `trusted` modules with their line counts, the host capabilities it uses, the solver and the proof cache (`spec/13 §6`). Line counts do not say what a bug in a component could do, what catches it, or what is left open. This document says that for each component of the toolchain's trusted base, and ranks the open gaps.

Its sizes describe the repository at commit `3e5b800b`, when edition `0.3` was in preview. The formal coverage of §3.1 was refreshed at commit `491dc89c` (2026-11-10), for v0.4.0, whose previews are editions `0.3`, `0.4` and `0.5` (`una --version`). Sizes are lines of Rust under each crate's `src/`, unit tests included. The counts of `unsafe` code (§3.2, §3.3) were taken again from the code at commit `0516fba0` (#1686), by a regular expression over every crate's `src/` and the tests of `una-sys`, comments left out, cross-checked with `grep -c` and the `// SAFETY:` comments of each file. Proposed decisions are described as proposals.

## 1. What a bug can cause

Each component is rated by the worst outcome a bug in it can have on a program the toolchain accepts:

| Class | Meaning |
| --- | --- |
| **Soundness** | The checker accepts, or the verifier proves, what the specification rejects: a leak through the information-flow rules (`spec/07`), a capability used beyond its grant (`spec/05`), a false contract or refinement. |
| **Wrong result** | A run computes a value the Una Abstract Machine (`spec/11`) would not, without touching memory it does not own. |
| **Memory safety** | A run reads or writes memory outside the objects it owns. This is the class that turns any other bug into arbitrary behavior. |
| **Leak of the build** | An artifact reveals the machine, account or paths that built it. |
| **Supply chain** | An artifact differs from what its source and pinned inputs determine. |

## 2. The ranking

Ranked by the worst class, then by what guards it today:

| Rank | Component | Worst class | Main guard | Main gap |
| --- | --- | --- | --- | --- |
| 1 | Checker: names, types, labels, capabilities (`una-check`, `una-syntax`) | Soundness | Conformance suite; Lean re-check of fragment F1 | The re-check covers part of the language; capability confinement (T4) is not proven |
| 2 | Verifier and Z3 (`una-verify`) | Soundness; memory safety once proven checks are elided | Pinned solver; model re-checks of `sat`; obligations that are not proven are errors | `unsat` (proven) is trusted with no certificate; refinement soundness (T5) is not modeled |
| 3 | Native runtime (`una-rt`), the OS bindings and stack switch it shares with the interpreter (`una-sys`), and the code that calls them | Memory safety | `unsafe` confined to `ffi.rs` of `una-rt` and to the modules of `una-sys` that call the operating system or switch stacks; native and interpreter compared on every runnable program, also against an AddressSanitizer build; Miri on the unit tests of `una-rt` | Sanitizers and fuzzing on macOS only, with no leak detection; some tests smaller under Miri; Miri cannot run the stack switch |
| 4 | Host capabilities and the prelude | Soundness (labels), wrong result | Host-table checks; two implementations compared | Two implementations of each operation; the TLS stack is trusted |
| 5 | Native codegen (`una-codegen`) and the linker (`una-link` on macOS, the system `cc` on Linux) | Wrong result | Native and interpreter compared; both linkers compared; the linker's verifier | Programs outside the runnable corpus; `cc` unpinned and unrecorded on Linux |
| 6 | Reference interpreter (`una-interp`) | Wrong result | It is the reference; native runs are compared with it | Not related to the formal model |
| 7 | Elaboration and the bridge to the formal model | Soundness | Identity runs of the Core export | Elaboration and the importer are trusted |
| 8 | The Rust toolchain and the crate dependencies | Supply chain, and any class of the crate's own bug | Pinned toolchain; `Cargo.lock` with `--locked`; reproducible gate; the `deps` gate (advisories, licenses, sources, the review record) | The review record's baseline was not reviewed crate by crate |
| 9 | Release scripts and archives | Supply chain, leak of the build | Reproducible gate; SHA-256 digests | No signature or provenance statement |
| 10 | Proof cache | Soundness | HMAC-SHA-256 tags under the user's key | The key file is trusted |
| 11 | Package integrity and the registry client (Itá, edition `0.4`, ADR 0122) | Supply chain; soundness through a trusted module of a dependency | Closed grammars of `ita.una`, `ita.lock` and `itaty.una`; content digests re-hashed on every load over the bytes read once into memory, through descriptors that follow no link, and only those verified bytes used; writes into a fresh private directory renamed into place; provenance re-verified on every load; only `una ita` may reach the network; the root re-checks and re-proves every package | Registry packages are not mounted yet; the owner's key chain is not verified yet; the resolver's network side and the registry client are to come, each with its own review |

## 3. The components

### 3.1 The checker

`una-check` (about 32,700 lines) and `una-syntax` (about 8,900) decide names, types, labels and information flow (`spec/07`), capabilities and authority (`spec/05`), and generate the obligations the verifier discharges. The prelude, `crates/una-check/src/std/prelude.una` (177 lines), is part of it.

- **A bug can cause:** soundness. A leak accepted by the flow rules, or a capability used where it is not granted. This is where most past defects were: 8 of the 14 advisories of `docs/security/advisories.md` are checker defects in information flow or authority (UNA-SA-001, 002, 004, 005, 006, 011, 012 and 013), four of them Critical.
- **Guards:**
  - the conformance suite (`tests/conformance`: `authority`, `security`, `types`, `verification` and others), run on every change by `scripts/local-ci.sh`;
  - unit and scaling tests in `crates/una-check/tests`;
  - the determinism gate of `scripts/release-gates.sh`, which runs the suite twice and compares outputs;
  - adversarial reviews of each change that touches these rules, where the advisories above were found.
- **Formal coverage:** the Lean development in `formal/` (`docs/plan/formal-track.md`, `formal-track-status.md`) proves type safety (T1), the unary halves of T2 and T3, and noninterference (T6) for fragment F1, with no `sorry` and no axioms beyond Lean's standard three (checked by `scripts/formal.sh`). A Lean checker proven sound re-checks the exported Core (`una core --json`, ADR 0083) of each declaration it can read: it accepts only what it proves, and answers "not re-checked" for a form outside F1. The replay of past findings on pre-fix releases is rejected by the re-check for most of them.
- **Open gaps:**
  - The re-check reads a part of the language: on the corpus of the status document, about a quarter of all declarations are accepted by it. On `main` it rejected four declarations of three conformance cases, triaged in the status document (#1676): none is a flow `una check` gets wrong. Two (`move_checked.kept` and `.moved`, a `checked` of a collection) are now refused as not re-checked; the other two (`fold.total` and `inference.contravariant`) stay rejected until F1 models `uses of`, since F1 has no effect polymorphism. What it does not read is guarded by tests and review only.
  - Capability confinement (T4, fragment F2, milestone M7) is not proven. Handlers declared outside a document, and `given`, are outside the re-check until then.
  - Refinements, `together`, maps, text, JSON and HTTP are outside F1 (formal plan §3). So are the forms of edition `0.4` and `0.5` that F1 does not model, which the re-check refuses as not re-checked: HTTP servers, refused by name (#1012, `spec/31 §9`); the collections of `std.collections` (#983) and a `checked` of a collection (#1676); `tasks` statements, `start` and `first of`; and `for ever within`, whose deadline is timing. No server and no collection of edition `0.4` or `0.5` is proven by the Lean model: those guarantees are checked by the checker's rules and tested.

### 3.2 The verifier and the solver

`una-verify` (about 9,400 lines) encodes obligations in SMT-LIB (`spec/12 §4`) and runs one solver process per query. (ADR 0124, step 1.) The process is `una` itself, re-executed in its solver mode, running the Z3 built into `una` from source pinned by commit, tree and tarball digest (`supply-chain/z3.lock`) and built by the committed recipe of `supply-chain/z3/`; no `z3` on `PATH` is ever run, so a directory earlier on `PATH` can no longer forge proofs. The child confines itself before it reads the query (a seccomp filter on Linux, a deny-default sandbox profile on macOS, with limits on processor time, memory, descriptors, core dumps and file size; `crates/una-sys/src/solver/`), so a bug of Z3's parser or engine reached by a hostile query lands in a process that holds nothing but its pipes. On Linux the filter refuses `open`, `openat` and `openat2` with `EACCES` and kills on the other dangerous families (ADR 0124 rule 7): the C library re-reads the processor count during a query (glibc 2.39, #1455), and with the error it takes its fallback, `sched_getaffinity`. Either way no file is opened after the filter, so the child reads only the descriptors it holds, its pipes. The confinement is `unsafe` code of `una-sys` (`solver/`, §3.3), and the call of Z3's front end, with the reclaiming of its arguments, is the two `unsafe` blocks of `crates/una-z3`, a crate of at most 150 lines: a bug there leaves the child less confined than stated, or Z3 called with arguments it does not expect. A proof needs the child's handshake, a normal exit with status 0 and `unsat`; a crash or a limit is `unknown`, never a proof, never cached. The proof cache's key covers the solver's build.

- **A bug can cause:** soundness. An encoding error, or a solver bug, that answers `unsat` for a false obligation proves a contract, a refinement or the absence of an overflow that does not hold. For a fixed-width integer, whose overflow is proven absent and not checked at run time (`spec/18 §3`), the run then computes a wrong value. Today it cannot access memory out of bounds through that, because index, length and handle checks always run. **That holds only while no such check is elided.** Once a run-time check is removed because the verifier proved it unneeded (#737, ADR 0112), the verifier and the solver guard memory safety for every elided bounds, handle or stack check: a false `unsat` behind an elided bounds check is an out-of-bounds access. ADR 0106's rule RB-3a, which its amendment of 2026-10-31 keeps for any release path, and ADR 0112 keep proof-based elision to checks whose failure stays a wrong value (§5).
- **Guards:**
  - an obligation that is not proven is an error (charter P8), so a timeout or an unknown never passes;
  - a `sat` answer is re-checked when it uses uninterpreted arithmetic (ADR 0053, ADR 0054), and a model that disagrees with real arithmetic is not a counterexample;
  - a malformed query is U8001, never a status (ADR 0033);
  - the verification tests and the `verification` conformance cases.
- **Formal coverage:** none. Refinement soundness (T5) is planned relative to the pinned solver, and is not started.
- **Open gaps:**
  - **No certificate for `unsat`.** A proven obligation is trusted as Z3 answers it. Proof certificates checked by a small kernel are on the backlog (#66).
  - The encoding is not modeled. A divergence between `spec/12 §4` and the encoder shows only through tests.

### 3.3 The native runtime

`una-rt` (about 6,000 lines) holds the values, tasks, host operations and the C ABI that generated code calls. `una-sys` (about 3,200 lines) holds the code with `unsafe` that the runtime and the interpreter share: the coroutines of the task runtime (stacks mapped with a guard page, and the switch between them), the handlers of SIGINT and SIGTERM, the write-readiness check, the `kqueue` or `epoll` instance of the reactor, the bindings of `serve:` grants, and, behind its feature `solver`, the solver child's confinement (§3.2).

- **A bug can cause:** memory safety, at the boundary with generated code, and in `una-sys`: a stack overrun past a guard page, a register corrupted by a switch, or a signal handler that is not async-signal-safe. Elsewhere, a wrong result.
- **Guards:**
  - `unsafe` is forbidden in the workspace (`unsafe_code = "forbid"`). Three crates set `unsafe_code = "deny"` instead, and only the modules below opt in with `#[allow(unsafe_code)]`, and the integration tests of `una-sys` (`crates/una-sys/tests/`: 30 `unsafe` blocks at commit `689d53a0`, 18 in `solver_confinement.rs`, 6 in `no_allocation.rs`, whose counting allocator is an `unsafe impl GlobalAlloc`, 3 in `wake_placement.rs`, and one each in `coroutine.rs`, `escalation.rs` and `poll.rs`), which build no artifact (ADR 0058 and its amendments by ADRs 0116, 0117 and 0124). Every `unsafe` block carries a `// SAFETY:` comment. The counts are those of commit `0516fba0`:

    | Module | `unsafe` blocks | Other `unsafe` items |
    | --- | --- | --- |
    | `crates/una-rt/src/ffi.rs` | 17 | 4 exported `unsafe extern "C"` functions (`una_rt_start`, `una_rt_int_literal`, `una_rt_text_literal`, `una_rt_closure`); the private `unsafe fn text`; one `unsafe extern "C"` block, which imports `signal` of the C library; and, in debug builds only, the `unsafe impl GlobalAlloc` of the allocator that counts the peak, with its 4 methods |
    | `crates/una-sys/src/coroutine.rs` | 18 | 4 `unsafe extern "C"` functions written with `naked_asm!`, a `switch` and a `trampoline` for each of AArch64 and x86-64, in Rust only; `unsafe impl Send for Stack`; and one `unsafe extern "C"` block, the sanitizer's fiber interface, in AddressSanitizer builds only |
    | `crates/una-sys/src/signals.rs` | 20 | one `unsafe fn` (`fcntl`) |
    | `crates/una-sys/src/server.rs` | 12 | |
    | `crates/una-sys/src/poll.rs` | 8 | |
    | `crates/una-sys/src/io.rs` | 2 | |
    | `crates/una-sys/src/solver/` (`sandbox.rs`, `spawn.rs`, `mod.rs`, `footprint.rs`, `seccomp.rs`, `limits.rs`, `descriptors.rs`) | 57 (25, 18, 4, 3, 3, 2, 2) | in `sandbox.rs`, one `unsafe extern "C"` block (`sandbox_init` and `sandbox_free_error` of macOS) and one `transmute`, of the symbol `sandbox_check_network` into its function type |
    | `crates/una-z3/src/lib.rs` | 2 | one `unsafe extern "C"` block, which declares the entry of Z3's front end (§3.2) |

    That is 136 `unsafe` blocks in 14 modules of 3 crates. Of the blocks of `ffi.rs`, 4 are in the debug-only allocator, 2 set the floating-point control register with `asm!`, one is built only with `--cfg una_fuzz`, and one is in the macro that wraps each kernel variant of the dense types after the processor's features are detected (ADR 0120 rule 56). The attention words of `una-sys` (`attention.rs`) use atomics and hold no `unsafe`;
  - two `transmute`s in `invoke`, one per arity, turn a closure's code address into a function pointer. They are the one place where a wrong code word becomes a call to an arbitrary address. `invoke` checks that the word is a closure of the right arity before them (#424), but the address itself is the one generated code passed to `una_rt_closure`;
  - handles are slot indices, not pointers, and the runtime's lookup refuses a word that is not a live handle (`crates/una-rt/src/values.rs`). A stale handle whose slot was reused names another live object: a wrong result, not a memory error. Handles carry no generation yet (ADR 0107 proposes one, §5);
  - the allocator `cap` enforces the memory budget (ADR 0061);
  - a test calls every entry point of the runtime's export table with words the generated code never passes (every tag pattern, freed and out-of-table handles, objects of the wrong kind, and fixed-seed pseudo-random words), and requires each call to return a word or count a fault, never to panic, with the runtime still usable after (#766). The same calls run again inside a started run with a memory budget, where a call may also end the run with U6003 or U8001, never on a signal; this phase found two divergences between the backends, fixed in #773 and #775. The host operations are left out, since their effects need a run's grants;
  - the native gate compares every runnable program of the repository's suites with the interpreter (`crates/una-cli/tests/native.rs`, `spec/16`).
- **Formal coverage:** none.
- **Open gaps:**
  - The `sanitize` release gate (#766, `scripts/sanitize.sh`), with a nightly Rust used only for checking (`scripts/check-toolchain.toml`):
    - AddressSanitizer: the unit tests of `una-rt` at their full sizes, the scenarios that run in a process of their own included, and `una-rt` built with it with the native equivalence test run against it, every runnable program; a canary fails the gate unless it is active and the linked runtime is the instrumented one. It instruments the runtime, its crate dependencies and the generic standard-library code compiled into them, under those programs. The precompiled standard library is not instrumented (only its libc calls are intercepted), and neither is the generated code.
    - Miri on the unit tests of `una-rt`, which reports undefined behavior in the Rust code they reach, `ffi.rs` included, with permissive provenance, since the runtime's handles are integers: a known weakening of its checks. Each allocation is slow under Miri, so tests that allocate much run smaller there, at sizes the gate pins by counting every mention of `miri` in `una-rt` (`scripts/sanitize.sh`, #778 and later): among them two deep values at depth 1,000 rather than 1,000,000, the copy between heaps of #775 at depth 1,000 rather than 200,000, 200 rounds of `find` rather than 10,000, the entry points with a pool of one word of each kind, the copies of ADR 0113, the integer digit cap, maps and chains of a few levels, three scaling tests, of the reactor's table, a chunked body and the sockets' gate, at a tenth to a hundredth of their sizes, a list one segment and one level deep rather than three segments, two tests of the debug credit of the quarantine, one at 70 and 60 objects rather than 70,000 and 60,000, which skip their checks of table sizes that hold only at the quarantine's full size, and the debug quarantine of freed slots at 64 rather than 65,536. Their full sizes run in the ordinary tests, which alone check that those walks use no recursion, since Miri emulates no native stack limit. Those skipped checks run in the ordinary tests and under AddressSanitizer, at full size; three other tests of the credit, which check only full-size tables, are ignored under Miri by name, so no test passes there while checking nothing. 121 tests are not run under Miri, a set the gate pins by name (`scripts/sanitize-miri-ignored.txt`): scenarios that run in a process of their own, tests that start such a process, and tests that start the scheduler's threads or the timer thread, map a task's stack, switch coroutines, or time the scheduler's turns on the real clock, which Miri cannot do or only simulates, a test that asks the allocator for more than it can give, which Miri reports as resource exhaustion rather than returning null, the three tests of the debug credit above, a timing test ignored in every build and run by hand, and a test that waits for a phase of the real clock within its millisecond, which Miri's simulated clock, moving in steps of 5,000 ns, never reads (its arithmetic runs under Miri in a test of its own), two tests that use the file system, which Miri's isolation refuses, and a timing test of the walk at `start`, which Miri ran for over 18 minutes even at a fiftieth of its size. Miri runs no test of `una-sys`, and cannot run its stack switch, which is assembly.
    - libFuzzer: the runtime's three targets of `fuzz/` (the crate also holds the targets of the linker, the package formats and the registry, and a canary), a crate outside the workspace with its own lock, under AddressSanitizer: `literal`, the two entry points that read bytes by pointer and length, on any bytes; `words`, sequences of calls on words the generated code never passes, outside a run, where every word a call returns can be an argument of the next: the 87 entry points of the export table but its 10 host effects (console, clock, environment, files, keys and HTTP, which need a run's grants), and 13 entry points outside it (reference counts, `push`, `enter`, `leave`, `budget`, `poll`, `stopped`, the operation and event state, and the status of `together`); and `json`, the runtime's JSON parser on any text, whose canonical text must parse back to itself and agree with the entry points. Each runs a fixed number of inputs from committed seeds with a fixed seed, and a canary target's planted crash must be found and minimized first. Not fuzzed: `una_rt_closure` and `una_rt_push_op`, which take the address of compiled code, `together` and `together for`, which run such code on tasks, `una_rt_start` and `una_rt_main_failed`, which start and end a run, the host effects, and any entry point inside a run. The fuzzed code is built with `--cfg una_fuzz`, which only adds the two hooks the targets call.
  - `una-sys` is reached by AddressSanitizer as a crate dependency of the instrumented runtime, with every coroutine switch announced through the sanitizer's fiber interface (`--cfg una_asan`). Neither Miri nor a fuzz target reaches its stack switch, its guard pages or its signal handlers, so their tests (`crates/una-sys/tests/`) and the native equivalence test are what exercise them.
  - The sanitizer gate runs on macOS only, where LeakSanitizer does not run: no leak is detected by it. The `words` target calls the entry points outside a run only, as the word tests do, and none of the targets reaches the host operations or the generated code.
  - (Closed by ADR 0124 step 2, #1207.) The build report did not record the runtime, although it is in the Trusted zone. A release `una` now carries the runtime built from its own commit and build, pinned by the digest its build checked, which `una build` checks again before each link (U8001 on a mismatch) and the report records as `native.runtime_sha256` (`spec/13 §6`). A development build reads the runtime from a file and records none.

### 3.4 Host capabilities and the prelude

The host operations (`Clock`, `Env`, `Files`, `Keys`, `Http`) have two implementations, one in the interpreter (`crates/una-interp/src/host.rs`) and one in the runtime (`crates/una-rt/src/host.rs`). `Http` uses `una-http` (about 1,100 lines) over `rustls` with the `ring` provider and `webpki-roots`, which are trusted (`docs/compiler/architecture.md`).

(Edition 0.4 preview, ADR 0123 step 3.) Before `main`, a run with `serve:` grants runs `una_http::serve::prepare` in both engines: it checks overlaps, raises the descriptor limit, opens each TLS key and certificate once and checks the open descriptor (owner, group and mode for the key), and binds one listening socket per grant through the OS bindings of `una-sys` (`server.rs`; its scope and cap are amended by a separate docs-only change). A bug there could accept a key file that others can read or write, or let another process share a listener. Nothing accepts on the listeners yet, and no TLS server is built until the decision on the provider (#1059).

(Edition 0.4 preview, ADR 0123 step 4.) The serve engine of `una-http` (`serve/thread.rs`, `run.rs`, `grant.rs`, `pressure.rs`, `peer.rs`, `server.rs`, about 3,000 lines of safe Rust, no `unsafe`) is the server's trusted code beyond the reader and the writer: it accepts, places connections by a keyed hash, applies every limit and share, times each connection and decides what the host answers on its own. A bug there could let a peer hold more connections, bytes or time than the grant allows (a denial of service, bounded by the descriptors of the run), answer a request twice or never, or write one connection's reply to another's; a reply is cut into segments owned by one connection's outbox, and a connection is found only by its slot and generation, so a message for a slot reused since is dropped. The key of the placement comes from the operating system's random source (U6009 when it gives none) and is shown nowhere. The poller and the wake pair use the `una-sys` bindings that the reactor already uses; this slice adds no system call.

(Edition 0.4 preview, ADR 0123 step 6.) The driver of a `serve` section is trusted engine code in both engines: `machine/driver.rs` of `una-interp`, and in native code `driver.rs` of `una-rt` (about 160 lines of safe Rust) with the `answer` lambda that `una-codegen` emits (`serve.rs`). It runs the program of `spec/31 §7` rule 4: it turns a failure of `handle` into `500` with an empty body, which is the guarantee that a failure's payload never reaches a peer, moves each exchange's reply right to its task, and refuses to start without a `serve:` grant (rule 1) or with a `within` (rule 3 item 7). A bug there could send a failure's payload, answer a request twice or never, or run the driver without the deadline its section names. The scripted cases `tests/serve_runs/serve_section_*` compare its bytes and traces in both engines with the program of rule 4 written out, and check that no failure payload is sent.

- **A bug can cause:** soundness through labels: a failure or an outcome that depends on internal data but is labeled public. Four advisories were of this kind (UNA-SA-003, 008, 009 and 010). Also a wrong result where the two implementations differ.
- **Guards:**
  - the host table, which states each operation's labels and failures, and the conformance cases on it;
  - the differential native gate, which compares the two implementations on the runnable programs;
  - the release-mode TLS test, which shows that a release build never trusts the test authority (ADR 0074).
- **Formal coverage:** the files and HTTP host are modeled as shared state (milestone M5), under stated premises about the host (H1 to H4 in the status document). The premises are assumptions, not checked properties of the implementation.
- **Open gaps:** each operation exists twice, and only the runnable programs compare them; the host premises are not tested against the implementation.

### 3.5 Native codegen and the linker

`una-codegen` (about 4,500 lines) lowers Core to Cranelift and emits an object file; `una build` links it with `libuna_rt.a` through the system `cc` (`crates/una-cli/src/build.rs`). (ADR 0124 step 2, #1207.) The runtime of a release `una` is the one built into it, pinned by its digest and recorded by the report (§3.3); no variable or file replaces it, so `UNA_RT_LIB` cannot put code into every executable. Until step 3, `una build` writes it into the link's private directory (mode 0700, created for the build; the file new, with mode 0600) for `cc` to read, and removes it after the link. (ADR 0124 step 3, #1208.) On `aarch64-apple-darwin`, `una build` links with `una-link`, inside `una`, in safe Rust: it reads the program's object and the embedded runtime in place, writes the executable alone, runs no other program, and reads every output back with its verifier (`spec/16 §6`) before it writes it. The linker is in the trusted base: a bug in it can make an executable compute a wrong result, or drop a hardening that the verifier does not check.

- **A bug can cause:** a wrong result. The generated code has no `unsafe` of its own and reaches objects only through the runtime's entry points, which refuse a word that is not a live handle (§3.3).
- **Guards:** the native gate, the `unsupported` list that names every runnable program native does not compile yet (it must be exact), and the reproducible and determinism gates. (ADR 0124 step 3.) On macOS: the comparison of every runnable program linked by `una-link` and by `cc` (`crates/una-cli/tests/native.rs`), a Rust program that unwinds linked by both (`crates/una-link/tests/oracle.rs`), the verifier on every link and its canaries, and `codesign --verify --strict` in the tests.
- **Formal coverage:** none.
- **Open gaps:**
  - A program outside the runnable corpus is compared with nothing.
  - On Linux, the system `cc` and linker are trusted, their version is neither pinned nor recorded in the build report. They stay so until the internal linker of ADR 0124 step 4. Between the write of the runtime into the private directory and the link, a process of the same user could replace it there, as it could replace `cc` itself. On macOS this gap is closed by step 3.
  - libSystem's export list comes from the macOS 12.1 SDK; that the libSystem of macOS 13, the oldest system the executables name, exports each of its symbols is assumed, not yet checked: the `macos-oldest` gate (ADR 0124 rule 31), which runs the executables on macOS 13, does not exist yet.
  - `una-link`'s Mach-O link has no fuzzing yet and no oracle test per relocation type against Apple's `ld` (ADR 0124 rule 33, #1208); a relocation of a supported type that it applies wrongly in a way neither comparison exercises is not caught. Its ELF reader and relocation engine for Linux (step 4b, #1209), which no `una build` reaches yet, have the `elf_link` fuzz target and an oracle per relocation type against `ld.lld` (every `cargo test` on macOS) and GNU `ld` (`scripts/link-oracle-elf.sh`, release-time).

### 3.6 The reference interpreter

`una-interp` (about 4,000 lines) implements the Una Abstract Machine over Core IR (`spec/11`). It is the meaning that every backend must refine (ADR 0055).

- **A bug can cause:** a wrong result, and every backend compared with it inherits the wrong expectation.
- **Guards:** the `runtime` conformance cases, and the expected outputs of the examples.
- **Formal coverage:** the Lean model has its own semantics of F1, but it is not compared with the interpreter.
- **Open gap:** a disagreement between the interpreter and the model's semantics is not tested.

### 3.7 Elaboration and the bridge to the formal model

The theorems hold for the Core that the Lean importer reads from `una.core/1`. Elaboration from the surface language to Core, the importer (`formal/UnaFormal/F1/Import.lean`) and the Lean kernel, at the version that `formal/lean-toolchain` pins, are trusted (formal status document).

- **A bug can cause:** soundness: a program whose Core is proven while its source means something else.
- **Guards:** the identity runs of the export (#397, #407), and the conformance suite, which checks the source. Elaboration fails closed (#1050): a final cross-check requires every declaration that type-checked to be in Core, with every contract of the standard library, host capability and prelude kind that Core carries, and the consistency check of `spec/10 §2` requires each Core type to keep its checked components (ADR 0038 D1). A gap in either is U8001 and rejects the package, never a declaration accepted without its obligations. A unit test injects an elaboration failure through a hook compiled only in tests.
- **Open gap:** elaboration is not modeled. The cross-check sees a declaration that is missing, not one present in Core with a wrong meaning.

### 3.8 The Rust toolchain and the crate dependencies

Every component is compiled by `rustc` at the version that `rust-toolchain.toml` pins (1.98.1), from crates of crates.io, among them `cranelift`, `rustls` with `ring` and `webpki-roots`, at the versions that `Cargo.lock` records.

- **A bug can cause:** whatever the crate or compiler can cause, in every artifact: a soundness defect, a wrong result, memory unsafety in a crate's own `unsafe`, or a compromised dependency (supply chain).
- **Guards:** the pinned toolchain; `Cargo.lock`, which `scripts/local-ci.sh` enforces with `--locked`; the reproducible gate, which shows that an archive is what its source and lock determine; the `deps` release gate (#770, `docs/release-gates.md`), which checks `Cargo.lock` against the RustSec advisory database fetched for each run (its commit in the record), with no ignored advisory, and checks licenses, wildcard requirements and sources, crates.io only, with `cargo-deny` at a pinned version; and the supply-chain review record `supply-chain/crates.tsv`, which must list every crates.io package by name, version and checksum, so that a new or moved dependency fails `scripts/local-ci.sh` until a reviewed change adds it. Its first run found four advisories against `rustls` 0.23.45, fixed by an update (S-26, #779). A second, nightly toolchain is pinned in `scripts/check-toolchain.toml` for the `sanitize` gate only: it checks, and builds no artifact.
- **Open gaps:** the record's 158 crates at the gate's introduction are a baseline, not a review of each; a compromised version published before that baseline, and not yet known to the advisory database, would pass. A per-crate audit record (such as `cargo-vet`) would close it.

**`getrandom` (ADR 0119 rule 9).** Keyed hashing reads its process key, 128 bits, from the operating system's cryptographic random source through `getrandom` 0.4.3, the one crate `una-hash` depends on. Its own `unsafe` code, which calls the system, puts it in this zone.

- **A bug can cause:** a key that is not random, or that an attacker can learn. Then the attacker can choose keys that collide in one table, and each operation of that table takes time linear in its size instead of constant expected time: a denial of service, not a leak, since no listing, trace or message depends on a hash.
- **Guards:**
  - the crate's source on each target, reviewed at 0.4.3: on Linux with glibc, the `getrandom` system call with no flags, which blocks until the kernel's pool is seeded, with the crate's fallback where the call is missing or refused (it polls `/dev/random`, then reads `/dev/urandom`); on macOS, `getentropy`; on Windows, `ProcessPrng`;
  - no fallback key: when the source gives nothing, the run aborts with U6009 before any effect;
  - native executables link the same crate through `una-rt` (#981): an executable whose compiled code makes a hash table reads the key before `main`, as `una build` records in its embedded description; a table the build did not foresee, which only a defect of that record makes, stops the run with an internal fault, U8001, at the table, as the interpreter does when its own analysis missed a table: no key is ever read late, and both engines fail the same way;
  - the crate's source can be switched at compile time with `--cfg getrandom_backend=...`; `scripts/release.sh` refuses build flags, in the environment or a cargo configuration file, that set it;
  - the process key hashes only table keys, two SipHash-2-4 results per table, so one table's key reveals nothing of another's;
  - the test-only feature of `una-hash` (a fixed key, a probe counter, a constant hash) is not in any shipped artifact: `scripts/check-release.sh` looks for its marker in `una` and `libuna_rt.a`.
- **Open gaps:** the crate's `unsafe` code is trusted as published at 0.4.3, not audited line by line here; a sandbox that denies the random source turns every run that can make a hash table into U6009, by design.

### 3.9 Release scripts and archives

`scripts/local-release.sh` builds the archives from a clean worktree of the tagged commit, and `scripts/release-gates.sh` runs every gate on that commit in a fresh clone (`docs/release-gates.md`).

- **A bug can cause:** an archive that is not what its source determines, or one that reveals the build environment. Two Low advisories were of the second kind (UNA-SA-007, build paths in executables, and UNA-SA-014, account names in archives).
- **Guards:** the reproducible gate rebuilds the archives and compares their digests; every archive has a SHA-256 file; the gate summary is checked against a privacy pattern before it can be published.
- **Open gaps:** no signature or provenance statement accompanies an archive, so a downloader can check a digest but not who built it from which commit.

### 3.10 The proof cache

The cache answers a query that was solved before. Since ADR 0064, each entry carries an HMAC-SHA-256 tag under the user's key, and an entry whose tag fails is solved again.

- **A bug can cause:** soundness, if a forged entry were taken as proven.
- **Guards:** the tag, with a test against RFC 4231; no key means no cache. (#1540.) When `.una`, `.una/cache` or `.una/cache/proofs` of the package is a symbolic link, wherever it leads and even dangling, the cache is off for the run, checked once with `symlink_metadata` when the cache is built, so a link committed in a repository makes `una` neither read nor write through it. A process of the same user that swaps one of them for a link later in the run is not covered: reads then follow the swapped link, but only an entry tagged under the user's key for that exact query is an answer, so the residual cannot make a proof; stores stay bounded by `create_dir_inside`, which refuses a link leading outside the package but follows one inside it, so a store may land in a directory of the package. The descriptor-relative design of `docs/plan/proof-cache-eviction.md` section 6.4 closes that case.
- **Open gap:** the key file is in the Trusted zone; anyone who can write it can forge entries.

### 3.11 Package integrity and the registry client

From edition `0.4`, a package may need other packages (ADR 0122, `spec/30`). Itá, the package manager inside `una`, reads `ita.una`, `ita.lock` and `itaty.una` by closed grammars, and, as it lands, fetches archives, checks their digests, resolves versions and verifies the registry's signatures, log proofs and witnesses. No code of a package runs when it is fetched, resolved, checked or built, and Itá starts no other program.

- **A bug can cause:** a program built from bytes other than those its lock pins (supply chain); a dependency that receives authority or trust that the root did not write (soundness); a store or vendor directory written outside its place (path traversal through an archive).
- **What is in the base:** the parsers of the three files; the archive reader and the content digest (`una-project` `content`); the reading and writing of package files with no link followed (`tree`); Itaoca (`itaoca`); the provenance reader and its offline verification (`provenance`), over the verification of Ed25519 signatures, roots, checkpoints, cosignatures and log proofs (`tlog`); and the verified load and vendoring of registry packages (`vendor`). To come: the resolver's network side, the verification of name maps and owners' key chains, the registry's built-in root metadata, and the HTTPS client of `una-http` as `una ita` uses it. Each joins with the security review of ADR 0121 rule 2 (b).
- **Guards:** the grammars are closed and bounded (1 MiB for a manifest, 16 MiB for a lock), with no expressions, interpolation, includes or environment; a deterministic robustness test of the readers on mutated files, the archive and provenance readers included, each of which accepts only its one encoding; `una.toml` and `ita.una` never both; the lock is written only by `una ita` and `una migrate`, through a temporary file and a rename.
  - **Every load re-verifies** (`spec/30 §9` rules 6, 7 and 9): a registry package is read from the vendor directory, else from Itaoca, and its digest is computed from the bytes read and compared with the lock's; its stored provenance is verified against the lock: the source's root from the pin in `ita.una`, the checkpoint of the lock's resolution point with its log signature and the witnesses' threshold, the statement's digest, `ita.una` digest and signature by the key the lock names, and its inclusion proof. A vendored copy that fails is U7010 and is never replaced by Itaoca's. A package in neither place is U7011. A package of `itaty`, whose root is not in this release, never verifies, so `una ita vendor` refuses it; loading does not check it, since its need is refused (U7008) and it never loads.
  - **Verified bytes only, no link followed** (`tree`): below a base the user chose (the package's root, or Itaoca's root, which itself must not be a link), canonicalized once, every component is checked to be a directory and not a link. The package is listed by path: only directories and regular files with one link are listed; a symbolic or hard link, a device, a FIFO or a socket refuses the package, as does every path rule 27 refuses (`..`, absolute, hidden, a device name of Windows, names equal ignoring case, a file beside a directory of its name) and every bound (10,000 files, 256 MiB, 20,000 entries listed, 32 levels), each before any byte is read. Each listed file is then read once into memory through a descriptor opened with `O_NOFOLLOW`, and on macOS `O_NOFOLLOW_ANY`, and compared by device and inode with the entry listed; the content digest is computed over those bytes, and only when it is the expected one are the files handed out, as a `VerifiedTree`, the only way the crate gives the contents of a stored or vendored package. The provenance check, the copy into the vendor directory and every later step use those bytes, and no package file is opened by its path again, so an entry swapped while the package is read can at most make the load fail. Writing creates a fresh directory with a name of its own, which `mkdir` refuses if it exists, with mode 0700; each directory below it the same way and each file with `O_CREAT | O_EXCL | O_NOFOLLOW`; each file's permissions are set through its descriptor, each file and directory is synced, and the directory (or, for a provenance, the one file) is renamed into place. Nothing is chmod-ed by path. The fresh directory must still be the one created, by the identity taken from its descriptor, before each file and before the rename, and a failed write removes it only then, and otherwise leaves it and says so. The flag values are this crate's own constants for macOS and Linux on x86-64 and AArch64, since `una-project` has no `unsafe` and does not depend on `libc`; a test opens a link with them and must be refused, so a wrong value fails the tests, and on any other platform every read and write is refused.
  - **Only `una ita` may reach the network** (rule 31): `una-project` names no networking API and does not depend on `una-http`, and the command-line crate names the HTTP client only where it configures a program's `Http` capability; a test reads the sources and fails on any other use. No command of this release fetches.
- **Ed25519 is pure Rust.** The registry client verifies signatures with `ed25519-dalek` and `curve25519-dalek`, which compile no C: their one build script chooses a backend from the compiler's version. `ring`, which carries C and assembly, stays only where `rustls` brings it, and is not a dependency of the client: Una admits no foreign code, and the client must not widen it. Verification is `verify_strict`, behind the client's own checks that keys and `R` are canonical encodings of points not of small order and that `S` is below the group order, so the rule is one for every implementation; RFC 8032's vectors and the malleability and small-order cases are tests. The crates added are listed in `supply-chain/crates.tsv`.
- **The registry service** (`una-itaty`, ADR 0122 S8) is not in a client's trusted base: a client verifies everything it serves. It is in the base of the registry's promises: it verifies every submission before logging it (signatures by keys valid at that point, each name's chain, rules 26, 37 and 43 to 45, the statement against the archive), bounds every request before reading it, and stops logging after a failed write. It adds no external crate. Open: the offline root ceremony, recovery and transfers, notifications, its own security review, and fuzz targets for its HTTP head parser and entry readers.
- **Open gaps:** the readers' libFuzzer targets (`provenance`, `archive`, `ita_lock`) run with placeholder counts and coverage floors until measured; dependencies other than path ones are refused until they are loaded and checked as one program with the root. The standard library opens files by path, not relative to a directory descriptor (`openat`). Reading does not depend on it: a swap can change only the bytes read, which then fail the digest. Writing does in one case: on Linux, which has no `O_NOFOLLOW_ANY`, someone who can rename entries of the directory a fresh one is created in (`vendor/ita/<source>/`, or a directory of Itaoca) can swap the fresh directory's path for a link between two of its checks, and the files written in that window, verified package bytes, are created where the link points, with this process's rights; the swap is detected before the rename, so nothing is moved into place and the write fails. A component above a base the user chose is resolved once, and its later swap is the same case. The provenance does not yet carry the owner's key chain and its map proof (rules 36.1 and 36.3) or the per-name state at the resolution point: they MUST be verified before a registry package is mounted in a program, which no release does yet, and until then `una ita verify` reports a package whose copies match the lock as not verified (U7013). The commands that neither check nor build (`una core`, `una fmt`, `una fix`, `una trace`, `una contract`, `una ita tree`) look for registry packages in the vendor directory only.

**What a dependency can do, and what stops it** (ADR 0122, Security):

| Threat | Control |
| --- | --- |
| Code that runs at install or build | None exists: no scripts, hooks, build programs or macros. |
| A dependency that reaches the network, files or keys | It holds no capability unless a call grants it with `with`, within the ceiling the calling package writes (U3020, U3021); only the root is granted host capabilities. |
| An agent that widens a ceiling to make a check pass | The lock records the consented ceilings; a wider `may` line is U7009 until `--accept-authority <package>` records it, visible in the lock's diff. |
| A dependency that declassifies the program's data | Its policies are in trusted modules, which need a trust line naming its identity and module (U7012); only that module is exempt from U3024. |
| A dependency that brings foreign code | None is admitted: a package holds only Una sources, and `ita.una` has no foreign section or grant (U7008). |
| Trust consented for one package used by another | Trust lines bind source, name and major, and the lock pins the content digest of each package whose trust was consented. |
| Proofs the publisher fakes | None is read: the root proves everything. |
| Typosquatting | Unscoped names are Itaúna's; owner names are unique by skeleton and reviewed near popular owners; reserved names are refused as local names too. |
| Dependency confusion | One source per need, no fallback; owners bound to the source that serves them; a local package with a registered name only with `accept name`; workspace members only by `from workspace`. |
| A dependency that adds a source or a local path | Only the root and `itaty.una` name sources and paths. |
| A compromised account | Publishing needs the owner's keys; a recovery is pending seven days of witness time, and any current key cancels it. |
| A stolen publisher key | Every release is public in the log and in the name's chain; minimal version selection never takes a release no need asks for; every selection waits the cooldown; authority growth in a minor release is refused. |
| A malicious update of an honest package | `una ita update` prints the source, authority and trust change and refuses a ceiling, trust or key change without an explicit flag. |
| A stolen security key | One key can hold a release back, never hurry one in. |
| A compromised registry or mirror | It cannot forge a signature, fork the log or hide an entry of a name without the witnesses; it cannot change a locked package. |
| A freeze or rollback attack | Witness co-signatures less than 24 hours old for resolution and audit; checkpoints never move backwards. |
| Censorship of a yank or key event | A signed promise to log within an hour. |
| A root key compromise | Three of five offline keys are needed. |
| Denial of service through the graph | Bounds on releases visited, needs, documents, bytes and time; no self-need. |
| A malformed archive | The closed layout and reader: no links, no modes, no compression, sorted listing, exact lengths, read once; descriptors with `O_NOFOLLOW`. |
| A store or vendor directory tampered with | Every load re-hashes, and registry packages are re-verified against their stored statements and proofs (U7010). |
| A poisoned proof cache | Entries are authenticated with the user's own key, under a domain-tagged key (`una-proof-cache/2`, in this release). |

## 5. How the accepted decisions move it

Five decisions of the performance track are accepted. Only ADR 0109's profiles are implemented (edition `0.4`); ADRs 0107, 0108 and 0112 wait for their implementation (#736, #751, #737), and ADR 0106's release path for its design (#1305). Each changes the base as follows once it is implemented.

- **ADR 0106, an optimized release backend (#757).** As first accepted, it emitted C and compiled it with the system C compiler, adding both to the base for release builds. Its amendment of 2026-10-31 (#1099) withdraws that route: no C compiler goes into `una` (ADR 0124), and release builds become Una's own optimizing code generation over Core IR, designed in #1305.
  - What survives: no optimization removes or weakens a check outside ADR 0112, a wrong proof stays a wrong value (RB-3a, RB-7), equivalence of the interpreter, Cranelift and release executables, a `check-survival` gate with canaries, and reproducible release builds.
  - What it adds to the base is the release code generator itself, inside `una`, which the design record states (requirement RP-10 of the amendment).
- **ADR 0107, data layout for the native backends (#749).** Generated code will read the runtime's slot table and objects directly, a new memory interface outside `una-rt`.
  - Handles gain a generation, and the layout is checked on each read, so a stale or corrupt handle fails a check or reads a live object of the expected layout. `unsafe` stays in `ffi.rs`.
  - It requires assertions of sizes and offsets on the runtime's side and in the code generator, tested against each other (requirement RP-7 of ADR 0106's amendment of 2026-10-31), and sanitizer cases for table growth, moved storage and reused slots.
- **ADR 0108, small records off the heap (#754).** It adds no `unsafe` and no new trusted tool. It moves correctness into the lowering (ownership of the unboxed values and their companions), guarded by equivalence and allocation tests, and states a stack-depth regression risk.
- **ADR 0112, eliding the run-time checks the verifier proves (#771).** It decides how elision works: only the `Int` promotion path and fixed-width overflow checks may be elided, on a proof, in release builds; memory, resource, cancellation and division checks always stay. For exactly the checks it elides, the verifier, the query generator, the pinned solver and the proof cache join the trusted base, and the build report lists them in `native.elided`. `una build --release --no-elision` builds without them, and takes them out of the base again. A wrong proof then costs a wrong value, never an access out of bounds. A certificate (#66) could later unlock bounds checks only (§9 of the ADR). Its amendment of 2026-10-31 (#1309) restates where elision happens and how the present checks are read back for Una's own release path, with the same rules on which checks may be elided.
- **ADR 0109, profiles `app` and `systems` (#762), implemented in edition `0.4`.** It adds nothing to the base. In `systems`, every `Int` operation gets an overflow obligation, so more results rest on the verifier (§3.2). Combined with the elision of proven checks (#737), a false proof of an overflow obligation would give a wrong value where `app` gives the right one, and, under ADR 0106's rule RB-7 and its amendment's requirement RP-5, no undefined behavior. That holds for overflow checks, whose failure is a wrong value. If elision also removes a bounds, handle or stack check, a false proof there is a memory-safety defect (§3.2), so elision must be restricted to checks whose failure stays a wrong value. ADR 0106 states this as its rule RB-3a, kept by its amendment of 2026-10-31: only such checks may be elided on a proof. A checked certificate of the `unsat` (#66) could later unlock bounds checks only; handle, stack and resource checks are never elided, even with a certificate (ADR 0112 §9).

No foreign code is to come: Una admits none, in any form (ADR 0124, Questions 1 and 2; ADR 0120 rule 67.3), so the foreign-function boundary that issues #23 and #33 once planned is not part of any decision. The largest addition to come is the release code generator, inside `una` (ADR 0106's amendment, requirement RP-10).

## 6. Open gaps, ranked

1. **Memory-safety tooling on the runtime boundary is partial** (§3.3), #766. The entry points are called with foreign words on every change, and the `sanitize` gate runs AddressSanitizer over the native equivalence test and Miri over the runtime's unit tests. It also fuzzes the literals, the entry points outside a run and the JSON parser. What remains: the gate on Linux, with leak detection, which macOS lacks (#802); the stack switch, guard pages and signal handlers of `una-sys`, which Miri cannot run and no fuzz target reaches; the entry points fuzzed inside a run, the tests that start a process of their own, which Miri cannot run, and the generated code, which no sanitizer instruments (the C backend that ADR 0106 proposed for UndefinedBehaviorSanitizer is withdrawn by its amendment of 2026-10-31; the evidence for the release path is #1307). This rank reflects the class, not the history: no memory-safety defect is known.
2. **Capability confinement unproven, and the re-check partial** (§3.1), #768. Milestone M7 of the formal track, and widening what the re-check reads.
3. **Proven obligations trusted without certificate** (§3.2), #66. Today a false proof gives a wrong value. **It becomes a memory-safety gap the day a bounds, handle or stack check is elided on a proof** (#737), unless elision is restricted to checks whose failure stays a wrong value, such as overflow, or, for bounds checks only, a checked certificate. ADR 0106 (RB-3a, kept by its amendment of 2026-10-31) and ADR 0112 state that restriction (RB-3a, and ADR 0112 §2 and §9): handle, stack and resource checks are never elided. Refinement soundness relative to the solver (T5) is not started.
4. **The dependencies' review record starts from an unreviewed baseline** (§3.8). The `deps` gate (#770) now checks `Cargo.lock` against the RustSec database, licenses and sources, and fails on any crate the record does not list; the record's first 158 crates were taken as they were, not audited one by one.
5. **The adversarial generators gate releases only in part** (`docs/plan/security-hunt.md`), #782. The `hunt` release gate (#767) runs a fixed, seeded set of generated programs through the must-reject and must-keep drivers, a two-run oracle and the comparison with the formal model's re-check (#791), and fails closed, with canaries that show it can see a fault. It runs on macOS only, where its sandbox exists. The oracle varies secret literals of the source, runs the interpreter, and natively a stratified sample of its programs (#792), and observes at `public` and `internal`: host inputs and the files a program writes stay campaign work. Its programs of `together` (#807) are compared, but most of what a secret decides there is redacted in the run document, so they are not live until an unredacted runner (#794). Since S-45 (#1552, `spec/11 §5`) its observation at `public` also sees the outcome of every operation whose decision, failure type or result is labeled above `public` as `{"kind":"redacted","level":...}`, so it sees fewer differences there: whether a request or a read failed, and how, is not in the run document. Its readers of outcome kinds must accept the kind `redacted`.
6. **The build report's `tcb` section is incomplete**, #769. It omits the runtime, the codegen, the linker and its version, and the TLS stack.
7. **The system `cc` and linker are unpinned and unrecorded** (§3.5). ADR 0124's own linker removes them (#1104): on macOS since step 3 (#1208), on Linux with step 4; release builds use no C compiler (ADR 0106, amendment of 2026-10-31).
8. **Host premises and the two host implementations** (§3.4). Testing the premises of the model against the implementations, and comparing the two implementations beyond the runnable programs.
9. **No provenance for archives** (§3.9). A signature, or a provenance statement that ties each archive to its commit and its gate record. The release statements of ADR 0122 (rule 37: a signed note, logged in a witnessed transparency log, naming the archive's digest) are the pattern a later record can reuse for `una`'s own releases.
10. **Elaboration and the interpreter are not related to the model** (§3.6, §3.7).

This document is revised when a component enters or leaves the base, when a gap closes, and before any decision that adds foreign code.
