# ADR 0122 amendment draft: `una ita lock --check` and the root-version floor (follow-ups of amendment 7c)

Status: Proposed (draft for the project's decision; it is appended to `docs/adr/0122-ita-packages-and-the-registry.md` only once accepted, with the date of its acceptance). Card #1538, findings L1 and L3 of the adversarial review of PR #1537 (card #1529). Nothing here is implemented: PR for #1538 implements L2 (the same-size checkpoint recorded as evidence, which `spec/30 §11` rule 9 already requires) and leaves L1 and L3 to this decision, since both change text of `spec/30` that states the accepted amendment of 2026-11-03.

## L1. `una ita lock --check` does not see a cut of the vendored root chain

**Problem.** An attacker who edits the vendored package, its provenance and the lock drops root version 2 and the `latest` block from the vendored provenance and lowers the lock's `last root 2` to `last root 1`. The lock's point names root 1, which is now the provenance's last stored version, so the witnesses that root 2 retired count as current ones. `una ita lock --check` reads the registry at the lock's point, walks the chain served up to version 2, and keeps the recorded `last root 1`, since that chain holds version 1 with its digest (`spec/30 §4`), so the regenerated lock equals the edited one and the check passes. The cut is caught only by the root-version floor that the same command stores (`registry/<id>/root-version`, `spec/30 §14`, Floors). When that store fails, a note says so and the command succeeds; on a machine that starts with an empty Itaoca, such as a CI run, the following offline `una check` then accepts the truncated chain (amendment 7c, item 5).

**Why the change did not decide it in code.** Two normative texts settle the current behavior, and both state the accepted amendment:
- `spec/30 §14`, Floors: "a floor that cannot be stored, or a lock that cannot be had in time, is a note that says so, and never fails a place or a command". Making a failed store an error contradicts it.
- `spec/30 §9` rule 7, Trust on first use, and amendment 7c, item 5: "The online commands do not detect such a cut in the vendored file". Making `--check` detect it changes that sentence.

**Proposed decision (option A, recommended).** `una ita lock --check`, with and without `--fresh`, verifies the provenance of each registry package of the lock, the vendored copy when the vendor directory holds the package and otherwise Itaoca's, as the offline load does (`spec/30 §9` rule 7), with the root-version floor taken as the larger of the floor Itaoca stores and the last root version of the chain the command walked at the lock's point: the version it accepted, whether or not storing it as the floor succeeded. A provenance whose chain ends below that version is refused (U7010) with the offline load's message: its root chain is older than the root version this machine has accepted, lock again at a fresh resolution point, never that the log forked. Since it verifies as the offline load does, it reports that load's other results too: a provenance whose checkpoint carries a retired witness's cosignature without the proof, or a floor that exists and cannot be read, is unavailable (U7013), and any other provenance that does not verify is refused (U7010). A package that neither place holds is not checked here; that is `una check`'s U7011. The storing of the floors is unchanged, a note on failure.

- **Effect.** `--check` no longer depends on the floor store: the scenario above fails `--check` itself, with or without a writable Itaoca, whenever the place it reads serves the later root version.
- **Reach.** The check is relative to the place read. A place that also hides `root/2` (the first place of a source serves `root/*` and `checkpoint`) makes the walked chain end at version 1; the lock's point names version 1, so no prefix proof runs, and on a machine with no stored floor option A sees nothing. That is the residual of amendment 7c, item 5 (trust on first use), now relative to the place read, and it is unchanged for an offline-only run, such as a CI job that never runs an online command.
- **Fail-safe cost.** After an honest rotation, a lock whose provenance was written before the rotation (its chain ends at the older version) fails `--check` with "lock again". The same lock already fails `una check` on every machine that stored the floor, and `--check` stores it, so `--check` now says before `una check` what `una check` would say after it. The only repair is to lock again at a fresh resolution point: a stored provenance is never replaced (`spec/30 §9` rule 5), and `una ita vendor` takes Itaoca's copy, which for the same point is the old one.
- **Cost.** One provenance verification per registry package, O(R + W + log L) each (`spec/30 §9` rule 7), and no read beyond what `--check` reads now.

Drafted spec sentences, applied only with the amendment:
- `spec/30 §4`, end of the `last root` bullet: "`una ita lock --check` also verifies each registry package's provenance, vendored or in Itaoca, as §9 rule 7 does, against a root-version floor of at least the last version of the chain it walks, whether or not that floor is stored: a provenance whose chain ends below it is refused (U7010)."
- `spec/30 §4`, the paragraph after the grammar: "`una ita lock --check` writes nothing, and reports where the lock is missing or not the one `una ita lock` writes (U7009), and a registry package whose provenance ends below the root version it accepted (U7010)."
- `spec/30 §9` rule 7, Trust on first use, replacing its last sentence: "`una ita lock --check` refuses such a cut against the last root version that the chain it reads at the lock's point holds, whether or not it stores the floor (§4); `una ita fetch` reads the registry and stores the floor (§14), and the next offline load refuses a provenance below it."

**Options rejected.**
- **B. A floor that cannot be stored fails `--check`.** It reverses `spec/30 §14` for one command, fails a check on a read-only Itaoca for a reason that is not the lock's, and still lets the cut pass wherever the store works but the next offline load runs on another machine.
- **C. A note in `--check` when the recorded `last root` is below the walked chain's last version.** It says what it saw, but does not fail closed, and it also fires on every honest lock after a rotation.
- **D. `--check` regenerates `last root` from the walked chain.** It fails every lock after a rotation, and it checks the lock line rather than the provenance the load trusts.

## L3. The root-version floor binds a version number, not a digest

**Problem.** Itaoca stores the floor as the version alone (`<n>` and a line feed, `spec/30 §14`, Floors; `Itaoca::store_root_version`). The offline load compares the provenance chain's last version with it (`provenance::verify`, `Floor::At`), so a vendored chain that reaches the floor's version through another root document, validly signed, passes. Making two root documents of one version needs a threshold of the root keys of the version before it, outside the threat model of amendment 7c (root keys honest); online, the client compares the digests of the chain it walks. The stored floor carries no digest, so there is nothing to compare today; no code changed.

**Proposed decision (optional hardening, low priority).** Store the floor as `<n> sha256:<hex>`, the version and the digest of that root metadata, still replaced only by a higher version. The offline load and `una ita unbundle` refuse (U7010) a chain whose version `n` has another digest, a fork of the root chain; a floor of the earlier form, the version alone, keeps the comparison by version. A client that walks a chain whose version `n` has another digest than the stored one refuses it (U7010) as a fork. Cost: O(1) more per load. Until decided, the residual stays as the review of #1537 recorded it: a fork of the root chain at or above the floor needs a threshold of root keys.

## Note: a re-sign under a new root looks like an equivocation (pre-existing, card #1561)

The PR for #1538 records a latest checkpoint of the lock's point's size that names another root version as evidence against the registry, as `spec/30 §11` rule 9 already required. `spec/30 §16` rule 9 lets the registry service sign a size again after a crash ("one signed again after a crash is the same"), but a checkpoint's text includes `ita-root <n>`, which is not a function of the entries: a service that rotates its root and then signs the current size again would produce exactly that pair, from an honest registry. §16 rule 5 ("after each entry") implies an honest service never does it, so the attribution is consistent with the spec, but §16 should say so in one sentence: a rotation takes effect from the checkpoint of the next entry, and a size signed again is signed under the root version it was first signed under.
