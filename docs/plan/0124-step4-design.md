# ADR 0124 step 4: the internal linker, Linux x86-64 and arm64 (design note)

- Issue: #1209 (part of #891 and of #1104; ADR 0124 rules 12, 16, 21, 24, 25, 29, 31, 33, 34, Implementation plan step 4, under Question 2 (a) as decided on 2026-10-27)
- Base: step 3 (#1208, `docs/plan/0124-step3-design.md`): the crate `una-link` with its readers, resolution, dead-code removal, relocation and bounds rules, verifier, oracle tests and fuzzing; step 2's embedded runtime and symbol index. Probe P2 (#1204) decides two points below before this step ships (rule 25).
- Scope: no construct of the language changes. On Linux, `una build` stops running `cc` and writes a static-pie ELF executable; `una` itself stays a glibc executable (rule 1). The runtime and Cranelift are retargeted to the musl triple; `una.build/1`'s `target` names it.

This note fixes how step 4 is built, and lists the decisions it takes where the record leaves a choice. Each decision takes the most secure option the record allows. What P2 decides is marked as such.

## 1. What step 4 delivers

1. `una-link` writes ELF: a static-pie executable for `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`, with no interpreter, no shared library and no symbol versions (rule 22), loaded at a random address and relocating itself at start-up.
2. The embedded inputs (rule 12), for the target of the `una` binary, from the pinned Rust toolchain's `self-contained` directory of its musl target: `libc.a`, the start-up objects of a static-pie executable (`rcrt1.o`, `crti.o`, `crtn.o`; `crtbeginS.o` and `crtendS.o` for the constructor tables), and `libunwind.a`; each with its digest in the build record (rule 20) and the symbol index of step 3.
3. The runtime built for the musl target and Cranelift compiling for the same triple (rule 16).
4. RELRO really applied at run time (rule 25): the runtime's start-up protects `PT_GNU_RELRO` with `mprotect`, or checks it when musl already did (P2), and a run-time conformance test reads `/proc/self/maps`.
5. The runtime's global allocator on Linux chosen by measurement, preferring one in Rust (rule 21).
6. The `toolchain-free` gate's build and run phases on Linux, the `link-oracle` gate against `ld.lld` and GNU `ld`, the native confinement cases on each target (rule 31), `spec/16` "Linking" with the ELF lists, and what a Linux executable contains and under which licenses (musl MIT, libunwind Apache-2.0 with LLVM exception; `una notices` prints them in step 5).

Not in step 4: `una` itself linked statically (ADR 0124 Alternative L, open), cross-compilation (rule 17), `DT_RELR` unless P2 shows the embedded musl applies it, range-extension thunks.

## 2. The inputs and the retargeting

**Decision D1: everything the executable links is carried inside `una`, taken from the pinned toolchain at `una`'s build, and nothing from the machine that runs `una build`.** `scripts/release.sh` (rule 18) finds the toolchain's `lib/rustlib/<arch>-unknown-linux-musl/lib/self-contained/` (the `rustup` component `rust-std` for the musl target, installed by `rust-toolchain.toml`'s targets list from this step on), takes `libc.a`, `rcrt1.o`, `crti.o`, `crtn.o`, `crtbeginS.o`, `crtendS.o` and `libunwind.a`, records each digest in the build record and the validation summary, and passes them to `una-cli`'s build script (`UNA_EMBED_MUSL_DIR`, `UNA_EMBED_MUSL_SHA256S`), which checks the digests and embeds the bytes with the symbol index of each archive (step 3's index, built for `libc.a` and `libunwind.a` as for the runtime).

- **Why the toolchain's musl and not a build of our own.** Rule 12 says so: the toolchain's `self-contained` objects are what Rust's own static-pie musl executables link, built and pinned by the Rust project with the toolchain `rust-toolchain.toml` pins; their advisories follow the toolchain's bumps (Security). A musl built by the project would be a second C toolchain to maintain, for no gain.
- **The runtime for musl** (rule 16): `scripts/release.sh` builds `una-rt` with `--target <arch>-unknown-linux-musl` (the runtime has no C in its own tree; its dependencies with C, `ring`'s assembly, build for musl as they do for glibc through the `cc` crate at `una`'s build, which rule 18 allows for `una`'s own build and which ADR 0124's security section lists under `una notices`); Cranelift's target triple in `una-codegen` becomes the musl triple on Linux, which changes nothing in the code it emits but the triple the object records.
- **`una` stays glibc** (rule 1): its own link is Cargo's, through the system linker, with `libstdc++` and `libgcc` static (step 1g); only the executables it writes are musl.

## 3. Resolution against musl's archive (rule 23)

The inputs are read in the fixed order: the program's object, the runtime's members as needed, then musl's start-up objects and `libc.a`'s members and `libunwind.a`'s members as undefined symbols demand them, to a fixed point over all archives. The first definition in input order wins among members; two strong definitions in loaded inputs are U8001. What musl's archive brings in deserves three notes:

- **Weak and common symbols.** musl's `libc.a` defines many symbols weak (the `weak_alias` pattern) and some as common; a weak definition yields to a strong one, and the first weak definition among equals is kept; common symbols are allocated in `.bss` with the largest size and alignment seen (the standard library's objects define none, which the scan confirms).
- **The linker-defined symbols** (rule 23): `__start_<section>` and `__stop_<section>` for sections whose names are C identifiers (the Rust standard library uses none today; musl's `libc.a` references none either, which the scan confirms), `__init_array_start`/`__init_array_end`, `__fini_array_start`/`__fini_array_end`, `__preinit_array_start`/`__preinit_array_end` (musl's `__libc_start_main` runs the init array through them), `_DYNAMIC` (musl's `rcrt1.o` reads it to find its own relocations), `_GLOBAL_OFFSET_TABLE_`, `__ehdr_start`, `__dso_handle` (for `crtbeginS.o`'s destructors). An input that defines one of them is U8001.
- **What stays undefined** at the end is U8001 naming the symbol and the inputs: there is no shared library to bind to, so the list of rule 23's macOS exception does not apply.

**Decision D2: no `IRELATIVE`, no indirect functions.** musl has none (rule 24, "never supported"); the scan refuses an `R_*_IRELATIVE` in any input, and the verifier's canary keeps it so.

## 4. Relocations (rule 24)

The sets, derived by `scripts/scan-relocations` over Cranelift 0.136's objects, the Rust 1.98.1 standard library of each musl target, `ring` 0.17's assembly, musl's archive and start-up objects, and `libunwind.a`, listed in `spec/16` "Linking" and rerun at every bump:

- **x86-64:** `R_X86_64_64`, `PC32`, `PC64`, `PLT32` (resolved directly, no PLT), `GOTPCREL`, `GOTPCRELX`, `REX_GOTPCRELX` (relaxed to an address computation when the target is local: `mov` from the GOT becomes `lea`, as the psABI's relaxation table says), `32` and `32S` under the restriction below, and the TLS types `TPOFF32`, `GOTTPOFF`, `TLSGD`, `TLSLD`, `DTPOFF32`, with the general- and local-dynamic sequences relaxed to the local-exec model as the psABI describes, in both the form that calls `__tls_get_addr` through `PLT32` and the form through `GOTPCRELX` that Rust's default of no PLT produces: a static executable has one TLS module, so every access becomes `mov %fs:0, %rax; lea off(%rax)` or the `GOTTPOFF`-through-GOT form with the offset known at link time.
- **arm64:** `R_AARCH64_ABS64`, `PREL64`, `PREL32`, `CALL26`, `JUMP26`, `CONDBR19`, `TSTBR14`, `ADR_PREL_PG_HI21`, `ADR_PREL_LO21`, `ADD_ABS_LO12_NC`, `LDST8_ABS_LO12_NC` to `LDST128_ABS_LO12_NC`, `ADR_GOT_PAGE`, `LD64_GOT_LO12_NC`, `ABS32` and `MOVW_UABS_G0` to `G3` under the restriction below, and the TLS types `TLSLE_*`, `TLSIE_*` and `TLSDESC_*`, the last two relaxed to the local-exec model (`TLSDESC_ADR_PAGE21`/`LD64_LO12`/`ADD_LO12`/`CALL` become `movz`/`movk` of the offset and a `nop`, as the ELF for the Arm 64-bit Architecture's relaxation table says).
- **Position independence:** a narrow absolute relocation (`32`, `32S`, `ABS32`, `MOVW_UABS_G*`) only against an absolute symbol or in a section the output does not load, else U8001; a 64-bit absolute relocation (`R_X86_64_64`, `ABS64`) against a symbol that is not absolute only in a writable or RELRO section, where it becomes a relative fixup (`R_*_RELATIVE` in `DT_RELA`), in any other loaded section U8001 (the equivalent of `-z text`).
- **Bounds, ignored sections, errors, range:** as step 3; `CALL26`/`JUMP26` beyond ±128 MiB is U7015 (no thunks, rule 24).

## 5. Layout and loading (rule 25)

- **Alignment:** `p_align` 0x10000 on arm64, so the executable loads on kernels with 4, 16 or 64 KiB pages; 0x1000 on x86-64. Segment boundaries in the file follow the same alignment modulo the page.
- **Segments, in order:** read-only data (`PT_LOAD` r--: the headers, `.rodata`, `.eh_frame_hdr`, `.eh_frame`, `.gcc_except_table`, `.rela.dyn`, `.dynamic`'s read-only copy is not needed), code (`PT_LOAD` r-x: `.text`, `.init`, `.fini`), RELRO data (`PT_LOAD` rw- covered by `PT_GNU_RELRO`: `.tdata`, `.init_array`, `.fini_array`, `.preinit_array`, `.data.rel.ro`, `.dynamic`, `.got`), writable data (`PT_LOAD` rw-: `.data`, `.bss`); none both writable and executable. `PT_PHDR`, `PT_DYNAMIC` (for the relative relocations: `DT_RELA`, `DT_RELASZ`, `DT_RELAENT`, `DT_RELACOUNT`; `DT_SYMTAB`/`DT_STRTAB` pointing at empty tables, which musl's start-up tolerates; `DT_FLAGS_1` `PIE`; no `DT_NEEDED`), `PT_TLS` (`.tdata` then `.tbss`, with its alignment), `PT_GNU_EH_FRAME` with a synthesized `.eh_frame_hdr` and its sorted binary-search table, `PT_GNU_STACK` not executable, `PT_GNU_RELRO` whose end is padded to the segment alignment so that one page protection covers exactly it.
- **Relative relocations** are written as `DT_RELA` entries (`R_X86_64_RELATIVE` / `R_AARCH64_RELATIVE`), which `rcrt1.o`'s `_dlstart_c` applies before `__libc_start_main`. **`DT_RELR` (P2):** if P2 shows the embedded musl's start-up applies `DT_RELR` (musl 1.2.4 and later do; the toolchain's musl version is read from the archive at the scan), the relative relocations are packed as `DT_RELR` bitmaps, with a gate test that the executable starts; otherwise `DT_RELA` alone. Either way the format is one or the other, fixed at `una`'s build by the pinned musl, never chosen at run time.
- **`.init_array` and `.fini_array`** keep their order and priorities (the Rust standard library uses them for its TLS destructors registration); `.preinit_array` is empty.
- **The entry** is `_start` of `rcrt1.o`, which relocates the executable and calls `_start_c`, then musl's `__libc_start_main`, then the runtime's `main` (`spec/16 §3`).
- **Thread-local storage:** `PT_TLS` with the TLS template; musl's start-up sets up the main thread's TLS from it; `TLSLE` offsets follow the variant I (arm64) and variant II (x86-64) layouts, with the alignment and size of `PT_TLS`.

## 6. RELRO at run time (rule 25, probe P2)

Writing `PT_GNU_RELRO` protects nothing unless the start-up code does. glibc's static-pie start-up does; **P2 answers whether the toolchain's musl does** (it reads `/proc/self/maps` before anything else in a static-pie musl executable and reports whether the RELRO pages are writable).

**Decision D3: the runtime protects the range itself in both cases, as the first thing `main` does, and the difference P2 makes is whether that call is the protection or a check of it.** In `crates/una-rt/src/ffi.rs` (about 40 lines of `unsafe`, rule 35, ADR 0058 amendment), before any input is read: `getauxval(AT_PHDR)`, `AT_PHNUM`, `AT_PHENT` give the program headers; the `PT_GNU_RELRO` entry's range, rounded to the page size (`sysconf(_SC_PAGESIZE)`, which handles the 4/16/64 KiB kernels under the 64 KiB `p_align`), is passed to `mprotect(PROT_READ)`; a failure is U8001, "cannot protect the executable's read-only data", and the run does not start. If P2 shows musl already protected it, `mprotect` is a no-op that succeeds, and the call stands as the check rule 25 names. The run-time conformance test reads `/proc/self/maps` from inside a program (through a host operation in a test build, or by the `toolchain-free` run phase's reading of the maps of a child it starts) and finds the GOT's page not writable; the claim "full RELRO" is made only with that test (rule 25).

Before `main`, only musl's start-up and the standard library's initializers have run (`.init_array`), none of which reads input.

## 7. The allocator (rule 21)

Under Question 2 (a), the runtime's global allocator on Linux is not musl's `malloc`, whose performance under many threads is known to be poor; it is a pinned allocator wrapped in the same `Cap` that counts and limits memory (ADR 0061).

**Decision D4: measured, Rust first.** Slice 4e builds the runtime's allocation-heavy programs of the release performance benchmarks (the collections' and numerics' scaling tests, the HTTP server's request loop) with each candidate and against the same programs under glibc's allocator, on the gate machine's `linux/arm64` container and the x86-64 machine, medians of 9 runs; the candidates are one allocator written in Rust with no C in its tree (the candidates are listed in the slice's pull request with their supply-chain records; a candidate that compiles C is reviewed as a C dependency and loses on a tie), and musl's `malloc` as the baseline. The choice is recorded with its numbers in the pull request and in `docs/plan/`, goes through `supply-chain/crates.tsv` and the `deps` gate, and is wrapped in `Cap<_>` in `crates/una-rt/src/lib.rs` under `cfg(target_os = "linux")`. musl's `malloc` remains for musl's own internal allocations (`getaddrinfo`, `stdio`), which are few.

## 8. Determinism and the record (rules 20, 28, 29)

- The executable is a function of the inputs' bytes (the program's object, the runtime, musl's objects and `libunwind.a`, all embedded with digests), the `una` version and the output's file name: no path, user name, time or random value is written; `.comment` and `.note.*` sections of the inputs are dropped (rule 26); the section header table is written in a fixed order with the names in a fixed string table. Two builds on two machines of the same target give the same bytes, which the `reproducible` gate checks across the macOS host's and the container's `una`.
- The build record gains `musl_sha256s` (one per embedded object, in a fixed order) and `libunwind_sha256`; the report's `native` section has `linker` and `runtime_sha256` from steps 2 and 3; `una.build/1`'s `target` is `x86_64-unknown-linux-musl` or `aarch64-unknown-linux-musl` (rule 29).

## 9. The verifier and its canaries (rule 34)

`verify(bytes, inputs)` on ELF: no `PT_LOAD` both writable and executable; `PT_GNU_STACK` present and not executable; `PT_GNU_RELRO` covers `.got`, `.init_array`, `.fini_array`, `.dynamic` and `.data.rel.ro`, and its end is aligned; no text relocation (every `DT_RELA` entry's place is in a writable or RELRO segment); every relocation was applied inside its own section; every kept input section placed once without overlap; `p_align` 0x10000 on arm64; no `PT_INTERP`, no `DT_NEEDED`, no symbol versions; no `R_*_IRELATIVE`; the entry is `_start` of `rcrt1.o`. The canaries of step 3 apply, with the ELF forms: an object with a writable and executable section, an `IRELATIVE`, an undefined symbol, an executable `PT_GNU_STACK`, a relocation 8 bytes past its section, a symbol past its section's end, two overlapping input sections; and, for Linux, a `PT_GNU_RELRO` that does not cover `.got`.

## 10. The gates and their confinement (rule 31)

- **`toolchain-free`, build phase on Linux:** in a container of the bare Ubuntu image of `scripts/local-ci/`, where **Landlock** grants execution only to `una`'s file and to the glibc loader it needs (`ld-linux-*.so`, since `una` is dynamic), through `scripts/toolchain-free.sh`'s Linux leg gaining a Landlock launcher (the security hunt's `hunt/landlock.py` is the model: it restricts the file-system rules of a child before `execve`), `una check`, `una test` and `una build` of `examples/hello` and of a program with an `Http` request over TLS to a local test server; a `PATH` of one empty directory. The solver child's seccomp filter nests inside Landlock without conflict: Landlock restricts files, seccomp restricts calls, and `prctl(PR_SET_NO_NEW_PRIVS)` is set by both. **Run phase:** each executable built runs under a second Landlock rule set that grants execution to exactly those files and no loader (they are static), and gives the interpreter's output.
- **Native on each target** (rule 31): the `limits` gate and the confinement cases of the Conformance run natively on the arm64 container and on a native x86-64 Linux machine, never under emulation; probe P1 (#1203) says whether the seccomp cases can also run under Rosetta's emulation in the `linux` gate, and if not they are marked there and the native x86-64 run before each release is the record.
- **`link-oracle` on Linux:** `ld.lld` and GNU `ld` as oracles (both in the local-ci image from this step: `lld` and `binutils`), per relocation type (assembly fixtures assembled by the image's `as`), per program (the `native` gate's equivalence on `una-link`'s output), on generated programs; `llvm-readobj` reads every output; the RELRO test of §6 at run time.
- **The `sanitize` gate** keeps its external link (rule 19, step 3's `dev-external-link`) and its AddressSanitizer runtime on macOS; on Linux the address-space backstop of the solver child is off under ASan (step 1).
