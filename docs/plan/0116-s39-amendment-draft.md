# ADR 0116 amendment draft: the trace's own events under a raised program counter (S-39)

Status: Proposed (draft for the project's decision; it is appended to docs/adr/0116-long-running-programs.md only once accepted, with the date of its acceptance). Security fix of #1507; the behaviour is already implemented in the pull request. Until then `spec/09 §2` and `spec/26 §6` rule 4 cite it as proposed.

## Amendment (proposed 2026-11-02): the trace's own events under a raised program counter (S-39)

Rule 14 appends `{"seq": n, "outcome": {"kind": "stop"}}` for every `for ever` that a host stop ends at an iteration start, with no label, and IF4 lets a `for ever` stand under any program counter. An adversarial review of #1478 (issue #1507, S-39) showed that the event leaks: whether a loop under a `secret` branch is entered, and whether its budget or a host stop ends it rather than `stop when`, depends on the secret, and so do the number of `stop` events and the `seq` of every later event. A program that calls such a loop, guarded by `s > i`, for sixteen values of `i` gives exactly `s` events, with the same output and exit status. The same holds after SIGTERM and `--deadline`, since the request is sticky, in both engines and before the per-loop budget of #1478.

The second round of review found the same channel in the other events that the runtime appends by itself. A `within` with a public deadline around a loop that never ends, in a function called under `if s > i`, always times out, so it gives `s` `timeout` events; a `tasks` statement that starts a task and then fails, called the same way, gives `s` `cancelled` events. Neither needs a host stop or a deadline that races its code, and `una check` accepted both.

These events are sinks that accept `public`, as `Console.print` is. Code that stands under a program counter above `public`, joined with the effect floor and the timing floor as an effect's is, or that runs inside a call or an operation that stands under one, a call of a function value labeled `l_f`, which stands under `pc ⊔ l_f` with the decisions of its arguments (`spec/07 §3` rule 4), included, its callees, the operations of handlers and the tasks they start included, is quiet: it appends no `stop`, `timeout` or `cancelled` event, and takes no `seq` for them. Elaboration marks `quiet` in Core each `for ever`, `within`, `first of`, `tasks`, `together` and `together for` under a raised program counter, each call there whose callee can run one of them (a least fixed point over the call graph, linear in its edges; a function value, a prelude function that applies a function argument, and a function that installs a handler count as able to), and each operation there when the package declares a handler. Both engines count the `quiet` expressions a task is in, a started task beginning with the count of its `start`. Quiet code also numbers its `tasks` statements and `first of` blocks with counters of its own, per task, which give the paths `p.qs<c>.<k>` and `p.qf<c>.<i>`: the third round of review showed that a quiet statement, though it appended no event, advanced the counter that names `s<c>` and `f<c>`, so the `task` path of every later public event spelled out the secret. The same round showed that a call of a function value that is itself `secret`, made at a `public` program counter, directly or through a kind's field, or of one given an argument decided by values of a type parameter, was not marked, though `spec/07` puts it under `pc ⊔ l_f`: it gave the whole channel, `cancelled` events and paths included. Such a call is now quiet when `l_f`, joined with those decisions, is above `public`. A task started in quiet code is quiet, so all of its blocks are numbered this way. `spec/26 §6` rule 4 states the rule, and `spec/09 §2` the Core form.

Choice. The other sound option makes a `for ever`, a `within`, a task construct, and a call that reaches one, under a raised program counter an error, as an effect is (U4002). It rejects programs whose loops and deadlines perform no effect, and a server's started tasks under an `internal` program counter, which IF4 accepts; the quiet events keep them accepted and close the channel. Labeling the events and numbering `seq` per level would change the trace's format, `una.run/1`, for no reader that exists: the trace is one document, read by `una run --json`, `--trace`, the equivalence tests and the hunt's oracle, so the public view is the only one, and leaving the events out is the labeled events filtered for it.

Costs. Two runtime calls per entry of a quiet construct, call or operation, O(1) each, and nothing elsewhere: code without such a construct under a raised program counter, and calls under one of functions that can run none, are compiled as before. Marking a call takes the closure over the package's call edges once per check.

Out of scope:
- **Type parameters.** A label that mentions a type parameter, or a decision on values of a type parameter, counts as above `public` for the rule above, since one generic body serves every instantiation; a public program that calls such a generic function loses the events the rule suppresses. This is the safe direction and no equivalence test depends on those events.
- **Bodies no label rule checks.** The body of a policy's `via` function is not checked for labels, so its program counter counts as above `public`: its operations are quiet when the package declares a handler, whatever their arguments' labels. An operation in a checked body at a `public` program counter is not quiet because of a `secret` argument. This is the safe direction.
- **The reported timing channel.** A `within` that stands under a `public` program counter, and whose `τ(e)` is above `public`, keeps its `timeout` event and the `cancelled` events of the tasks it cuts: whether it timed out is timing, which the report's `timing` list names with its label (`spec/27 §5` rule 7). A `within` in quiet code is not that channel: in the round-2 reproducer the report lists no `timing` entry for it, rightly, since `τ(e)` is `public` there, and its events are now left out.
- **Stack exhaustion.** The `aborted` event of a started task that runs too deep is stack exhaustion, which also writes its line to stderr, and stays out of model (`spec/07 §1`): leaving the event out would not hide the line.
- **A `start` under a raised program counter in a `public` `tasks` statement** (S-40, #1512). The statement itself is not quiet, so the `cancelled` events of the tasks started there, and the index `k` in the paths of the tasks the same statement starts after them, still depend on the secret. The tasks such a `start` starts are not quiet either. The separate block counters of quiet code number statements, not the `start`s inside one, and do not close this.
- **Handler installations** (S-41, #1514). A `with` under a raised program counter is accepted, and the run-wide count behind `with:<h>#n` counts it, so the instance id of a later public installation depends on the secret. This amendment leaves that count as it is.
- **Operations of a capability that accepts a label above `public`** (S-42, #1515). Performed under a raised program counter they are recorded by occurrence, each taking a `seq`: the count of events and the `seq` of later events depend on the secret. This needs a decision on what the trace is, the `public` view or a reader at the highest `accepts` label of the program's capabilities; this amendment does not make it.
- **The run-wide budget** (S-36, #1478): how many iterations a `secret` loop took from `--stop-after-iterations` shows in the output of a later public loop, not in the trace.
- **The hard stop.** The `cancelled` events and U6007 of the hard stop of `public` code are the time of a host stop (`spec/07 §1`); inside quiet code its `cancelled` events are left out as well.

The formal model has none of these events yet, so a declaration that runs a `for ever`, or holds `quiet`, is not re-checked by it.
