# ADR 0116 amendment draft: the trace's own events under a raised program counter (S-39)

Status: Proposed (draft for the project's decision; it is appended to docs/adr/0116-long-running-programs.md only once accepted, with the date of its acceptance). Security fix of #1507; the behaviour is already implemented in the pull request. Until then `spec/09 §2` and `spec/26 §6` rule 4 cite it as proposed.

## Amendment (proposed 2026-11-02): the trace's own events under a raised program counter (S-39)

Rule 14 appends `{"seq": n, "outcome": {"kind": "stop"}}` for every `for ever` that a host stop ends at an iteration start, with no label, and IF4 lets a `for ever` stand under any program counter. An adversarial review of #1478 (issue #1507, S-39) showed that the event leaks: whether a loop under a `secret` branch is entered, and whether its budget or a host stop ends it rather than `stop when`, depends on the secret, and so do the number of `stop` events and the `seq` of every later event. A program that calls such a loop, guarded by `s > i`, for sixteen values of `i` gives exactly `s` events, with the same output and exit status. The same holds after SIGTERM and `--deadline`, since the request is sticky, in both engines and before the per-loop budget of #1478.

The second round of review found the same channel in the other events that the runtime appends by itself. A `within` with a public deadline around a loop that never ends, in a function called under `if s > i`, always times out, so it gives `s` `timeout` events; a `tasks` statement that starts a task and then fails, called the same way, gives `s` `cancelled` events. Neither needs a host stop or a deadline that races its code, and `una check` accepted both.

These events are sinks that accept `public`, as `Console.print` is. Code that stands under a program counter above `public`, joined with the effect floor and the timing floor as an effect's is, or that runs inside a call or an operation that stands under one, a call of a function value labeled `l_f`, which stands under `pc ⊔ l_f` with the decisions of its arguments (`spec/07 §3` rule 4), included, its callees, the operations of handlers and the tasks they start included, is quiet: it appends no `stop`, `timeout` or `cancelled` event, and takes no `seq` for them. Elaboration marks `quiet` in Core each `for ever`, `within`, `first of`, `tasks`, `together` and `together for` under a raised program counter, each call there whose callee can run one of them (a least fixed point over the call graph, linear in its edges; a function value, a prelude function that applies a function argument, and a function that installs a handler count as able to), and each operation there when the package declares a handler (every operation there, since the S-42 addition below). Both engines count the `quiet` expressions a task is in, a started task beginning with the count of its `start`. Quiet code also kept its `tasks` statements and `first of` blocks off the public counters, per task (the paths are now `p.qs.<k>` and `p.qf.<i>`, with no number, see below): the third round of review showed that a quiet statement, though it appended no event, advanced the counter that names `s<c>` and `f<c>`, so the `task` path of every later public event spelled out the secret. The same round showed that a call of a function value that is itself `secret`, made at a `public` program counter, directly or through a kind's field, or of one given an argument decided by values of a type parameter, was not marked, though `spec/07` puts it under `pc ⊔ l_f`: it gave the whole channel, `cancelled` events and paths included. Such a call is now quiet when `l_f`, joined with those decisions, is above `public`. A task started in quiet code is quiet, so none of its blocks are counted. `spec/26 §6` rule 4 states the rule, and `spec/09 §2` the Core form.

A `start` under a raised program counter in a `public` `tasks` statement (S-40, #1512) was the next route: the statement is not quiet, so the `cancelled` event of such a task, and the index `k` in the paths of the tasks the same statement starts after it, which also picks their worker, depended on the secret. Elaboration now marks such a `start` `quiet`, so its task runs in quiet code and ends without its `cancelled` event. Its review then showed that counting quiet code apart is not enough: code is also quiet under a decision on values of a type parameter and under the effect floor of an operation body, with no `secret` branch around it, so its events occur whatever the secret, and a count of quiet `start`s, or of quiet statements and races (S-44, #1546), in their paths (`s1.q1` against `s1.q2`, `qs1.q1` against `qs1.q3`) spelled out how many ran before under a `secret` branch. So quiet code counts none of its statements, races and `start`s: their path parts are `qs`, `qf` and `q`, with no number. Paths in quiet code are therefore not unique, an exception to ADR 0117 rule 7's "paths are unique" that this amendment states; nothing in either engine relies on it (a join matches the paths of its own tasks only, and the installations of quiet code take no number, S-41), and two quiet tasks that run too deep write the same U6003 line. A quiet task is placed by the position of its `start` in the program, since a count of quiet `start`s would show how many ran: every task of one quiet `start`, such as those of a quiet `for` loop, runs on one worker, a cost of quiet code only.

Choice. The other sound option makes a `for ever`, a `within`, a task construct, and a call that reaches one, under a raised program counter an error, as an effect is (U4002). It rejects programs whose loops and deadlines perform no effect, and a server's started tasks under an `internal` program counter, which IF4 accepts; the quiet events keep them accepted and close the channel. Labeling the events and numbering `seq` per level would change the trace's format, `una.run/1`, for no reader that exists: the trace is one document, read by `una run --json`, `--trace`, the equivalence tests and the hunt's oracle, so the public view is the only one, and leaving the events out is the labeled events filtered for it.

Costs. Two runtime calls per entry of a quiet construct, call or operation, O(1) each, and nothing elsewhere: code without such a construct under a raised program counter, and calls under one of functions that can run none, are compiled as before. Marking a call takes the closure over the package's call edges once per check.

Out of scope:
- **Type parameters.** A label that mentions a type parameter, or a decision on values of a type parameter, counts as above `public` for the rule above, since one generic body serves every instantiation; a public program that calls such a generic function loses the events the rule suppresses. This is the safe direction and no equivalence test depends on those events.
- **Bodies no label rule checks.** The body of a policy's `via` function is not checked for labels, so its program counter counts as above `public`: its operations are quiet, whatever their arguments' labels (when the package declares a handler, before the S-42 addition below). An operation in a checked body at a `public` program counter is not quiet because of a `secret` argument. This is the safe direction.
- **The reported timing channel.** A `within` that stands under a `public` program counter, and whose `τ(e)` is above `public`, keeps its `timeout` event and the `cancelled` events of the tasks it cuts: whether it timed out is timing, which the report's `timing` list names with its label (`spec/27 §5` rule 7). A `within` in quiet code is not that channel: in the round-2 reproducer the report lists no `timing` entry for it, rightly, since `τ(e)` is `public` there, and its events are now left out.
- **Stack exhaustion.** The `aborted` event of a started task that runs too deep is stack exhaustion, which also writes its line to stderr, and stays out of model (`spec/07 §1`): leaving the event out would not hide the line.
- **Slots and parks of quiet code** (S-40 remainder, #1545). A quiet task holds a slot of its statement's one bound (ADR 0117 rule 7), so whether `start`s under a `secret` branch ran decides whether a later public `start` waits, and in the interpreter a task that waits or parks inside quiet code lets the queued tasks run first, so the order of other tasks' public events depends on the secret. Bounding quiet tasks apart is proposed separately (`docs/plan/0117-quiet-bounds-amendment-draft.md`), since it changes rule 7's bound.
- **Handler installations** (S-41, #1514), closed by the addition below.
- **The counters of quiet blocks** (S-44, #1546). `qs<c>` and `qf<c>` counted every quiet statement of a task, those under a raised program counter included. In code that is quiet only by the conservative rules, under an effect floor or a decision on values of a type parameter, events that always happen carried a `c` that showed how many statements guarded by a secret ran before. Closed with S-40 above: quiet statements and races take no number, as the installation ids of the addition below take none.
- **Operations of a capability that accepts a label above `public`** (S-42, #1515), closed by the last addition below.
- **Shared host state** (S-45, #1552). The events of quiet code are left out, not what its operations did to host state: a later public operation on the same files or limiter showed it in its outcome. Closed by the proposed amendment of ADR 0032 (`docs/plan/0032-outcome-redaction-amendment-draft.md`), which renders every outcome of a run's trace at its label; the route needs no quiet code, so it is a rule of the trace's rendering, not of this amendment.
- **The run-wide budget** (S-36, #1478): how many iterations a `secret` loop took from `--stop-after-iterations` shows in the output of a later public loop, not in the trace.
- **The hard stop.** The `cancelled` events and U6007 of the hard stop of `public` code are the time of a host stop (`spec/07 §1`); inside quiet code its `cancelled` events are left out as well.

The formal model has none of these events yet. Since #1553 its importer reads `quiet e` as `e`, so a declaration that holds `quiet` is re-checked on F1's trace, which keeps the operations' events that quiet code leaves out; the step to the runtime's trace is argued, not proven.

## Addition (proposed 2026-11-04): handler installations in quiet code (S-41)

An adversarial review of #1511 (round 2, H2; issue #1514, S-41) showed that a `with` under a raised program counter, written there or in a callee, was accepted and counted by the run-wide count behind `with:<h>#n`: a later public installation of the same handler read `with:keep#1` for `s = 0` and `with:keep#3` for `s = 2`, in both engines, so its id spelled out the secret. A `with` that installs a handler under a raised program counter is now marked `quiet` in Core, with the body it scopes, which stands under the same program counter; a call there whose callee installs a handler already was. Quiet code numbers none of its installations: each instance it installs is `with:<h>#q`, in every task, which a join leaves as it is. The first version of this fix counted quiet installations apart, `with:<h>#q#<n>`; its review (#1541, H1) showed that this moved the channel rather than closing it. Code is quiet not only under a secret branch but also by the conservative rules above (an operation body under an effect floor above `public`, a decision on values of a type parameter), where the occurrence of an operation is public: a later quiet `put` read `with:keep#q#(s+1)` at the same `seq` for every `s`. With no number, how many installations quiet code ran shows in no id, public or quiet. The cost is that the instances quiet code installs are not told apart by their ids; nothing reads the id but the trace.

Editions. The quiet marking of S-39 already has no edition check: a call under a raised program counter whose callee installs a handler, an operation there when the package declares a handler, and a call of a function value are `quiet` in Core in editions `0.1` to `0.3` too. Handlers and `with` exist in every edition, so this addition changes the ids of handlers that quiet code installs in every edition: `with:<h>#q` in place of a number. That is the safe direction, and gating it to edition `0.4` would keep the S-41 channel open in earlier editions; `spec/26` states the exception to its edition rule, and `spec/11 §5` the ids.

Choice. Rejecting a `with` under a raised program counter would reject programs that the label rules accept today, a handler answering at `public` in the body that installs it (ADR 0094 rule 4). Numbering installations by static site plus occurrence would change every id of the trace format. A count of quiet installations reset at each outermost quiet extent would still carry, inside one extent, how many installations code under a secret branch of that extent ran. An id with no number keeps every public id as it was, needs no change to the adoption and streaming renumbering, which leave an id with no task path untouched, and keeps the format `una.run/1`.

Costs. An installation in quiet code makes its id, O(|h|), and touches no count; outside quiet code nothing changes: O(log h) per installation, h the handler names the task installed, as before.

## Addition (proposed 2026-11-04): the operations of handlers that quiet code installs (#1544)

An adversarial review of #1543 (`p_local.una`) showed that a function with no effects of its own that installs a handler and performs an operation served by it, called under a `secret` branch, wrote that operation's event: the trace of `s > 0` held a `put` that the trace of `s <= 0` did not, with the same output and exit status, in both engines and in every edition. The direct form, a `with` under the branch whose body performs the operation, is rejected (U4002), since the operation is an effect checked against the program counter where it is written; through the callee it is not, since the handler discharges the effect inside the callee, whose header shows none, and the callee's own checking cannot know the program counter of its callers. The call site already is marked: a call under a raised program counter whose callee installs a handler is `quiet`, so the instance the callee installs is `with:<h>#q` (S-41). An operation served by an instance that quiet code installed now appends no event and takes no `seq`, in both engines and every edition; the handler's code runs as before, and the events it writes are its own.

Choice. A `#q` instance is in scope only in quiet code: the `with` that installs it scopes its body, a capability is second class, and a task started there is quiet. Keying the rule on the instance, not on the operation's program counter, leaves every operation of an instance that public code installed as it was: such an operation in quiet code is an effect of the code that performs it, checked by the label rules at its call (U4002). Rejecting a call under a raised program counter of a function that installs a handler would reject programs that the label rules accept today, a local handler that answers at `public` (ADR 0094 rule 4), and the handlers that the conservative rules (an effect floor, a decision on values of a type parameter) reach at a `public` program counter. Labeling the events would change the trace's format for no reader that exists, as for the events of S-39.

Costs. One test of the instance's id per operation, O(1), in both engines; nothing else changes. Where code is quiet only by the conservative rules, the operations of the instances it installs always happen, and a public program loses their events: the safe direction, as for the other events this amendment leaves out. Arguments and results of such operations are not rendered, so one that holds an integer too long for text does not abort the run there, in both engines, as when a native run records no trace.

## Addition (proposed 2026-11-04): operations in quiet code (S-42)

An adversarial review of #1511 (round 2, H3; issue #1515, S-42) showed that an operation of a capability that accepts `secret`, performed under `if s > i` for each `i`, appended one event per run of it: arguments redacted, but `s` events and a `seq` of `s + 1` for the later `print`, in both engines, with the handler in the package or in a path dependency. The same held for a host operation that accepts `internal` (`Http`, `Limit.acquire`) under an `internal` branch, in a package with no handler. Round 1 of #1511 had decided that the trace is the `public` view: it redacts every argument above `public` (`spec/11 §5`), and it is one document, read by `una run --json`, `--trace`, the equivalence tests and the hunt's oracle. An operation's event is then a sink that accepts `public`, as the runtime's own events are: the effect rule (`spec/07` rule 4) lets the receiver that accepts `secret`, the handler or the host, observe the occurrence, and it still does; the trace is another reader.

The #1544 addition above keyed its rule on the instance, `with:<h>#q`, and left an operation of an instance that public code installed, performed in quiet code, as it was; this addition keys on the program counter, and both apply. So an operation performed in quiet code appends no event to a run's trace and takes no `seq`, in both engines and every edition, whatever serves it; the code of a handler that serves it runs in quiet code, so its own operations append none either. Elaboration marks every operation under a raised program counter `quiet`, and every call there whose callee can perform one, not only when the package declares a handler, since a host operation or a handler of a dependency writes an event too. The timing floor of a `within` or a `first of` is not such a program counter for this addition: an operation in `e within d` whose `τ(e)` is above `public`, at a `public` program counter, occurs or not by the reported timing channel, and `spec/27 §5` rule 7 keeps its event (the request that the deadline cuts shows its `TimedOut`). Core therefore writes `quiet timing` for a mark that the timing floor alone made; it keeps the S-39 to S-44 rules for its own events, ids and paths, and its operations keep their events, while a `quiet` without `timing` hides them, in its callees and started tasks too (both engines count the marks of each kind a task is in). A failure that the deadline of a `for ever within` iteration causes in quiet code no longer counts as the iteration's first observation of it (review round 2 of #1511, L1), so whether the iteration's `timeout` event appears never depends on whether quiet code observed the deadline first. With S-39, S-40, S-41 and S-44, a run's trace now holds no event written in quiet code but the `aborted` event of a task that runs too deep, which stays out of model.

Examples. An example's trace keeps those events, but those of instances that quiet code installed, which the #1544 addition above leaves out of every trace: its data come from its source (ADR 0078), the `given` instances are the example's own, and `expect performed @x.op` reads its trace (`spec/08 §2` rule 7). An example whose operation stands under a branch on a `secret` parameter would otherwise fail. The other events of quiet code stay out of an example's trace, as before.

Editions. As the quiet marking (see the S-41 addition), this applies in every edition: an edition `0.1` to `0.3` package checked and run by this compiler leaves out the events of operations under a raised program counter. The released lines (`v0.3.17`, `v0.1.13`) record them by occurrence, as their `spec/11 §5` says (triage of #1547); they make no claim that the trace's shape is independent of labeled data, so they are not changed. Gating the rule to edition `0.4` would keep the channel open in earlier editions on this line, where `spec/26 §6` rule 4 already states, for installations, that the trace's ids do not depend on the secret in any edition; it would also need the edition at run time in both engines.

Choice and costs. The other options were rejected. Declaring the trace a reader at the highest `accepts` label of the program's capabilities would give up the `public` view that every other quiet rule protects, and the trace would have to be treated as secret wherever it goes. Numbering `seq` per label would change the format `una.run/1`. Keeping the events in a separate unnumbered section would still show their number. The cost of the rule is that code quiet only by the conservative rules, a decision on values of a type parameter, an operation body under an effect floor above `public` or a `via` body, loses its operations' events in a run's trace, though they occur whatever the secret there: the same code also runs under `secret` branches or on `secret` arguments, nothing at run time tells the cases apart, and a count of them would show how many ran under the branch. The operation that enters such code from a `public` program counter keeps its event, its arguments redacted. Hiding never adds an observation, so T6 is unaffected, and both engines hide the same events, so their traces still compare (`spec/16 §5`). A `una replay` (backlog) would have to re-run quiet code's host operations rather than substitute them. At run time a quiet operation does one O(1) check of the count of `quiet` marks without `timing` and skips the event, its arguments' rendering and its redaction; marking costs nothing beyond the closure of S-39, linear in the call edges.
