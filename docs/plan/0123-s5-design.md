# ADR 0123 S5: the `HttpServer` capability (design note)

- Issue: #1007, part of #897. Implementation plan step 5 of ADR 0123: the declarations of `std.host`, imported only in edition `0.4` (rules 0 and 1); `next`, `reply` and `close` (rules 2 and 3); reply rights, their moves at `start`, the state machine of rule 4.7, auto-answers and their trace events, and the reduced trace form (rules 1 and 4); U3033 (rule 5); the information-flow rules with IF6; and the language form of rule 15.
- Base: ADR 0123 S4 (#1006, `docs/plan/0123-s4-design.md`, the serve threads), itself on ADR 0117 S7 (#972, the reactor) and ADR 0123 S3 (#1005, grants and TLS), as those branches stand; the code of this slice is written on that tower once S4 builds. The departures of S4 that its amendment draft (`docs/plan/0123-s4-amendment-draft.md`) carries are taken as given here: dedicated serve threads, placement of tasks by ADR 0116 P6 (the placement of ADR 0123 Appendix A is withdrawn), accepting from the run's first server operation.
- Normative text: ADR 0123 rules 0 to 5, 14, 15, 18 (the program's side), 21 (`std.testing`, only what `given` handlers need), Verification, Information flow IF1 to IF7, Security, Diagnostics; `spec/31 §1` grows with this slice, `spec/14 §3` (host capabilities) and `§4` (`std.testing`), `spec/10 §11` rule 10, `spec/11 §5` (the reduced trace form), `spec/13 §4` (U3033).
- Not in this slice: `[serve]` and its driver (S6, #1008); `--serve-script`, `--serve-out`, `test_request`, `test_exchange` and the example servers (S7, #1009); the TLS server (#1059); the report's server entries (S6, rule 22).

This note fixes how S5 is built, and lists the decisions it takes where the records leave a choice. Each decision takes the most secure option the records allow.

**First part, landed with #1007:** the declarations, U3033, IF1 to IF7 with IF6 and `L_srv` (§2, §6, §7) in the checker, with runs refused until the operations land (`spec/31 §1` rule 10). The points where the implementation departs from this note or from ADR 0123, the field `params` for `query` among them, are in `docs/plan/0123-s5-amendment-draft.md`. §3 to §5 and the runs of §9 are the second part.

## 2. The declarations (rules 0 and 1)

- **Where.** `crates/una-check/src/std/host_0_4.una`, a text appended to `std.host`'s source for edition `0.4` only, as `std.testing` gains `elapse` in edition `0.4` (`testing_source`). `std_host_names` returns a fourth list for `Edition::V0_4`: `STD_HOST_NAMES_0_2` plus `HttpServer`, `Request`, `Reply`, `Exchange`, `Method`, `Param`, `Status`, `ServeError` and `ReplyRight`. In editions `0.1` to `0.3` the names are absent, so an import of one is U1001 by the existing rule (`spec/10 §11` rule 4), with no new code (rule 0).
- **Imported, not in the prelude.** The prelude puts none of them in scope; `spec/10 §11` rule 10 lists them as names whose import is not redundant. A user kind `Request` or `Reply` stays legal in every edition: the conformance case `names/host_request_beside_user_request` declares `pub kind Request` and imports `std.host (Reply)`.
- **The kinds** are the ADR's, field for field, with every field `internal` (rule 1, "Labeled fields"), so a constructor field is a flow site for `secret` data (U4001). `Status = Int where 200 <= it and it <= 599` is a refined alias: every `Reply(status: s, ...)` carries the refinement obligation (Verification), proven by the verifier at tier 1 as any refinement is; `Reply(status: 700, ...)` is U5001.
- **`ReplyRight`** is declared as `Hashed` is: an opaque kind of the standard library with no constructor, no fields and no literal (decision S5-D1: the same elaboration path as `Hashed`, so no new kind of declaration). Two values are equal when they name the same exchange (§4), so `==` is defined on it as on `Hashed`; it has no order and no hash; interpolation writes `<reply-right>`.
- **The capability** `HttpServer` with `next() -> internal Exchange fails ServeError`, `reply(to: ReplyRight, reply: Reply) -> Unit fails ServeError accepts internal`, `close() -> Unit` (no `fails`, so a handling clause on it is U3025). It is a host capability of `std.host`: `authority::host` returns true for it, so an example that uses it without a `given` is U3014; `granted` already maps a `serve:` grant to all three operations (S3), so a `uses` without a grant is U3012, whose repair is a description only (rule 1, "Examples").
- **Core IR.** The kinds and the capability elaborate as the other `std.host` declarations do (`standard_kinds`), in the module `std.host`, so `una.core/1` of a package that imports them lists them as it lists `Header` and `Response`; nothing changes for packages that do not.
- **Edition test.** `crates/una-cli/tests/editions.rs`: every `0.3` package checks the same in `0.4` (the names are imported only, so no `0.3` package gains or loses a diagnostic); the `0.4` conformance cases that import them are `0.4`-only.

## 3. The operations, over S4's engine (rules 2, 3, 13, 14, 18)

The engine of S4 (`crates/una-http/src/serve/engine.rs`) owns connections, reads requests, and keeps, per serve thread, the queue of requests read and waiting, with a ready flag; delivery scans the flags from a per-run rotating cursor (S4 §6.7). This slice adds the program's side, in both engines, as host operations of the capability `HttpServer`, `host:HttpServer`, one instance per run (rule 1, "One instance"):

- **`next`.**
  1. If the run has `close`d: fail `Closed` at once (rule 1).
  2. If the run's host stop has been requested: fail `Interrupted` (rule 18 item 3; ADR 0116 rule 14), before taking any request, so a stopped run never takes a request it will not answer.
  3. Take the first request of the first ready serve thread from the cursor; when none is ready, park the task on the grant's list of waiters (S4's mutex "taken only on the waiting path"), as an interruptible operation of ADR 0117 rules 3 and 4: it wakes on a delivery, on a host stop (`Interrupted`), on a cancellation of its task, or on the task's deadline (`TimedOut`, ADR 0117 rule 5). Delivery also waits for a `/once` slot, a token of the grant's rate and room in `delivered` (S4 §6.1), each a wake of the same parking.
  4. **Atomic delivery (rule 4.7).** The take of a request from its queue and the resolution of `next` are one step under the thread's queue mutex: an exchange is either delivered to exactly one task, or left in the queue when `next` fails, never taken and lost. The delivered request is charged to `delivered` and `/once`; its body reservation in `buffers` is released (S4 §6.4).
  5. The `Exchange` is built in the task's heap: one copy of the request's bytes into Una values (`Text`, the lists of `segments`, `query`, `headers`), with the UTF-8 check already done by the reader (S2). Its `right` is a fresh reply right (§4), held by the calling task.
  6. **The native path.** `una_rt_server_next(site)` through the host path (sited, with the stopped check), as `una_rt_limit_acquire` of ADR 0117 S6 is; the interpreter dispatches `("HttpServer", "next")` in `machine.rs` beside `("Http", ...)`. Both call one function of `una-http`'s engine, `Engine::next(task, wake)`, so the two engines share the order of delivery.
- **`reply(to, reply)`.**
  1. The reply right must be held by the calling task and unanswered, else `NotHeld` and nothing is sent (rule 4.4, §4).
  2. The reply's checks of rule 13 (status with `204`/`304` and a body, header names and values, the forbidden headers, at most 100 headers and 64 KiB of them): a failure is `BadReply`, nothing is sent, the right stays held.
  3. Serialize into segments and hand them to the connection's serve thread (S4 §6.5: reserve on `replies`, free victims under pressure, push, wake). `reply` never waits on a peer and never fails for pressure.
  4. The exchange's state machine (rule 4.7): the program's `reply` is one of the atomic transitions that end an exchange; when another transition already ended it (the host's `answer` deadline, the peer leaving, a stop, an auto-answer), `reply` returns `unit`, its event shows `ok`, and nothing is sent (rule 14). The transition is a compare-and-swap on the exchange's state in S4's exchange table, so it is one atomic step on every thread.
  5. A successful `reply`, or one discarded by rule 14, releases the reply right: the task no longer holds it (so a second `reply` is `NotHeld`), and the exchange's `/once` slot and `delivered` bytes are given back when the serve thread finishes writing, not at `reply` (the bytes are still in flight).
  6. `reply` never parks: no check point, as S4 states for the freeing loop.
- **`close()`.** Sets the run's closed flag once (compare-and-swap); pushes S4's close message to every serve thread (listeners closed, `503` with `Connection: close` to requests read but not delivered, open exchanges allowed to finish); wakes every task parked in `next` with `Closed`. A second `close` does nothing (rule 1). It accepts `public` only (IF1), so the checker refuses it under a raised program counter (U4003), which the existing sink rule gives since `accepts` of `close` is `public` by default.
- **The host stop** (rule 18, the program's side): the stop path of ADR 0116 rule 14 already wakes parked interruptible operations; `next` is one (ADR 0117 amendment of 2026-10-19, rule 3). Started tasks drain; the auto-answers of the hard stop (rule 18 item 6) are §4's.
- **Trace events** of `next` and `reply` are events of `spec/11 §5` with `instance` `host:HttpServer`, `capability` `HttpServer`, `op` `next`/`reply`, `args` and `outcome` in the reduced form of §5. `close` is an event too, with no arguments.
- **The serve threads start** before `main` when the program can perform an operation of `HttpServer`: S4's static condition (an operation of `HttpServer` in the effect set of the program, computed by the checker and carried in the executable's description as `serve: true` already is) or a `[serve]` table (S6). Accepting begins at the run's first server operation (S4 §4, decision S4-D12): `next`, `reply` and `close` each set the flag.

## 4. Reply rights (rule 4)

- **Representation.** A `ReplyRight` value is a handle `(slot, generation)` into S4's exchange table, an opaque `Int`-sized value in both engines (decision S5-D2: an opaque kind over two 32-bit halves packed in one 64-bit word, as `Hashed` holds its digest; the program cannot read either half). Equality compares the word. The table entry holds the exchange's state (rule 4.7), its connection, its request's byte count, and its **holder**: the id of the task that holds the right, or `none` once answered.
- **Holding.** `next` sets the holder to the calling task and appends the right to the task's **held list**, a per-task `Vec` of rights in the order received (rule 4.5 needs that order). `reply` checks `holder == current task` and the state `open`; on success it clears the holder and removes the right from the held list, O(1) with a swap-remove and an index kept in the entry.
- **Moves at `start e`** (rule 4.2). ADR 0113's copy of the captures of `e` into the started task is the walk that finds the rights: every `ReplyRight` value reachable from the captured values moves to the started task, in the order the copy meets them: the entry's holder becomes the started task, and the right moves from the calling task's held list to the started task's. Native code: the copy of captures is a typed walk already (ADR 0113), and a `ReplyRight` is a leaf of a known type, so the move costs nothing beyond the copy; the interpreter walks only captured values whose type can hold a `ReplyRight` or a function (Costs), which the checker marks at the `start` (§7, IF6 uses the same mark).
- **No other construct moves a right** (rule 4.3): `together`, `together for` and `first of` run for the task that runs the construct; rule 5's U3033 keeps server operations out of them, so no branch can answer a right.
- **The end of a task** (rule 4.5). When a task ends by returning, by a failure, by ending alone past its depth, by a cancellation (`within`, `first of`, a stopped `together`), or at the hard stop, the engine walks the task's held list in order and, for each unanswered right, performs an **auto-answer**: `500 Internal Server Error` for a return, a failure or an end alone; `503 Service Unavailable` with `Retry-After: 1` for a cancellation, a time-out by `within`, or a stop. Each is one of rule 4.7's transitions: when the exchange already ended, nothing is sent, but the task's trace still gains the event `{"seq": n, "task": "<path>", "outcome": {"kind": "unanswered", "status": s}}` (rule 4.7, "an auto-answer after one still appends its `unanswered` event"), so the trace does not depend on timing. The bytes are S4's own answers (§7 of its note). The main task's end is a task's end too: a program whose `main` returns holding a right gets the `500` auto-answer.
- **Determinism** (rule 4.6): the holder is a function of the order of `next`, `start` and `reply` in each task, never of timing; the conformance runs compare both engines on it.
- **Tests without the host.** A `given` handler for `HttpServer` in an example installs a user handler, whose `next` returns an `Exchange` the handler builds; until S7's `test_exchange` lands, such an example cannot build a `ReplyRight`, so the examples of this slice test `reply` only through the host under the test harness (§9), and the handler path is covered by the U3014/`given` cases of the checker. S7 adds `test_exchange`, whose rights live in the same table with a connection of `none`: `reply` on one succeeds, sends nothing, and its event shows `ok`.

## 5. The reduced trace form (rule 1)

- The values of the headers `authorization`, `proxy-authorization`, `cookie`, `set-cookie`, `x-api-key` and `x-auth-token` are written `<credential>` in requests and replies; a body is `{"length": n, "hmac": "<hex>"}`; the values of query parameters, in `query` and in `target`, are written as bodies are; a reply right is `<reply-right>`. Path segments, other headers and statuses stay in clear.
- **The key.** 32 bytes drawn from the operating system's random source when the run starts (`una_hash`'s host source, as S4's placement key is), all zeros under `--serve-script` (S7). The HMAC is HMAC-SHA-256 from `sha2`'s `Sha256` with the standard HMAC construction, which is a dependency of the workspace already (`Keys.hmac`), so no crate joins `Cargo.lock` (decision S5-D3).
- **Where it applies.** In the `args` and `outcome` of the `next` and `reply` events, in human and `--json` output, and in any recording kept for replay (`spec/11 §5`): the reduction happens where the event is built, so no path writes the clear form. The redaction by labels applies on top, as for every event.

## 6. U3033 (rule 5)

- **Where.** `crates/una-check/src/types/stmt.rs`, `together` and `together_for`, and the checker of `first of` (ADR 0117 S3): each already computes the effect set of its branches for ADR 0116's timing (`timing_sites`) and for the authority pass. S5 adds: an operation of `HttpServer`, performed directly in the branch or by a callee whose effect set holds one (transitively, from `Findings`' per-function effect sets, which the authority pass already builds for `spec/05 §3` rule 3), is U3033 at the operation or at the call, "`@server.reply` cannot run in a branch of `together`; answer after the block", with one repair, a description: move the operation after the construct. One lookup per branch over a set already computed: linear in the branches.
- **A function value or a lambda** passed into a branch whose type's `uses` include `HttpServer` is U3033 at the branch too (the branch's effect set includes the value's `uses`).
- **Handlers.** A handler for `HttpServer` installed by `given` in a test: its operations in a branch are U3033 as the host's are, since the rule is about the construct, not the instance.

## 7. Information flow (IF1 to IF7)

- **IF1.** `next` returns `internal Exchange` by its declaration. Whether `next` succeeds is `public`: its failures are decided by no argument, so `decides_failure` returns false for every parameter of `next` (it has none), and the host-stop and `close` reasons are `public` by the existing rules; `TimedOut` under the program's own deadline is labeled by ADR 0116 IF8 and ADR 0117 IF2 as every interruptible operation's is, through the existing `within` plumbing.
- **IF2.** Every argument of `reply` is a sink with `accepts internal`: the existing sink rule (`spec/07 §3` rule 4) applies through the declaration. A `secret` value in a field of `Reply` is U4001 where the reply is made (a constructor field is a flow site).
- **IF3.** `NotHeld` and `BadReply` are decided by `to` and `reply`, capped at `internal`: `decides_failure("HttpServer", "reply", _)` returns true for both parameters, so `decided` is the join of their labels capped at `accepts`, `internal` at most, and `attempt` gives an `internal` `Result`; `if error pass` and `if error fail` are U4002. `close` has no failure.
- **IF4.** No host deadline becomes a value: `reply` after another transition returns `unit`, so nothing of the host's timing is observable in a value (§3). The checker has nothing to add; the conformance run "a reply discarded after `answer`" checks it in both engines.
- **IF6, at `start`.** A `start e` whose captures can hold a `ReplyRight`, by their types, or include a function value, is checked as a `reply` under `pc ⊔ τ(e)` when it has `within`, and under `pc` otherwise, against `internal`: U4003 at the `start` when the label is above `internal`. The mark "captures can hold a `ReplyRight`" is computed from the types of the captured bindings by the existing capture walk of ADR 0113 in the checker (`captured_value`), extended with a predicate "type can hold `ReplyRight`" (the opaque kind itself, a kind with a field of that type, transitively, a list or option of such, or any function type). The same mark tells the interpreter which captures to walk at `start` (§4).
- **IF5 and IF7** need no code: the request stream is input (Question 4, S4's amendment A); a request task's program counter is `internal` after it branches on the request, and the existing rules follow.
- **The label `L_srv`** of S4 §10 (the timing label of the code after the program's server operations) is implemented here as S4 states it: the sites of `S_srv` are the calls of `next`, `reply` and `close`, and the checker's timing pass treats them as S4 §10.1 specifies (the note's P8 condition and the label of what follows a server operation). This slice follows S4's text; where S4's amendment is not yet accepted, the code carries the conservative reading and the PR says so.

## 10. Decisions

- S5-D1 `ReplyRight` elaborates as `Hashed` does: an opaque standard kind with equality and no constructor.
- S5-D2 A reply right is a `(slot, generation)` handle in one 64-bit word; its holder is recorded in the exchange table, and each task keeps its held list in order of receipt.
- S5-D3 The trace key is 32 random bytes per run, zero under a script; HMAC-SHA-256 over `sha2`, no new crate.
- S5-D4 `next` checks `Closed`, then the host stop, before taking a request, so a stopped or closed run never delivers.
- S5-D5 A `given` handler for `HttpServer` is an ordinary handler; the test paths that need a reply right wait for S7's `test_exchange`.
- S5-D6 The serve threads' start condition is the program's effect set (an operation of `HttpServer`) or a `[serve]` table, carried in the executable's description.
