# The C math library's names that the `una` binary alone may leave undefined (#1277): the
# imports of the Z3 solver built into it (ADR 0124 rule 1), which is C++ and calls the platform's
# math library in its search heuristics (restart schedules, local search, lookahead scores), in
# its own floating-point model and in the C++ library's text formatting, never in a value of a
# Una program. scripts/no-libm.sh reads this list for `una` only: the
# release `libuna_rt.a` and every executable that `una build` links stay strict against
# scripts/no-libm.txt, so none of these names is reachable from emitted code.
#
# One entry per line: the platform (`macos`, `linux` or `linux-builtins`, below), the name, and
# the objects of the Z3 library that may import it there, by their member names in `libz3shell.a` (#1953); `#` starts
# a comment. Each name must be on scripts/no-libm.txt. A name is allowed in `una` only on a
# platform it is listed for, and only from those objects: every object of the Z3 library that
# UNA_Z3_LIB names (`nm -A -u`) importing it must be listed here for it, and at least one must
# import it, so a new import of a future Z3 (a new supply-chain/z3.lock) in another object fails
# the check until this list names it, by review. The shipped Linux `una` is checked by its link
# trace too (scripts/no-libm.sh --link-trace, from scripts/check-release.sh): there every object
# of the link that references the name must be one of these objects of the Z3 library the lock
# pins, so a reference of libstdc++.a's own objects, of Rust code or of any other object fails.
# A name `una` imports that this list does not hold for the platform fails. Objects from
# `nm -A -u` of the library of supply-chain/z3.lock: 2026-10-31, macOS arm64; 2026-11-11 and
# 2026-11-25, Linux aarch64 (#1951, #1953).
#

# Linux, glibc and GCC's libstdc++ (#1951). The `std::format` of libstdc++ 13 formats a
# floating-point value in its header (`std::__format::__formatter_fp<char>::format<T>`, which
# calls `frexp` for `double`, `frexpf` for `float`, `frexpl` for `long double`), so each Z3
# object that instantiates it imports the three; Apple's libc++ formats through `std::to_chars`
# in the dylib and its Z3 imports none of them. libstdc++.a's own importers of `frexpl`
# (hash_tr1.o, hash_c++0x.o) are not Z3 objects: the link trace of the shipped `una` must show
# no reference of theirs.

linux frexpf array_decl_plugin.cpp.o ast.cpp.o bv_decl_plugin.cpp.o datatype_decl_plugin.cpp.o dl_decl_plugin.cpp.o seq_decl_plugin.cpp.o
linux frexpl array_decl_plugin.cpp.o ast.cpp.o bv_decl_plugin.cpp.o datatype_decl_plugin.cpp.o dl_decl_plugin.cpp.o seq_decl_plugin.cpp.o

# `remainder` is called by `hwf_manager::rem` of hwf.cpp, Z3's hardware floating-point numbers:
# dead code, referenced by no object of the Z3 library, on Linux and on macOS (#1951 review, L4).
# The macOS library imports it too, but ld64 drops each unreferenced function of an object, so
# the macOS `una` does not; GNU ld keeps the whole text section of hwf.cpp.o (Z3 is not built
# with -ffunction-sections), so the Linux `una` does.
macos remainder hwf.cpp.o
linux remainder hwf.cpp.o
#
# `linux-builtins`: the names that Z3 objects refer to on Linux and that the link of `una`
# resolves inside it, to the compiler_builtins of the pinned Rust toolchain (its weak
# definitions of the math functions, Rust's own code, not the platform's C library), so that
# `una` does not import them and `nm -u` cannot see them; the link trace of the shipped `una`
# shows them (#1953). Only the trace mode reads these entries: a reference must be from one of
# these Z3 objects, and the definition must be compiler_builtins' or a shared library's; `una`
# may not import these names, since they are not `linux` entries. The objects are those that
# refer to them in the trace of the shipped `una` of 2026-11-25.
linux-builtins ceil pdd_solver.cpp.o
linux-builtins sqrt hwf.cpp.o sls_arith_lookahead.cpp.o sls_bv_engine.cpp.o sls_bv_lookahead.cpp.o
#
# x86-64 Linux (#2106; the Owner's decisions of 2026-11-27, recorded in the release's decisions,
# card #2354), each scoped to x86-64 by `@x86_64` (`uname -m`, #2365): on aarch64 each of these is
# an instruction or inlined, and none is allowed there; on the x86-64 baseline
# (no SSE4.1, no FMA at build time, ADR 0114 rule 6.5) the compiler calls the function.
# `nearbyint`: Z3's hardware floating-point numbers (hwf.cpp.o) call it, and the link binds it to
# the platform's libm, as `remainder` above: a solver import, in `una` only (decision (a)).
linux@x86_64 nearbyint hwf.cpp.o
# `fma`: hwf.cpp's `hwf_manager::fma` calls it, and the link binds it to the toolchain's
# compiler_builtins, whose hardware paths ADR 0120's amendment of 2026-11-27 allows (decision (b)).
linux-builtins@x86_64 fma hwf.cpp.o
#
# `linux-rust-builtins`: Rust objects of the release graph, each by its exact member name (the
# crate, its metadata hash and its codegen unit, so that another build of the crate fails closed
# until this list names it), whose references to a name resolve to the toolchain's
# compiler_builtins, never to the platform's libm: in the link trace of `una` (the definition
# must be compiler_builtins' and `una` may not import the name) and in `libuna_rt.a` (only where
# the same archive defines the name in a compiler_builtins member). An executable that `una build`
# links stays strict. The toml crate's object takes `%` of an f64 and of an f32, which the x86-64
# baseline lowers to calls of `fmod` and `fmodf` (decision (c)).
linux-rust-builtins@x86_64 fmod toml-a2ec2fe2cccba1d6.toml.a72671b9309b829-cgu.14.rcgu.o
linux-rust-builtins@x86_64 fmodf toml-a2ec2fe2cccba1d6.toml.a72671b9309b829-cgu.14.rcgu.o
#
# `linux-rt-builtins NAME FUNCTION`: a reference to NAME, in `libuna_rt.a` only, by the member of
# the toolchain's compiler_builtins that defines FUNCTION (its role, never its file name, which
# carries a hash), and only where the same archive defines NAME in a compiler_builtins member.
# Rust's port of `cbrt` in compiler_builtins calls `fma`, which binds to compiler_builtins' own
# weak `fma` (decision (d), the coordinator's under the Owner's (b) and (c), for confirmation).
linux-rt-builtins@x86_64 fma compiler_builtins::math::libm_math::cbrt::cbrt
