# What the `una` binary alone may ask the dynamic loader for beyond scripts/load-commands.txt
# (#1277): the C++ runtime of the Z3 solver built into it (ADR 0124 rule 1), read by
# scripts/load-commands.sh for `una` only. An executable that `una build` links stays strict
# against scripts/load-commands.txt. The format is that file's: PLATFORM KIND VALUE, then `#`
# and the reason; an entry allows, it never requires.
macos dylib /usr/lib/libc++.1.dylib  # the system's C++ runtime, which Z3's C++ code needs (una-z3's build script links it, ADR 0124 rule 1: on macOS `una` uses the system's libc++)
#
# Linux: `una` links libstdc++ statically (crates/una-z3/build.rs, `static:-bundle=stdc++`,
# ADR 0124 rule 1, #1956) and GCC's libgcc.a (scripts/release.sh, -static-libgcc), so the C++
# runtime adds no NEEDED entry. The unwinder libgcc_s.so.1 stays NEEDED, as in every Rust
# executable of the -gnu targets (the standard library links -lgcc_s); scripts/load-commands.txt
# allows it for every artifact. The math functions Z3 imports (scripts/no-libm-una.txt) are
# glibc's libm, a library of its own there. Observed 2026-11-11 (aarch64, #1956): libgcc_s.so.1,
# libm.so.6, libc.so.6, ld-linux-aarch64.so.1 and the interpreter /lib/ld-linux-aarch64.so.1.
# Anything else fails the check until it is reviewed and listed here.
linux needed libm.so.6  # glibc's math library, for the solver's imports of scripts/no-libm-una.txt only
