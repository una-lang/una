- **Security: `Http` name lookups hold at most 64 threads** (#1575, `spec/24 §4` rule 2). The system's resolver has no timeout, so `una-http` looks a name up on a thread of its own, which a request abandons at its deadline and which lives until the resolver returns. Each request started such a thread, with no bound, in every release from v0.3.0 to v0.3.17, in both engines: a program that kept requesting names, under its grants, whose lookups stalled (a slow or unreachable DNS authority) kept one thread for each request it gave up on, as long as each lookup ran, so the threads of the process could grow with the rate of its requests. The lookups of the process now run on at most 64 threads, taken from a counting semaphore in O(1). A request that finds all 64 taken waits for one until its deadline, with no queue of lookups, and then fails with `TimedOut`, as a request past its deadline always does; no lookup starts for a request whose deadline has passed, before or after it waited for a slot. An address literal, such as `127.0.0.1` or `[::1]`, is read without a thread, as the resolver read it, and takes no slot. A request that gets a slot and resolves in time behaves as before. The cost is a bounded denial of service in place of unbounded thread growth: the 64 slots are shared by every name, so while 64 lookups of the process stall, every request to any host name, healthy ones included, waits for a slot and fails with `TimedOut` at its deadline, until a stalled lookup returns; a lookup that never returns keeps its slot for the rest of the process. Requests to address literals are unaffected. The cap is fixed at 64 and not configurable, and the per-name and per-zone bounds of main (#1265) are not part of this fix. Rebuild native executables with the patched toolchain, since `una-http` is linked into them.
