- **`Files`: a grant on the current directory reaches its files again, confined as any other** (#2144, `spec/13 §5`, `spec/14 §3` rule 2; a regression of #1459, never released; a security fix). The prefix of `files:.:<modes>` (or of `./` or `a/..`, a path that names the directory the grant is relative to), in a `--grant` flag, in the grants of an executable and in `[run] grants` of a package run as `una run .`, was held as the empty path, which no host resolves, so since #1459 every `Files` operation under such a grant ended with `NotFound` and wrote nothing. In released versions, up to 0.4.0, a `Files` grant on the current directory (`.`, `./`, `a/..` with an empty or `.` base) was not confined against symbolic links: a path under it was opened as written, so a link in that directory was followed out of the grant, for reads and writes; `..` and absolute paths were refused as always. This is fixed: such paths are `Denied`. That prefix is now `.`, which resolves to the directory itself: the operation is given the canonical form of a directory inside it joined with the final component, and a missing directory is still `NotFound` with no path given to the operating system, in `una run` and in native executables. A grant path that goes up two or more levels now means what it says: `..` no longer removes a `..` before it, so `files:../..:<modes>` is the directory two levels up (it was the empty prefix) and `files:../../x:<modes>` is `../../x` (it was `x` in the current directory, in every released version). No other prefix changes.
