- **`Files` confinement: the record of #1459 corrected, and its rule tested where it was argued** (#2138, `spec/14 §3` rule 2; tests and documents, no behavior changes). The v0.5.0 entry of #1459 says that the value of a `Files` operation below a missing directory changed from `Io` to `NotFound` in two classes and in no other; there is a third, which v0.5.0 also changed and that entry does not name: a NUL in a component after the missing directory (`Files.read("missing/a\u{0}b")`), `Io` in v0.4.0, where the host's interface refused the path as written before any lookup, and `NotFound` from v0.5.0. It is pinned in both engines, with what did not change: a NUL in the final component of a path whose directory resolves is still the operation's own `Io`, and a NUL in a directory that confinement must resolve is `Denied`. The check of one long final component below a missing directory uses 300 bytes, more than the 255 a host takes in a name, where its 200 tested nothing. Three conformance cases state the rule and run in both engines: `runtime/files_missing_directory` (`NotFound` for a read and a write), `runtime/files_missing_final_component` (a read is `NotFound`, a write creates the file) and `runtime/files_component_not_directory` (`Io`). In the native runtime, `Files.read` and `Files.write` are now tested whole in a world that keeps every path it is asked about: below a missing directory no read and no write reaches it, and no lookup goes past that directory; what is still read in the source is that the two operations pass the machine to that code and nothing else. `spec/14 §3` rule 2 gains one sentence: the dangling symbolic link that is `Denied` is the directory or the grant prefix itself, and a grant prefix whose path passes through a dangling link does not exist, `NotFound`. The entry of UNA-SA-022 in `docs/security/advisories.md` keeps its account of v0.4.0 and adds the behavior since #1459.
