- **Soundness: deadlines armed and fired in nanoseconds, and the timer thread started before `main`** (#1151, ADR 0116 amendment P8 and P13, `spec/27 §1` rule 4 and §5, `spec/26 §2` and §7). In native code a `within`, an iteration of `for ever within` and a tick of the driver are armed on the monotonic clock in nanoseconds, not whole milliseconds, so each lasts exactly `d` from its arming instead of between `d - 1` and `d` milliseconds by the phase that earlier code, possibly on `secret` data, left; the timer thread sleeps until the earliest exact deadline and fires each timer at its own nanosecond, never at the end of a millisecond slot, with each millisecond slot of the timing wheel's finest level keeping its timers in a min-heap by exact deadline (arming O(log s), O(1) on average; cancelling O(1), lazily in the finest level and at once above it; firing O(log s) amortized). A program with a `within`, a `for ever` or a task construct starts the timer thread with its workers before `main`, so whether an earlier `within` ran no longer changes the cost of the next one; one that cannot start stops the run there with U6003, and a program without these constructs starts no timer thread. Virtual time and `Clock.now` stay in milliseconds.
