- **Security (#1708): `internal` data no longer order the turns of started tasks** (`spec/27 §8` rules 2, 3 and 5, the ADR 0117 amendment of 2026-11-22, second, proposed for the Owner's decision). In the interpreter and in native code under `--virtual-time`, a task switches after 1024 check points in its turn, so a count of check points that a request of `HttpServer` or another `internal` value decided ordered the public prints and trace events of the tasks, the same in every run, and a held task (#1545) could still be let go when its own turn ended. The checker now marks in Core IR each call, operation, loop, `start` or prelude function that applies a function argument whose running data above `public` decide as `uncounted`; its check points, in its callees and in the tasks it starts included, neither advance nor end the turn, so the order of turns follows `public` data only, for every label. The `for` and `for until` loops whose bound, list or condition is above `internal` are accepted again, the hunt's probe of #973 included: such a loop ends and pushes no frame, and its public prints are the same for every key. Every other check point that data above `internal` decide stays U4002, since it can still decide a task's depth (#1677), whether a held task is let go at a park of its own, whether a `for ever` loop runs or how many tasks run at once; at `internal` those stay a known residual, which the report lists as a `task switch`. The cost is O(1) per uncounted construct and one O(1) test per check point; a task does not switch during uncounted work, which runs to its end or to a park before another ready task runs. Native code under the real clock is unchanged; its order across tasks is real time, out of model.
