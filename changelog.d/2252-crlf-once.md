- **Project files are decoded exactly once, so a lone carriage return is always reported** (#2252, `spec/30 §1` rule 1, `spec/01 §1`; kind: U7008, U7009). `ita.una`, `ita.lock` and `itaty.una` were decoded a second time by most commands, which read a text the source database had already decoded: a lone `\r` just before a `\r\n` (`\r\r\n`) decodes to a `\r\n`, which the second decoding read as one more line end, so `una check`, `una fmt`, `una ita remove` and `una ita yank` accepted the file, and an ill-formed UTF-8 sequence, read as U+FFFD, went unreported too. The readers now take the file as written, which they decode once and whose bytes every range names, or a file decoded once, which they read as it is and whose decoded text every range names; every command passes the file it decoded. Each such file is now reported (U7008 for `ita.una` and `itaty.una`, U7009 for `ita.lock`) at the `\r`, or at the ill-formed sequence, by every command, and nothing is written. Files with `\r\n` line ends, and every file without a lone `\r` or an ill-formed sequence, read as before. New tests cover `una ita add` and `una ita yank` on a file with `\r\n` line ends. O(n) in the file's size, as before.
