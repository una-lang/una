- **The bytes held are never read torn by a change of the allocator's limit** (#2151): `cap` 0.1.2 derives the bytes the process holds as `limit - remaining` and changes its limit in two writes, so a read between them returned close to `usize::MAX`, and a sibling task's budget check or copy step that read it could stop the run with U6003 at its own site, where a run that was already ending should have reported its real stop. The runtime now changes the limit and reads the bytes held under its own sequence lock: a read that overlaps a change is retried until the change is done, whatever its length, and the allocation path is unchanged. A stop that ends a run also claims the end of the process before it lifts the limit, so a sibling that stops afterwards parks. The same lock covers the lift at the normal end of a run and the debug build's high-water mark, which skips a sample rather than wait in the allocator. No budget, ceiling or test bound changes.
