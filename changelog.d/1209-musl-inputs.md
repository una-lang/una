- **musl inputs for Linux, step 4a of the internal linker** (#1209, ADR 0124 rules 12, 16, 20 and 24). `rust-toolchain.toml` installs the `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` targets, and the local-ci image carries them. On Linux, `scripts/release.sh` takes musl's `libc.a`, `rcrt1.o`, `crti.o`, `crtn.o`, `crtbeginS.o`, `crtendS.o` and `libunwind.a` from the pinned toolchain's `self-contained` directory of the musl target of the machine's architecture, refuses any whose digest differs from the new `supply-chain/musl.lock`, prints each digest (`musl: <target>: <file> sha256 <digest>`), and `una`'s build script checks them against the lock and the target's architecture and embeds them, for that target only (`scripts/check-release.sh` checks the packed `una` records the pinned digests); the build record gains `musl_sha256s` and `libunwind_sha256`, empty on macOS and in a development build; the report does not list them yet (rule 28, later in step 4). A Linux `una` grows by about 6.8 MB. A Linux release checks them against their digests before each link, as it checks the runtime. Cranelift compiles for the musl triple on Linux, which changes no byte of the objects it writes (a test pins it). `scripts/scan-musl.sh TARGET` scans those inputs and the standard library of the target through `una-link`'s new ELF reader: no `R_*_IRELATIVE` or indirect function, every relocation type in a loaded section in rule 24's list, the position-independence restrictions, no common symbol in the standard library, the archives' symbol tables both ways, relocation sections the reader would skip, and musl's version (1.2.5 in Rust 1.98.1). `una build` still links Linux executables through `cc`, unchanged; the internal linker of Linux comes in the next slices. The getting-started guide notes the name-resolution limit of musl executables.
