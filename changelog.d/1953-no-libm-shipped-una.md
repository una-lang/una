- **The C math library check reads the shipped Linux `una`, object by object** (#1953, follow-ups of the #1952 review). `scripts/release.sh` links on Linux through `scripts/link-trace.sh`, which adds GNU ld's `--trace-symbol` for every name of `scripts/no-libm.txt` and keeps the trace of the `una` link, and `scripts/check-release.sh` runs `scripts/no-libm.sh --link-trace` on the packed `una`, the runtime built into it and the examples' executables: every object of the link that refers to a math name must be, byte for byte, an object of the Z3 library that `supply-chain/z3.lock` pins and one that `scripts/no-libm-una.txt` names for it, so a reference of libstdc++.a's own objects (`hash_tr1.o`, `hash_c++0x.o` import `frexpl`) or of Rust code fails, and so does a math function linked in statically. The trace of the aarch64 Linux `una` built with this change shows no libstdc++.a object referring to a math name; it shows that Z3's `ceil` and `sqrt` calls resolve inside `una` to the weak definitions of the pinned toolchain's compiler_builtins, which `nm -u` could not see: they are listed as `linux-builtins` entries, allowed from the Z3 objects named only. `scripts/no-libm-una.txt` now lists, per platform, the Z3 objects that may import each name, and the check of the release `una` ties each name to those objects instead of to the name alone. The canaries add a `una` importing two names with a Z3 stand-in importing only the first, stand-in Z3 objects outside the list, and on Linux real traced links. The list's comment now says that `hwf_manager::rem` is dead code that no Z3 object calls.
