- **Resolution and the `una ita` commands** (#997, ADR 0122 rules 23 to 25 and 57, `spec/30 §6` and `§10`). `una ita lock` resolves by minimal version selection over what is held offline, each path dependency as its directory holds it, within the bounds of rule 23, the root's needs counted as a release's. A registry need is refused with the new code U7013, no resolution, since this release holds no registry's per-name state, and a source is refused as a whole rather than resolved from a partial view; an avoided version with no later release and a bound exceeded are U7013 too. Every change of the lock is printed as a review before it is written: per package, its origin, versions, digests, the ceiling granted, and what its code uses at tier 0, also as `changes` in `una.ita/1`. New: `--dry-run`; `una ita update [<name>...]` with `--cooldown`, `--now` and the `--accept-...` flags; `una ita add <name> [<version>] [--as] [--from]`, which writes `ita.una` and the lock only when the resolution succeeds, and so, in this release, never for a registry need; and `una ita verify`, which verifies each locked registry package again in `vendor/ita/` and in Itaoca. `una ita fetch` and rule 26's check of two release statements join with the registry client. No command opens a connection or starts a program. Each consent flag names what it accepts, `--accept-authority <package>` and `--accept-trust <package>@<digest>`, and without it the review is printed with the flags to copy and nothing is written; consent is checked against the digest of the bytes the package was loaded from. Which identities admit a pre-release is a fixed point, so the result never depends on the order of needs. `una ita update <names>` resolves only the named needs; `add` and `remove` write the lock, then `ita.una`, putting the lock back on failure; and `una ita verify` reports a package whose copies match the lock as not yet verified (U7013), since the owner's key chain is not held. Itaoca stores a provenance without ever replacing one, and new fuzz targets read provenances, archives and `ita.lock`. `ita.lock` belongs to the toolchain: a symbolic link at its name is replaced by the lock, never followed, and the file it led to is left as it was; `ita.una` is written through a link only when it leads inside the package, as for sources.
