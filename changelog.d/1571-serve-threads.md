- **The serve threads of a program that serves, over live sockets, in both engines** (#1571, ADR 0123 S4 amendment B.2 and rule 18, `spec/31 §6` rule 14), edition 0.4 preview. A run whose entry functions use `HttpServer` and that holds a `serve:` grant starts its serve threads, their pollers and wake pairs and the accept poller before `main`, over the listeners it bound, draws the key of its reduced trace form from the host's random source, and accepts nothing until its first server operation; `next` waits for the engine on the real clock and fails with `TimedOut` at its deadline. The run's watcher of host stops hands the host stop and the hard stop to the engine, and the run's end drains the engine as a host stop does, for at most the grace period, then makes the hard stop. At the hard stop (U6007), in both engines, the engine's hard stop comes first: from then on it discards the program's answers and replies that have not yet taken their exchange, its serve threads answer every exchange still open `503` with `Retry-After: 1` in one non-blocking write, and the host writes no `unanswered` event, in the interpreter as in native code. A reply already in progress when the hard stop comes may be lost, with neither it nor the `503` reaching the peer. At an internal error (U8001) native code does the same, while the interpreter's tasks answer their rights `503` themselves with their `unanswered` events, as at an abort of the run. A run under `--virtual-time` that holds a `serve:` grant is a usage error before `main`, in `una run` and in executables. In native code the serve threads' start, stop and join and the engine's panic hook are reached only through a call that the code of a program with an operation of `HttpServer` makes before the run starts, so an executable that serves nothing links none of them (it still links the table of reply rights and the answer of an exchange, which the run's end calls when it serves); in a program that serves, the panic hook is installed over the runtime's, from one place, before any thread of the run starts. New tests run servers over loopback in both engines on the real clock, and two timing oracles, `serve_prefix_secret` and `serve_prefix_early_peers`, check that set-up code before the first server operation, and peers that connect during it, leave no trace in the time of a later reply.
