- **The serve threads of a program that serves, over live sockets, in both engines** (#1571, ADR 0123 S4 amendment B.2 and rule 18, `spec/31 §6` rule 14), edition 0.4 preview, not yet reachable by `una run` or `una build`, which still refuse a program that serves (`spec/31 §1` rule 10). A run whose entry functions use `HttpServer` and that holds a `serve:` grant starts its serve threads, their pollers and wake pairs and the accept poller before `main`, over the listeners it bound, draws the key of its reduced trace form from the host's random source, and accepts nothing until its first server operation; `next` waits for the engine on the real clock and fails with `TimedOut` at its deadline. The run's watcher of host stops hands the host stop and the hard stop to the engine, and the run's end drains the engine as a host stop does, for at most the grace period, then makes the hard stop. At the hard stop, in both engines, the engine answers every exchange a task still holds `503` with `Retry-After: 1` in one non-blocking write before the host drops it, and no `unanswered` event is written: the interpreter now writes what native code writes. A run under `--virtual-time` that holds a `serve:` grant is a usage error before `main`, in `una run` and in executables. The panic hook of the serve engine is installed with the runtime's, from one place, before any thread of the run starts. New tests run servers over loopback in both engines on the real clock, and two timing oracles, `serve_prefix_secret` and `serve_prefix_early_peers`, check that set-up code before the first server operation, and peers that connect during it, leave no trace in the time of a later reply.
