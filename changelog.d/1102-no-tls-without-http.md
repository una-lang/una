- **An executable that never uses `Http` links no TLS code** (#1102, ADR 0074 H7). Dead stripping left about 50 symbols of `ring`'s assembly kernels (SHA-2, AES, ChaCha20, P-256) in every executable on macOS: `ld64` does not dead-strip an object assembled without `.subsections_via_symbols`, and the archive member of the runtime's entry points named the `Http` client, so loading it pulled `rustls` and `ring` in. The runtime is now two static libraries. `libuna_rt.a` holds no TLS code: the interpreter and the runtime use the new crate `una-http-core`, the client without TLS, and `una-http` keeps the TLS client over `rustls`, which `una` installs at start. `libuna_rt_http.a`, built by the new package `una-rt-http` from the runtime's source with `una-http`, is what `una build` links into an executable whose code calls an `Http` operation. Release archives ship both under `lib/`, `install.sh` installs both, `scripts/check-release.sh` refuses a `libuna_rt.a` with a TLS symbol, and `UNA_RT_HTTP_LIB` names the second library as `UNA_RT_LIB` names the first (by default it is found beside it). The tests read executables with the toolchain's `llvm-nm`, so `rust-toolchain.toml` adds the `llvm-tools` component. A source build is `cargo build --release -p una-cli -p una-rt -p una-rt-http`.
