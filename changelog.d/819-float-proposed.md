- **Proposed: floating point, `F64`** (#819, ADR 0114, Proposed). Edition `0.3` would gain `F64`, IEEE 754 binary64, with literals such as `0.5` and `6.674_30e-11`, correctly rounded arithmetic and `sqrt`, and explicit conversions only. Results would be bitwise identical in both engines and on every target: one canonical NaN in memory and at every observation, no fused or reassociated operations, subnormals kept, the floating-point environment set and self-tested at start (U6006), and the runtime's own routines instead of the platform math library. `==` would compare bits, so `nan() == nan()` and `-0.0 != 0.0`, and `<` would be IEEE totalOrder, so floats work as map keys and in `sort`; the IEEE comparisons are named methods (`ieee_lt` and the others), and comparing with a literal zero is an error (U2033), repaired by `is_zero()` for an equality and by the IEEE methods for an ordering. Floats would print by the shortest text that reads back to the same bits, and parse correctly rounded. Contracts over floats would be verified exactly, through the solver's floating-point theory, on a slice of the hypotheses and under a fixed size bound; the queries of every program without `F64` stay byte-identical, and every float query runs with a fixed step budget. Units apply (`F64 of Meter`). A package function named `to_f64` on integers becomes an error in edition `0.3`. Transcendental functions and `F32` are later steps.
