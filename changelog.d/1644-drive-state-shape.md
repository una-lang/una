- **The state of a driven module is one type, labels aside and refinements included** (#1644, `spec/26 §2` rule 2). The host's shape check of `una run` and `una build` compared the labels inside a function type of the state, so `init() -> fn(Int) -> Int` with `step(edit f: fn(Int) -> secret Int, ...)`, which `una check` accepts, was refused with exit code 2; it now runs in both engines, the labels being the checker's (U4001 at each hand-off, #1642). The check also ignored refinements, so `init() -> Int` with `step(edit n: Pos, ...)` ran with a state nothing proved positive: the interpreter stopped at a division by zero the verifier had discharged, and the native build, which elides that check, printed a wrong result. A refinement of the state in `step` or `on_stop` must now be the one of the result of `init`, at every position, and a function type in the state must have the same `uses` and `fails`; otherwise the module lacks its shapes, exit code 2. Edition `0.4` preview: a driven module whose state is refined differently in `init` and `step` or `on_stop` no longer runs; declare the same refinement in each.
