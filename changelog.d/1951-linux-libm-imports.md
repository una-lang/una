- **The C math library check knows the solver's imports on Linux** (#1951). On aarch64 Linux the release `una` imports `frexp`, `frexpf`, `frexpl` and `remainder`, and `scripts/no-libm.sh` failed there. Each comes from the Z3 library built into `una` alone (`nm -A -u` of the library of `supply-chain/z3.lock`, and the GNU linker's trace of the link): the three `frexp` names from `std::__format::__formatter_fp<char>::format` of GCC's libstdc++ 13, a header template that six Z3 objects instantiate, and `remainder` from `hwf_manager::rem`, Z3's own floating-point numbers. `una` built without the solver, `libuna_rt.a` and all 126 executables of the check import none of them, nor does any Rust object of the build. macOS does not show them: Apple's libc++ formats through `std::to_chars` in its dylib, and ld64 drops the unreferenced `hwf_manager::rem` that GNU ld keeps with the rest of `hwf.cpp.o`. The four names join `scripts/no-libm-una.txt`, each still tied to the Z3 library's own imports and still rejected everywhere else, and `scripts/no-libm-test.sh` now checks every name of that list on its own in each scope.
